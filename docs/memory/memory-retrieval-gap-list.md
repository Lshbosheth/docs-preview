# 记忆检索方案缺口清单

这篇是《[记忆检索演进方案](./memory-retrieval-evolution-plan.md)》的补充。那篇讲的是"应该演进成什么样"，这篇只记一件事：**按现在的方案直接开工，会在哪些地方卡住。**

结论先放前面：方案的方向没问题，问题集中在**写入侧、生命周期和查询预处理**这三块。它们都不在原文档的叙述主线上，但缺了其中任何一个，后面的向量检索都拿不到预期效果。

## 现场事实

先确认一个实现现状，避免继续在错误前提上讨论。

`scripts/memory-context-builder/build-context.mjs:1037` 已经有一个 `Open Loops` 段落，但内容是三条硬编码的行为指令：

```text
- Use retrieved event and summary context only when it is relevant to the current message.
- If memory conflicts, prefer newer memory.
- If retrieved memory is insufficient, say so instead of guessing.
```

这里放的是"怎么用记忆"的提示词，不是待办数据。

所以更准确的描述不是"记忆单元缺少状态设计"，而是：**注入位已经留好，缺的是往这个位子里写数据的那条链路。** 水管接口在，水源没接。

## 缺口一：写入侧完全没有设计

原方案从"原始会话"直接画箭头到"结构化记忆单元"，但没有说明这个箭头由谁执行。

必须定下来的问题：

| 问题 | 说明 |
| --- | --- |
| 抽取时机 | 每轮对话后台抽，还是靠 `daily-memory-maintenance.mjs` 批量抽 |
| 抽取执行者 | 用哪个模型、跑在哪条进程里、失败了怎么办 |
| 幂等策略 | 跨天谈同一件事时，必须 upsert 回原 id，不能每天新建一条 |
| 状态收敛 | 谁负责把 `pending` 改成 `done`，是模型判断还是显式确认 |

幂等这条最容易被忽略，也最容易毁掉整个 open loop 机制。如果每天都新建一条"确认 GPT Live 是否可用"，一周后向量检索会同时召回七条几乎一样的记忆，去重逻辑再怎么写都会漏。

建议约定：open loop 的 id 由主题生成而非时间生成。

```text
open-loop:gpt-live-check          ← 稳定 id，跨天更新同一条
open-loop:2026-08-06:gpt-live     ← 不要这样，每天会产生新记录
```

检索层做得再精细，写入器不可靠的话，那张表永远是空的。**写入侧优先级高于向量索引。**

## 缺口二：状态没有垃圾回收

原方案定义了五种状态，但没有人负责推进状态。`pending` 只会被创建，不会自己过期。

半年之后的结果是每轮召回都端上来几十条早就不做了的事项，而且它们全都合法地停在 `pending`。

需要一个兜底 TTL 规则：

| 规则 | 动作 |
| --- | --- |
| `pending` 超过 7 天无更新 | 降权，不再优先注入 |
| `pending` 超过 30 天无更新 | 自动标记 `expired` |
| `blocked` 超过 14 天无更新 | 提醒一次，或降级为 `expired` |
| `done` 超过 30 天 | 移出召回候选集，仅保留可回查 |

清扫动作挂在每日维护脚本里跑一次即可，不需要实时。

关键点：**TTL 是兜底，不是主要状态流转手段。** 正常路径仍然应该由对话中的显式信号来更新状态，TTL 只负责收拾没人管的残留。

## 缺口三：查询侧缺指代消解（对命中率影响最大）

原方案的检索流程假设"当前消息"里带着可用的检索信号。实际的消息经常长这样：

```text
那个咋样了
继续吧
它修好了没
昨天说的那个事
```

这些 query 里没有任何实体。向量检索和关键词检索会同时哑火——不是排序不对，是压根没有可用的查询内容。

考虑到日常会用语音转文字，这类省略主语的短消息占比不低，这一层不能留到后期再补。

需要在检索之前插入一步查询改写：

```text
原始消息:  它修好了没
  + 最近 N 轮对话
  -> 改写为:  GPT Live 的可用性检查完成了吗
  -> 再进入向量 / 关键词 / 状态检索
```

同时把相对时间解析成绝对时间窗，供元数据过滤使用：

```text
昨天     -> [2026-08-09T00:00, 2026-08-09T23:59] +08:00
上周     -> [2026-08-03, 2026-08-09]
之前那个 -> 不做时间过滤，转为按 open loop 状态优先
```

这一层决定前面所有召回工作有没有意义，**应该放进阶段 0，和状态 schema 同批做。**

## 缺口四：注入预算需要分区硬配额

原方案只写了"限制最终注入条数与字符数"。全局限额有个具体的失效场景：某轮事件命中特别多，把 open loop 直接挤出上下文——而 open loop 恰好是最不该被挤掉的那部分。

改成按段位切死各自的配额：

```text
稳定记忆        <= A 字符   超出则截断，不占用其他段
Open loop       <= B 字符   保底至少 1 条，优先 pending / in_progress
检索事件        <= C 字符
每日摘要        <= D 字符
合计            <= 总预算
```

`build-context.mjs` 里已经有 `formatBudgetStats`（`build-context.mjs:1048`）在按段统计字符和估算 token，顺着现有结构加分区上限就行，不需要重写。

配额之间不互相借用。宁可某段空着，也不要让一段吃掉另一段。

## 缺口五：评测集要落成可执行的东西

原方案的验收表格写在文档里，只能靠人读。这样的话，那套 `0.40 / 0.25 / 0.15 / 0.10 / 0.10` 的权重永远只能凭"这次好像想起来了"来判断好坏。

需要落成文件和命令：

```text
eval/
  cases.jsonl          固定用例，含 query、期望命中 id、期望不命中 id
  run-eval.mjs         跑全量，输出 Recall@K / Precision@K
  reports/
    2026-08-10-baseline.md
    2026-08-12-vector-shadow.md
```

用例里要显式写"期望不命中"，否则误召回率无法度量——只测该找到的，把阈值放宽就能刷高分。

报告进 git，调权重前先有基线。

## 其余可以顺手带上的

### 冲突消解需要形式化

原方案只说"新记忆优先"，这条规则在长期偏好和一次性状态冲突时会给出错误答案。

加显式指针，并写清优先级：

```json
{
  "id": "event:2026-08-07:gpt-live",
  "supersedes": ["event:2026-07-20:gpt-live"],
  "superseded_by": null
}
```

规则：一次性状态之间按时间新旧覆盖；长期偏好不被单次临时状态覆盖，需要显式的偏好变更事件才能改写。

### 召回 trace 提前到阶段 0

原方案把"记录每次召回为何命中"排在阶段 3。这件事成本几乎为零，而后面所有调优都依赖它，没理由等到最后。

每次注入落一条日志：命中了哪些 id、各项分值多少、哪些候选被裁掉、为什么被裁。

### 检索链路需要硬超时

记忆检索卡在用户消息和模型回复之间的同步路径上。embedding 服务抽风时，微信那头会明显变卡。

约定降级策略：

```text
query embedding 超过 800ms 未返回
  -> 放弃向量召回
  -> 仅走关键词 + 状态过滤
  -> 记录降级日志，不影响回复
```

向量检索是增强项，不能变成可用性依赖。

### 编码问题要先确认

`zvec-memory-plan.md` 提到 `build-context.mjs` 里的中文规则在 PowerShell 默认读取下显示为乱码。在动检索逻辑之前先确认这批规则的实际内容，否则会在看不清的旧规则上叠新逻辑。

## 优先级建议

| 优先级 | 缺口 | 理由 |
| --- | --- | --- |
| P0 | 写入侧链路 + 幂等 | 没有它，结构化记忆表是空的 |
| P0 | 查询改写 / 指代消解 | 没有它，短消息场景全部哑火 |
| P0 | 召回 trace | 成本极低，是后续所有调优的前提 |
| P1 | 状态 TTL 与清扫 | 短期不痛，一个月后开始明显劣化 |
| P1 | 注入分区配额 | 现有代码结构改动小，收益直接 |
| P1 | 可执行评测集 | 引入向量之前必须有基线 |
| P2 | 冲突消解指针 | 记忆量上来之后才会频繁触发 |
| P2 | 检索硬超时 | 接入云端 embedding 的同批做即可 |

三个 P0 都不涉及向量数据库。**先把写入、改写、可观测这三件事做完，再谈 embedding。**

## 2026-08-10：方案侧逐条回应

先给总判断：这份审查大部分成立。《演进方案》原本主要回答“目标结构是什么、为什么不能只做向量检索”，不是一份可以直接照着编码的实现规格；写入器、生命周期和查询预处理确实需要补成阶段 0 的正式设计，不能靠实现者临场猜。

不过有几处现场判断和具体做法需要修正，下面把“接受什么、怎么落、哪里不同意”说清楚。

### 先纠正 `Open Loops` 的现状

`build-context.mjs` 预览里的 `## Open Loops` 不是已经留好的数据注入位。它目前只是 preview 中一个命名不准确的静态提示段；真正写给模型的 injection payload 只单独组装 resident memory、events 和 daily summaries，并没有独立的 open-loop 数据块。

另一方面，daily summary 模板确实也有 `## Open Loops`，但它只是非结构化 Markdown 小节，目前没有 `id / status / next_action`，也没有独立的状态过滤和预算保护。最近几天这一节还是 `No durable updates captured.`。

所以准确结论是：**现在既缺结构化水源，也缺独立检索和注入管线；不能把 preview 标题当成接口已经接好。**

### 1. 写入侧：接受，补成“逐轮候选 + 夜间对账”

写入不应只押在每晚批处理，也不应把额外模型调用塞进用户回复前的同步链路。阶段 0 采用两段式：

1. 每次 `task_complete` 后，后台 extraction worker 读取当轮和最近少量纯文本对话，异步产出结构化候选；回复不等它。
2. 夜间维护负责补漏、合并重复项、推进 TTL，并重放白天失败的候选任务。

抽取模型不写死在 schema 里，由 `extractor.command / model / timeout` 配置决定，并使用独立后台会话，不能污染主聊天 thread。模型只负责给候选；本地 writer 负责 schema 校验、权限边界、幂等和真正落盘。抽取失败进入重试队列，不能静默丢失，也不能阻断当前回复。

幂等原则接受，但不建议把可变主题直接做成主键。更稳的是：

```json
{
  "id": "ol_01J...",
  "identity_key": "lshbosheth|product-check|gpt-live-availability",
  "aliases": ["GPT Live 失效检查", "看看 Live 还能不能用"]
}
```

`id` 是生成后不变的 opaque id；`identity_key` 用于匹配和 upsert。这样主题改名、目标细化或同一主题下出现两个不同任务时，不会被 topic id 强行撞成一条。

状态更新走“显式信号优先”：用户明确说“好了、确认了、不弄了”时可以直接更新；语义含糊时只产生候选，不得擅自把事项判成 `done`。

### 2. TTL：接受垃圾回收，保留“陈旧”和“失效”的区别

`7 / 30 / 14 天`可以作为首轮评测参数，但不应直接把所有长期未更新事项改成 `expired`。三十天没聊，不等于用户已经取消。

应拆成两层：

- 语义状态：`pending / in_progress / blocked / done / expired`；
- 召回资格：`active / stale / archived`，由 `last_confirmed_at / stale_after / expires_at` 计算。

默认可以先设：7 天后降为 `stale`，30 天后移出主动注入候选，但仍可在“以前那件事”这类明确历史查询中搜到。只有明确截止日期已过、用户取消，或新事项正式取代它时才标 `expired`。`done` 应立即退出当前待办候选，不必再等 30 天；历史查询仍可回查。

`blocked` 超时后也不能默认主动提醒用户，是否提醒要受提醒权限和场景控制，不能让记忆系统偷偷变成催办系统。

### 3. 指代消解：接受为 P0，而且当前有一个更具体的断点

`build-context.mjs` 已支持重复传入 `--recent`，但现役 App Server 的 `memoryContextCommand()` 只传了当前 `--message`，没有把最近对话交给 builder。因此“它修好了吗 / 继续吧”这类消息在模型 thread 内可能接得上，检索器本身却看不到指代对象；会话轮换后问题更明显。

阶段 0 先做两件事：

1. App Server 把最近 2～4 轮纯文本 handoff 传给 builder，不携带工具输出和推理正文；
2. 只对低信息、含指代或相对时间的 query 做改写，同时保留原 query。

检索输入应是 `raw_query + rewritten_query + resolved_entities + time_window + rewrite_confidence`，不能用改写文本覆盖原话。低置信度时扩大候选或回查来源，不允许把错误改写当事实。

### 4. 注入预算：接受“保护槽位”，不接受永远禁止借用

open loop 需要保底，但“某段空着也绝不借给别段”会白白浪费预算。更合适的是“保底下限 + 段内上限 + 二次借用”：

```text
先为相关 active open loop 保留至少 1 条
各段先在自己的 hard cap 内选取
完成保护后，空余预算可按优先级二次分配
总量仍受 max_injection_chars / tokens 硬限制
```

只有当前查询确实相关且存在 active loop 时才保底；不能为了凑栏位每轮都塞一个待办。

### 5. 评测集：完全接受，但应扩展现有资产

项目根目录已经有 `scripts/memory-context-builder/zvec-eval-questions.jsonl`，目前只有 `question + expected_terms`，没有期望 id、反例和自动指标。后续应迁入正式 `eval/` 结构并扩展，而不是另起一套互不相认的题库。

每条至少补：`recent_messages / expected_ids / forbidden_ids / expected_status / expected_time_window`。基线报告必须在调权重和接 embedding 之前生成并进 Git。这里同意提升到 P0。

### 6. 冲突消解：方向接受，但不能只靠“新覆盖旧”

`supersedes / superseded_by` 有用，应进入 schema；同时还需要 `scope` 和版本规则。一次性状态可以按同一 identity 的新版本覆盖，稳定偏好只有出现明确的“偏好变更”证据才允许改写，不能被一顿饭、一次通勤或一句临时状态覆盖。

这项依赖写入器先落地，开发顺序在 writer 之后，但 schema 要在阶段 0 一起定，避免后面迁移数据。

### 7. Recall trace：接受提前，但不是“成本几乎为零”

现有 preview 和运行日志已经能看到部分命中结果，却没有统一记录 query 改写、分项分数、裁剪原因和降级路径。阶段 0 应补结构化 trace。

不过 trace 会接触私人记忆，必须只记录必要元数据，默认记 `query_hash / candidate_id / scores / decision / latency / fallback`，正文脱敏并限制保留期；不能为了调参把完整聊天再复制一份到日志里。

### 8. 超时：接受向量分支软降级，不能把整个必需检索静默跳过

现役链路把 memory builder 设为 required，是为了防止检索失败后继续凭印象编个人事实。以后应把故障域拆开：

- 本地关键词 + 状态过滤是基础分支，保持必需；
- query embedding 是增强分支，超时后可降级；
- 整个 builder 真正失败时，仍按 required 策略暴露失败，不能伪装成“已经查过但没找到”。

`800ms` 可作为 shadow 初值，不先写死。应根据本机和实际 embedding 服务的 p95 延迟决定，例如先观察 `800～1200ms`，再定软超时。

### 9. 编码：已核实，不是待修代码缺口

`build-context.mjs` 中的中文规则本体是正常 UTF-8；之前的“乱码”来自旧 PowerShell 默认编码读取。当前用 PowerShell 7 并显式 `Get-Content -Encoding UTF8` 可以正常显示，Node 也按 UTF-8 读取。

因此这里保留为开发约束和回归检查即可，不应继续列成现存逻辑故障。

## 调整后的阶段 0

综合这次审查，向量 shadow 之前的阶段 0 改为：

1. 固定 memory unit / open loop schema，包括 identity、状态、时间、来源和冲突字段。
2. 落地异步逐轮候选、writer upsert、失败队列和夜间对账。
3. App Server 传最近纯文本，增加条件式 query rewrite 和时间解析。
4. 增加隐私受控的结构化 recall trace。
5. 把现有 zvec 问题集升级为可执行基线，覆盖正例、反例、状态和跨轮指代。
6. 增加 open-loop 检索与独立注入块，再做保护配额和生命周期清扫。

做完这些，embedding 才有一张可靠、可评测、会更新的表可搜。这里和审查结论是一致的：**向量检索仍是后续增强，不是阶段 0 的救命药。**

# 记忆检索演进方案：从规则召回到状态化混合记忆

这篇文档记录一个实际问题：为什么当前的 `build content` 已经会查记忆、拼上下文，回答却仍然可能接不上昨天的对话；以及后续怎样把它演进成“结构化记忆 + embedding + 向量检索 + 状态管理”的系统。

## 先说结论

最终方向确实应该包含 embedding 和向量索引，但“把所有原始会话清洗后塞进向量数据库，每轮只做向量搜索”还不是完整答案。

更可靠的目标是：

```text
原始会话
  -> 清洗、切片、去重
  -> 结构化记忆单元
     稳定偏好 / 事件 / 未完成事项 / 状态变化
  -> 文本索引 + 向量索引
  -> 当前消息的混合检索
     语义 + 关键词 + 时间 + 状态 + 重要性
  -> 重排、去重、裁剪
  -> 只注入真正相关的上下文
```

原始会话保留为证据，Markdown / JSONL 继续作为可读、可检查、可回滚的权威来源；向量数据库是可重建的检索层，不是唯一真相。

## 为什么要搞

### 当前系统已经解决了什么

现在的 `build-context.mjs` 大致会做这些事：

1. 从当前消息提取关键词和实体。
2. 根据固定的意图、别名和检索触发条件，判断要不要查历史。
3. 扫描 `events/events.jsonl` 和 `summaries/daily/*.md`。
4. 按关键词、主题、时间、重要性等信号打分。
5. 把稳定记忆、事件和摘要拼成一段上下文注入。

这套实现透明、容易调试，也比每次把完整原始会话塞进去省 token。问题在于，它仍然更像“带若干规则的文本搜索器”。

### GPT Live 案例暴露的缺口

昨晚我们说过要去看看 GPT Live 到底是不是彻底失效，第二天你说“我现在看看”。这件事明明在原始会话里，但如果当时没有被沉淀成事件或未完成事项，后续系统就只能碰运气：

- 当前消息里的词和旧消息不完全一致时，固定关键词规则可能不命中；
- 即使命中“GPT Live”，也可能捞出更早的使用记录，而不是“待继续检查”的那一件事；
- 系统知道“以前聊过 GPT Live”，却不知道这件事是 `pending`，也不知道下一步是继续检查。

这不是单纯的“少写了一条规则”，而是记忆单元缺少状态。

### 为什么不能不断加规则

如果每次漏召回一个主题就增加一条规则，系统会逐渐变成一张手工维护的关键词表：

- 同义说法、错别字和语音转写会不断制造新例外；
- 规则之间会互相覆盖，命中后还要继续维护优先级；
- 规则能回答“出现了哪些词”，却不一定能回答“这件事现在是否还有效”；
- 规则越来越多以后，和直接翻原始会话的区别只剩下人工提前写过索引。

规则应该保留在它擅长的地方：识别高风险边界、保护时间和状态约束、处理专有名词精确匹配，而不是承担全部记忆理解。

## “搜索得到”和“当前有效”不是一回事

向量搜索解决的是“哪些内容语义上相似”，记忆系统还要解决“哪些内容此刻可以影响回答”。

例如，下面三条都可能和“GPT Live”相似：

```text
2026-06-10：用户第一次尝试 GPT Live。
2026-07-20：讨论过 GPT Live 的功能和价格。
未完成事项：确认 GPT Live 当前是否仍可用，之后继续测试。
```

如果只按向量相似度排序，前两条完全可能排在第三条前面。真正需要的排序信号至少还包括：

- `status`：`pending` 和 `in_progress` 优先，`done` 默认降权；
- 时间：近期事项优先，长期偏好不能被一次临时状态覆盖；
- 重要性：关键决策和明确承诺高于普通闲聊；
- 类型：用户问“我之前还要做什么”时，优先找 open loop；
- 时间有效性：过期、撤销或已被新结论取代的内容不能继续注入。

所以，向量库应该是候选召回器，而不是最终裁判。

## 记忆应该存什么

### 稳定记忆

长期成立、跨场景可复用的信息，例如偏好、习惯、项目方向和已经确认的约束。它们不应该因为某一次聊天就被覆盖。

### 事件

带时间和来源的一次性事实，例如一次购买、一次故障、一次决定或一次提醒。事件可以有生命周期，也可以被后续事件修正。

### Open loop：临时未完成事项

`Open loop` 指“已经开始或明确约定，但还没有完成，之后需要继续”的事项。它不是泛泛的待办清单，而是从对话中提取出来、会影响后续上下文的短期状态。

例如：

```json
{
  "id": "open-loop:gpt-live-check",
  "type": "open_loop",
  "title": "确认 GPT Live 当前是否还能用",
  "status": "pending",
  "started_at": "2026-08-06T23:30:00+08:00",
  "updated_at": "2026-08-07T23:20:00+08:00",
  "next_action": "打开 GPT Live 并确认是否能正常进入或发起会话",
  "source": "conversation:2026-08-06",
  "expires_at": null,
  "importance": 3,
  "topics": ["GPT Live", "产品可用性"]
}
```

状态可以先收敛为五种：

| 状态 | 含义 |
| --- | --- |
| `pending` | 已记录，但还没有真正开始 |
| `in_progress` | 已经开始处理 |
| `blocked` | 想继续，但被外部条件卡住 |
| `done` | 已完成，默认不再主动提醒 |
| `expired` | 超过有效期或被新结论取代 |

“跨天”只是生命周期的一部分。跨天时不要复制一条新记忆，而是继续更新同一个 open loop：开始时间、最后进展、阻塞原因和下一步都保留下来。用户说“我现在看看”时，系统应优先召回这条待处理事项，并在完成后把它标成 `done`。

## 推荐的数据流

### 1. 原始会话层

保存完整对话、时间戳和会话标识。它的职责是可追溯和取证，不直接作为每轮注入内容。

### 2. 结构化记忆层

从原始会话中抽取少量可复用单元：

```json
{
  "id": "event:2026-08-07:gpt-live",
  "type": "event",
  "summary": "用户准备继续检查 GPT Live 是否失效",
  "status": "in_progress",
  "time": "2026-08-07T23:22:32+08:00",
  "entities": ["GPT Live"],
  "topics": ["产品可用性"],
  "importance": 3,
  "source_path": "lshbosheth-memory/events/events.jsonl"
}
```

结构化层负责状态、时间和类型；它不是把每句话都永久总结一遍。

### 3. 检索索引层

同一个记忆单元可以同时进入：

- 全文或 BM25 索引：擅长专有名词、编号、原词命中；
- 向量索引：擅长换一种说法表达同一件事；
- 元数据索引：过滤 `type`、`status`、时间范围和项目空间。

索引都是派生数据，损坏后可从结构化层重建。

### 4. 运行时混合检索

每轮收到新消息后，检索器根据消息意图选择信号，不是无条件全库乱搜：

```text
候选集 = 向量 top-k
       + 关键词/BM25 top-k
       + 当前状态过滤后的 open loop
       + 必要的近期事件
```

然后统一重排、去重和裁剪。一个可落地的初始评分形式是：

```text
final_score =
  vector_score   * 0.40
  + keyword_score * 0.25
  + state_score   * 0.15
  + time_score    * 0.10
  + importance    * 0.10
```

权重只是起点，必须用失败案例集校准，不能把它当成永远正确的常数。

### 5. 原始会话回查

当结构化记忆不足、多个事件冲突，或用户明确问“原话是什么”时，再根据 `source` 回查原始会话。这样既保留证据，又避免每轮都把长聊天记录拖进上下文。

## Embedding 该怎么接

不要为每条普通闲聊都实时生成向量。更稳的节奏是：

1. 结构化记忆单元写入或更新时生成 embedding。
2. 每日摘要整理完成后批量生成 embedding。
3. 当前用户消息在需要检索时生成一次 query embedding。
4. 更换 embedding 模型时从权威源重建新索引，不在旧向量上混用维度。

embedding 文本应是“可检索的短摘要 + 必要关键词”，而不是未经处理的整段聊天。

## 为什么不做纯向量系统

纯向量方案有三个明显问题：

1. 语义相似不代表状态有效。已完成事项仍可能被召回。
2. 专有名词、数字和日期需要精确匹配，关键词索引通常更可靠。
3. 向量结果不天然提供可解释的生命周期，无法替代 `pending / done / expired`。

因此最终态不是“规则系统”或“向量系统”二选一，而是：

```text
规则负责边界和安全
结构化状态负责当前有效性
关键词负责精确命中
向量负责语义扩展
原始会话负责证据回查
```

## 分阶段落地

### 阶段 0：先把状态写对

- 固定 `memory unit` 和 `open_loop` schema。
- 让事件抽取能记录 `status`、`next_action`、`source`。
- 先用 SQLite/JSONL 做可查询的结构化存储。
- 建立 GPT Live、被中断的学习任务、已完成事项三类验收案例。

这一阶段解决的是“记住什么”和“现在是否有效”，不急着引入向量数据库。

### 阶段 1：向量索引 shadow 模式

- 从结构化记忆单元切 chunk。
- 选择中文效果和成本合适的 embedding 模型。
- 写入 zvec 或其他本地向量索引。
- 与现有关键词召回并行运行，只记录结果，不改变主链路。

重点观察 `Recall@K`、误召回和 token 增量。

### 阶段 2：混合召回接入

- 合并向量、全文、时间和状态结果。
- 对重复记忆去重，对 `done/expired` 做降权或过滤。
- 保留旧规则作为 fallback 和边界保护。
- 限制最终注入条数与字符数。

### 阶段 3：重排、回查和维护

- 对 top-k 候选做更精细的重排。
- 冲突或低置信度时回查原始会话。
- 增加索引重建、版本切换、删除和回滚工具。
- 记录每次召回为何命中，方便定位问题。

## 怎么判断做成了

至少准备一组固定回归问题，而不是凭“这次感觉想起来了”验收：

| 场景 | 期望行为 |
| --- | --- |
| “我现在看看 GPT Live” | 找到跨天的 `pending/in_progress` 检查事项，而不是只找旧产品介绍 |
| “那个之前没做完的 React 任务” | 找到对应 open loop，并显示下一步或阻塞原因 |
| “GPT Live 已经确认能用了” | 更新原事项为 `done`，后续默认不再主动提醒 |
| “我以前用 GPT Live 做过什么” | 可以召回历史事件，但不把历史事件误当成当前待办 |
| 用户换同义说法或有转写错误 | 向量召回仍能找到候选，专有名词由全文检索兜底 |

建议记录这些指标：

- `Recall@K`：正确记忆是否出现在候选前 K 条；
- `Precision@K`：候选里有多少真的相关；
- open loop 状态更新是否正确；
- 每轮注入字符数和 token 消耗；
- 已完成、已过期内容的误召回率；
- 发生冲突时是否能回查来源。

## 边界、成本和隐私

- 云端 embedding 会发送记忆文本，敏感内容要过滤或改用本地模型。
- 记忆抽取错了，向量检索只会更快地找出错误；必须保留人工修正和来源。
- 用户删除记忆时，要同时删除结构化记录、索引记录和可回查的源片段。
- 向量索引应支持按版本重建和回滚，不能把不可逆的在线更新当成唯一存档。
- 暂时不做多用户权限、复杂 Agent 自主规划和全量聊天永久入库，先把单用户的状态化召回做稳。

## 最终形态

最终想要的不是一个“记得更多”的系统，而是一个能区分下面几件事的系统：

```text
我以前提过什么？       -> 历史事件 / 原始会话
我长期有什么偏好？     -> 稳定记忆
我还有什么没做完？     -> open loop + 状态
我这句话在说哪件事？   -> 混合检索 + 重排
你为什么这样判断？     -> 来源回查
```

所以 embedding 和向量数据库值得做，但它们应该接在结构化记忆和状态管理之后，成为更强的“找东西”能力。真正的最终态，是可追溯、可更新、能跨天延续，又不会把所有旧聊天一股脑塞回来的混合记忆系统。

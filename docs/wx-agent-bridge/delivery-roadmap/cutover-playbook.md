# 自研微信链路切换与回滚手册

> 本手册用于把当前 `微信 -> cc-connect -> Codex` 切换到自研 `wx-agent-bridge`。核心原则：同一微信账号任何时刻只能有一个会发送回复的消费者；不通过兼容门禁，不进行正式切换。

## 1. 切换角色

正式操作前明确以下角色；同一人可兼任，但职责不能缺失：

```text
切换负责人：决定开始、暂停、扩大和回滚
链路观察人：监控拉取、队列、Agent、附件和发送指标
验收人：用真实微信执行验收脚本
回滚执行人：维护旧链路可恢复状态并执行回滚
记录人：记录版本、配置、时间、证据和异常
```

## 2. 不可妥协的切换条件

切换前必须同时满足：

- Phase 1 退出证据完整，并通过[现有链路兼容基线](/wx-agent-bridge/cc-connect-compatibility-baseline)。
- 新旧版本、配置版本、数据 schema、启动命令和精确工作目录均已记录。
- 当前工作区的消息、会话、thread 映射、状态、配置和凭据引用已备份。
- 已在非生产副本完成一次恢复演练，确认回滚版本可读迁移后的数据。
- 新实例有单消费者保护，启动前能识别旧消费者是否仍持有账号。
- 回滚入口经过演练，旧链路二进制和配置没有在切换中被覆盖。
- 关键指标、脱敏日志和告警可用，能用 `traceId` 串起完整回复。
- 真实验收用例、停止条件、观察窗口和负责人已经确认。

任一条件缺失，结论为“暂不切换”，不能以人工盯守代替。

## 3. 阶段 A：历史事件回放

目标：验证新链路的解析、状态机和回复决策，不接触生产 iLink 消费权。

步骤：

1. 从脱敏样本集回放文本、纯附件、图片结果、文件结果、空结果、断连、卡死和重启事件。
2. 禁用真实微信发送和真实外部副作用；输出写入隔离结果集。
3. 对比新旧链路的终态、回复数量、附件、错误类别和用户可见语义。
4. 对不一致项分类：预期改进、可接受差异、兼容回退、阻断缺陷。
5. 阻断缺陷归零后，固化样本为自动回归。

退出条件：没有静默丢失、重复有效回复、附件后空响应、工具副作用重放和原始错误泄漏。

## 4. 阶段 B：影子处理

目标：用实时或准实时生产形态验证性能，但仍由旧链路负责唯一回复。

安全方式：

- 优先由旧链路将脱敏入站事件镜像到隔离队列，或读取持久化事件进行准实时回放。
- 新链路设置 `sendDisabled=true` 或等价硬门禁，发送接口在代码层拒绝生产目标。
- 不允许新旧两个长轮询消费者同时绑定同一微信账号来实现“影子”。
- 影子链路调用 Agent 时关闭有副作用工具，或使用专用只读环境。

观察：

```text
解析成功率和未知事件
去重与会话排序
队列等待、Agent 执行、gpt-image-2、上传模拟耗时
新旧终态和回复语义差异
thread 恢复与新 thread 降级
资源和状态目录是否只属于当前工作区
```

退出条件：覆盖完整业务时段，关键指标不劣于既定门槛，所有差异已经解释并留档。

## 5. 阶段 C：切换演练

目标：在隔离账号或等价非生产入口完成一次真实停旧、启新、验收和退回。

演练顺序：

1. 记录旧消费者 PID、端口、版本、游标和最后已处理 `messageId`。
2. 停止旧消费者并验证进程退出、端口释放、租约释放。
3. 启动新消费者，确认 PID、工作目录、版本、配置和账号归属正确。
4. 健康检查依次验证 iLink 拉取、入队、Agent、文本发送和附件发送。
5. 执行真实验收矩阵。
6. 停止新消费者并验证无在途发送。
7. 恢复旧消费者，确认从正确游标继续且不重放已完成消息。
8. 保存时间线、日志查询、截图或消息记录和所有偏差。

至少成功演练一次后，才能申请生产小流量。

## 6. 阶段 D：生产小流量切换

如果 iLink 账号不能按用户安全分流，生产“小流量”不能通过两个消费者实现，应选择以下之一：

- 使用独立微信测试账号验证后，执行单账号短观察窗全量切换。
- 让唯一入口消费消息，在入口内部按允许名单选择新旧处理器，但只由统一发送出口回复。

正式顺序：

1. 宣布切换窗口，暂停非必要部署和配置修改。
2. 等待旧链路在途 turn 到达可安全边界；记录仍运行任务及通知责任。
3. 记录最后游标和最后终态消息，停止旧消费者。
4. 验证旧 PID 已退出、端口和租约已释放；验证目标是当前工作区实例。
5. 启动新消费者并通过恢复屏障，未健康前不得发“已恢复”。
6. 发送一条受控探针，验证接收、Agent、文本或附件发送和审计全链路。
7. 开启生产处理，观察每条允许范围内消息的唯一终态。
8. 执行文本、连续对话、纯附件、生图、排队、失败、恢复等真实用例。
9. 持续观察停止条件；未触发才扩大范围或结束切换窗口。

## 7. 立即停止和回滚条件

出现以下任一情况立即停止新消息进入新处理器并启动回滚：

- 同一入站消息出现两条有效回复或两次外部副作用。
- 已接收消息无终态且无法从持久化记录安全恢复。
- 图片或文件送达后又发送空响应或错误兜底。
- 用户看见 app-server、管道、URL、状态码、调用栈或秘密。
- 已终止任务被告知仍在处理，或未恢复服务被告知已经恢复。
- 队列持续增长、单会话卡死扩散到其他会话。
- 新旧消费者同时有效，或当前账号消费者归属不明。
- 数据迁移导致旧版本不可读，且没有验证过的兼容读路径。
- 操作命中当前工作区之外的服务、进程或数据目录。

## 8. 回滚步骤

1. 关闭新入口或路由开关，阻止新任务进入，但保留日志和状态。
2. 查询新链路在途任务，逐项标记等待、安全取消、人工接管或继续观察；不要直接遗忘。
3. 等待发送出口清空或冻结，记录最后已发送回复和最后处理游标。
4. 停止新消费者，验证精确 PID 退出、端口和账号租约释放。
5. 如 schema 有变化，启用已演练的向后兼容读路径；不要现场执行破坏性降级。
6. 启动旧链路，确认版本、配置、工作目录、游标和账号归属。
7. 用受控探针验证接收、Codex、文本和附件发送。
8. 对受影响且需要通知的会话发送一次符合真实状态的恢复或失败消息。
9. 对比入站记录和回复记录，补齐没有终态的消息；有副作用的消息只人工判断，不自动重放。
10. 冻结新一轮切换，建立故障记录、根因、修复和新增回归用例。

## 9. 真实验收矩阵

| 场景 | 必须观察的结果 |
| --- | --- |
| 普通文本 | 一次接收、一次处理、一次自然回复 |
| 连续两条消息 | 同会话有序，第二条排队语义准确 |
| 不同会话并发 | 互不阻塞，回复不会串会话 |
| 纯图片 / 文件 | 无正文也进入 Agent，不报缺少 message |
| 生图 | 图片送达，附件即回复，无后续空消息 |
| 空结果 | 只在安全边界有限重试，无工具重放 |
| 队列已满 | 一次符合人设的明确反馈，不反复轰炸 |
| app-server 断连 | 不泄漏底层错误，状态判断真实 |
| 卡死 turn | 能发现、安全中断并继续后续会话 |
| 老 thread 失败 | 可切新 thread，说明准确且不阻塞 |
| 计划内重启 | 真正健康后主动通知一次 |
| 异常恢复 | 先恢复并探测成功，再主动通知一次 |
| 发送阶段断网 | 幂等重试，不产生双回复 |

## 11. 切换后观察

- 首个完整业务周期内持续关注双回复、无终态、队列、未知事件、附件终态、错误泄漏和恢复通知。
- 至少一周保留快速回滚能力，不立即删除旧链路配置和可恢复产物。
- 每天对比接收消息数、终态数、附件回复数、失败类别和人工反馈。
- 观察期结束后再决定归档旧链路；归档前保留必要的审计、迁移和故障样本。

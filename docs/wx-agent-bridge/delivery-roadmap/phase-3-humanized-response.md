# Phase 3：人话回复层

## 阶段结果

用户收到的是符合当前人设、承接上下文且不撒谎的回复，而不是工具日志或统一机械模板。正常、排队、慢任务、失败、取消和恢复的表达各不相同，但状态语义一致。

## 前置条件

- Phase 1 能提供可信结构化状态、错误类别和附件结果。
- Phase 2 能提供经过筛选的语气、长度等用户偏好。
- 底层原始错误不会直接进入最终回复通道。

## 回复流水线

```text
结构化结果 / 状态
  -> 安全裁剪和脱敏
  -> Persona + 用户表达偏好
  -> 人话生成
  -> 状态一致性校验
  -> 微信长度和附件适配
  -> 本地确定性兜底
```

## 工作包

### P3-01：场景和语义矩阵

至少区分：

```text
已接收
正在排队
队列已满
正在处理
处理较慢但仍运行
任务已失败
任务已取消
服务正在恢复
服务已经恢复
图片 / 文件已送达
需要用户补充信息
```

每个场景定义允许承诺、禁止表达、最大通知次数和本地兜底。任务已终止时不得写“稍后会自动回来”；尚未健康时不得写“已经恢复”。

### P3-02：Persona 配置

- 人设包含称呼、语气、节奏、常用表达和禁用表达，不绑定底层错误名。
- 同类提示提供多个自然变体，避免每次完全一样。
- 用户明确的长度和语气偏好可以覆盖默认值，但不能覆盖安全语义。
- 变体选择可测试、可去重，不能在重试时连续发送多条。

### P3-03：结果总结

- 外部 Agent 长结果先抽取结论、完成项、失败项和需要用户决定的事项。
- 图片或文件作为主结果时，文本只补必要说明，不把“没有文本”当失败。
- 技术细节按用户需要展开，默认不暴露进程、协议和调用栈。
- 不确定事实明确标为不确定，不把推断写成已完成动作。

### P3-04：错误回复 AI 与本地兜底

- 轻量 AI 只接收错误类别、真实运行状态、是否会自动恢复和允许披露的短摘要。
- 输出经过状态一致性、敏感词和长度校验。
- 模型超时、拒答、空输出或校验失败时使用场景化本地短文案。
- 同一入站消息最多发送一次兜底；后续只在真实状态发生变化时通知。

### P3-05：质量评估

- 建立正常、排队、失败、恢复、生图和需澄清的黄金样本。
- 自动检查空输出、泄漏词、错误状态承诺、过长和重复通知。
- 人工抽样评估自然度、准确性、上下文承接和人设一致性。

## 验收清单

- [ ] 同类错误连续发生时文案有自然变化，但用户理解到的状态一致。
- [ ] `file already closed`、app-server、URL、状态码和调用栈不会出现在微信。
- [ ] 已失败任务明确说明没有继续运行；仍运行任务不会被误报失败。
- [ ] 图片成功送达后不生成空回复，也不额外发送失败兜底。
- [ ] 轻量 AI 不可用时，各场景都有符合人设的本地回复。
- [ ] 队列提示、队满提示和恢复通知不会针对同一状态重复发送。
- [ ] 用户要求简短后，回复长度收敛，但关键失败事实不被省略。
- [ ] 黄金样本和真实会话抽样达到验收标准，并记录改进项。

## 不在本期做

- 用人设文案掩盖未知运行状态。
- 让错误回复 AI 自行读取原始日志或完整私人消息。
- 为“更像真人”制造虚假的处理进度、时间承诺或完成结果。

## 发布与回滚

先旁路生成并与现有回复对比，再按场景逐个启用；错误和恢复类最后启用。任一场景出现原始错误泄漏、错误状态承诺或重复轰炸时，立即关闭该场景 AI 改写并退回本地确定性文案。

# 现有微信链路兼容基线

> 记录日期：2026-08-13
>
> 适用范围：当前 `cc-connect-weixin-codex` 链路，以及计划在 10 月前切换的自研 `wx-agent-bridge`。
>
> 目的：自研、升级或替换实现时保留已经验证过的交互体验，不把旧故障重新带回来。

## 基线链路

```text
WeChat / iLink
  -> 消息接收与归一化
  -> 按 session 串行与排队
  -> Codex app-server
  -> Codex 推理 / 工具调用
  -> gpt-image-2（通过 image_gen 工具）或其他工具
  -> 文本 / 图片 / 文件回传
  -> WeChat / iLink 发送
```

工具入口名称和底层模型名称必须分开记录。例如 `image_gen__imagegen` 是工具入口，Codex 内置生图底层是 `gpt-image-2`，排障时不能混为一谈。

## 必须保留的行为

### 1. 纯附件消息

- 微信只发图片或文件、没有文字时，仍然是有效消息。
- 上下文构建器不得因空 `--message` 退出。
- 内部可以使用“仅附件消息，无文字”一类占位语义，但不得把占位文本冒充用户原话写回微信。
- 验收：只发一张图片，Agent 能看到附件并产生有效回复。

### 2. 空响应处理

- Agent 正常结束却没有文本、图片或文件时，不得给用户空白消息。
- 无工具副作用的纯推理轮次可以在同一 thread 内有限重试一次。
- 已经调用工具的轮次不得自动重放，避免重复改文件、重复发图或重复执行外部操作。
- 重试后仍为空时，使用本地、符合人设的短回复，并提示用户重发。
- 同一条入站消息最多发送一次兜底回复。

### 3. 图片和文件就是回复

- 图片或文件经侧通道成功发送后，本轮已经有回复。
- 随后的空 `EventResult` 必须静默结束，不能再补一个空响应、兜底文案或 `NO_REPLY` 文本。
- 只有附件实际发送成功后才设置“本轮已有附件回复”；发送失败不能误判为成功。
- 文本加附件时要去重，不能把同一段说明同时从侧通道和终态发送两次。

### 4. 忙会话与消息队列

- 同一个微信 session 内只允许一个前台 turn 执行，后续消息按 FIFO 排队。
- 接受排队时立即发送符合当前人设的短提示，不能使用生硬系统文案。
- 队列达到上限时明确提示暂时未收下，并带当前待处理数量。
- 不允许静默丢弃队列消息。
- 当前 Agent 已死亡时，排队消息收到的是脱敏后的人设错误，不得看到原始进程错误。
- 撤回、取消和过期消息必须从队列中正确移除，不能在之后“复活”。

### 5. 错误分类与人设回复

对用户可见的基础设施错误至少分类为：

```text
app-server / 管道连接关闭
Agent 进程意外退出
请求超时或 turn 卡死
上游网络断流
模型或服务繁忙（502 / 503 / capacity）
请求过频（429）
使用额度耗尽
服务余额不足
接口或工具参数不兼容
会话失效或旧 thread 无法恢复
```

要求：

- 每一类使用不同的、符合人设且语义准确的短回复。
- 用户回复中不得直接出现 `read |0: file already closed`、`app-server`、管道名、堆栈、请求 URL、request id、密钥或大段 stderr。
- 原始错误仍完整写入本地结构化日志，用户文案和诊断日志分离。
- 代码、命令或配置本身需要用户修复的错误，可以保留经过脱敏的必要细节。
- 错误转译必须覆盖当前消息、后台 unsolicited event、队列清理、压缩会话等所有发送分支，不能只修主路径。

### 6. 正确表达“仍在处理”与“已经失败”

- 只有 turn 仍活跃且有进展证据时，才能说“还在生成/还在处理”。
- app-server 存活不等于 turn 正在工作；需要结合事件时间、CPU/子进程、工具状态和终态判断。
- 连接已断或进程已退出时必须明确本轮中断，不能让用户误以为稍后会自动收到结果。
- 对长任务保留 `received_at`、`first_event_at`、`last_progress_at`、`tool_started_at` 和终态。

### 7. 异常恢复与重启通知

区分两层生命周期：

```text
cc-connect / Bridge 主服务
Codex app-server Agent 子进程
```

- 计划内主服务重启：重启前持久化通知目标；微信平台 ready 后主动发送重启成功消息。
- Agent 子进程异常退出：标记对应 session 为待恢复；只有替代 app-server/session 真正创建成功后才主动发送恢复消息。
- 不得在进程尚未恢复时提前报成功。
- 同一次故障只通知一次，恢复通知不能替代用户新消息的正常回答。
- 手工部署默认是否通知必须成为显式策略，不能依赖操作者记忆；正式自研链路建议默认记录并在恢复后通知。

### 8. 卡死 turn、超时和安全中断

- 长时间没有事件或进展时进入疑似卡死状态，而不是无限占用 session。
- 生图等本来较慢的工具需要独立超时，不能与普通文本 turn 使用同一个阈值。
- 超时前可发送一次状态提示；确认终止后发送失败语义的人设回复。
- 优先中断当前 turn；若协议不支持，再只重启对应 Agent 子进程。
- 不应为了一个 Agent turn 重启整个 Bridge 主服务。
- 部署前必须检查活跃 turn；除非用户明确要求强切，不得中断正在生图或执行工具的任务。

### 9. thread 恢复和上下文膨胀

- 旧 thread 恢复出现超大帧、解析失败或 `token too long` 时，自动回退到新 thread。
- 回退不能导致微信 session 永久卡住。
- 记录旧、新 thread id 和回退原因，但不得暴露给普通用户。
- 设置 thread 轮换或压缩门槛，避免会话文件无限膨胀。
- 新 thread 建立后要继续保留必要的会话摘要、用户偏好和项目上下文。

### 10. 生图链路和耗时可观测性

每次生图至少记录以下阶段耗时：

```text
微信接收 -> Codex 首事件
首事件 -> image_gen 工具调用
gpt-image-2 生成耗时
生成结果回传耗时
本地落盘 / 读取耗时
微信媒体上传与发送耗时
终态收尾耗时
总耗时
```

- 图片成功发出后立即视为用户已收到结果，不必等待额外文本终态才计算“首个有效回复”。
- 生图工具超时后必须释放 session 队列。
- 指标应能区分模型慢、工具慢、网络慢和微信上传慢。

### 11. 安全与实例隔离

- 日志和诊断输出不得打印 token、API key、完整私人消息或未脱敏配置。
- 多套工作区或多套机器人并存时，部署、停止、重启和日志查询必须按绝对路径、配置路径和 PID 精确定位。
- 当前工作区的升级不得修改其他工作区的源码、二进制、配置或进程。
- Windows 替换可执行文件时，先停止目标进程，确认文件锁释放，再替换并校验 SHA-256，最后由守护进程拉起。

## 迁移验收矩阵

| 场景 | 必须看到的结果 | 禁止出现 |
|---|---|---|
| 只发图片 | Agent 正常理解并回复 | `Missing --message` |
| 无工具空结果 | 最多重试一次，仍空则人设兜底 | 空白回复、无限重试 |
| 工具轮次空结果 | 不重放工具 | 重复发图、重复执行 |
| 图片成功发送 | 图片就是本轮回复 | 随后再发空消息 |
| 会话忙 | 人设排队提示，稍后 FIFO 处理 | 生硬系统提示、静默丢弃 |
| 队列已满 | 明确未收下并显示数量 | 假装已排队 |
| app-server 断开 | 当前消息收到脱敏失败提示 | 原始管道错误和 URL |
| 断开时有排队消息 | 每条仅收到一次脱敏提示 | 队列路径泄漏原始错误 |
| 新 app-server 建立 | 主动发送一次恢复成功通知 | 尚未恢复就报成功 |
| 主服务计划重启 | 微信 ready 后主动通知 | 永久无反馈 |
| 生图超过阈值 | 状态可查、可安全中断、释放队列 | 无限卡死 session |
| 旧 thread 过大 | 切新 thread 后继续处理 | 微信链路永久占用 |
| 多工作区并存 | 只影响目标绝对路径实例 | 误停或覆盖其他实例 |

## 发布门禁

自研桥正式替换当前链路前，必须满足：

1. 上述矩阵全部有自动化回归测试；异常恢复和微信媒体发送至少再做一次真实环境 smoke test。
2. 新实现连续运行一周，无空响应、重复附件、原始基础设施错误泄漏和无法释放的忙 session。
3. 能按 `message_id`、`session_key`、`turn_id` 串起完整链路，但日志仍保持脱敏。
4. 切换方案有可在分钟级执行的回滚路径，并保留当前稳定二进制、配置和数据备份。
5. 每次升级第三方 SDK、Codex app-server 或 Bridge 协议时，都重新执行本基线。

## 后续维护

- 任何线上出现过的新故障都要追加到错误分类和验收矩阵。
- 修复必须同时增加回归测试，不能只改文案。
- 路线图、实现和测试三者冲突时，以用户实际可观察行为和本兼容基线为迁移门槛。

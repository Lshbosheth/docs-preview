# 状态机：Agent 怎么知道下一步该做什么？

## 今天先记住

Agent 的“下一步”不该只存在模型的自然语言推理里。状态机（State Machine）把一次任务允许经历的状态、可触发的动作和退出条件写清楚：什么能继续，什么必须等待，什么已经终止。

## 它在大地图里的位置

::: tip 今日坐标
**▶ 规划 / 决策 → 状态机**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> ▶ 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

昨天的断点续跑解决“停在哪”；状态机进一步规定“从这里允许往哪走”。它把模型的建议放进程序可检查的轨道里，连接规划、工具执行和人工审批。

## 它到底是什么

状态机由三件事组成：

```txt
状态：draft / awaiting_approval / publishing / succeeded / failed
事件：approve / reject / tool_success / tool_error
迁移：awaiting_approval + approve -> publishing
```

关键不是状态名好不好听，而是迁移有没有边界。例如 `succeeded` 不应再接受 `publish`；`awaiting_approval` 收到模型“继续发布”的文本也不能自行跳到 `publishing`，必须等到带身份和时间的确认事件。

模型可以负责在 `draft` 状态提出“建议发布”；程序负责判断这个建议是否能成为真实事件。这就是“会推理”和“能执行”的责任分界。

## 为什么 Agent 里会用到它

多步任务同时面对模型输出不稳定和外部系统有副作用两件事。若只把历史消息重新塞回模型，模型可能忘记审批、重复调用工具，或把失败当成成功继续往下编。

状态机提供的是确定性骨架：每次工具返回后，运行器按结果迁移状态；不允许的迁移直接拒绝并写日志。这样 Agent 仍能在节点内灵活规划，但不能越过发布、删除、付款这类边界。

## 怎么判断它有没有用

- 如果任务有审批、等待、重试、取消或恢复，应该显式建状态机。
- 如果某个动作会写数据库、发消息、提交代码或扣费，迁移前应同时检查当前状态和幂等键。
- 如果流程永远是固定三步且没有分支，普通函数或工作流已经够用，不必为它造复杂运行时。
- 看真实系统时，问：收到工具超时、重复 webhook、用户撤销后，状态分别会变成什么？答不出来的流程，多半仍靠 Prompt 硬撑。

## 一个小例子

```txt
Input:
用户说：“发布今天的 AI Agent Daily。”

Process:
draft
  -> content_checked（敏感扫描通过）
  -> committing（git commit 已创建）
  -> pushing（开始 git push）
  -> succeeded（远端确认）

若 git push 超时：
pushing -> push_unknown
运行器先用 commit id 查询远端；确认已存在才转 succeeded，
否则转 retryable_failed，而不是重新生成文章、重新 commit。

Output:
页面发布成功，或留下带 commit id 的可恢复失败状态。
```

这也给了你一个解释口径：Checkpoint 是任务的存档；状态机是存档可被怎样继续读取和推进的规则。

## 常见误区

1. 把状态机误解成“每一步都不能用模型”。模型可以做分类、规划和生成，限制的是高风险状态迁移。
2. 只有 `success / failed` 两个状态。真实流程通常还需要 `waiting_for_approval`、`retryable_failed`、`cancelled`、`unknown`。
3. 工具成功就立刻结束。工具返回成功只说明调用成功，不一定说明业务目标已完成，例如远端部署仍可能异步失败。
4. 用一长串布尔值代替状态。`isCommitted`、`isPushed`、`isApproved` 很容易组合出互相矛盾的现场。

# 工具权限与护栏：先让系统知道哪些不能做

## 今天先记住

Agent 真正危险的，不是“会不会回答”，而是“把回答直接变成动作”。权限决定它能碰什么，护栏决定它在碰之前、碰之后要过什么检查。

## 它在大地图里的位置

::: tip 今日坐标
**横跨整条链路 → 工具权限与护栏**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> ▶ 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
```

这不是单独挂在 prompt 里的小规则，而是把整条链路包起来的约束层。它卡住的是“谁能调用什么工具、带什么参数、执行到哪一步必须停”。

## 它到底是什么

工具权限（permission）是白名单和范围控制。
比如这个 Agent 能读文档、不能删库；能生成草稿、不能直接发布；能查订单、不能改金额。

护栏（guardrail）是围在权限外面的检查。
常见有三种：输入过滤，防提示注入和敏感指令；动作确认，防高风险副作用；输出校验，防模型把不该发的话当成正式结果。

所以它们不是同一件事。
权限回答“能不能做”，护栏回答“做之前和做完后怎么拦一下”。

## 为什么 Agent 里会用到它

Agent 会把“理解意图”直接接到“调用工具”。链路一长，最怕的不是能力不够，而是越权太顺手。

如果没有权限层，模型一句“我来帮你发出去”，就可能把草稿发成正式消息。
如果没有护栏，检索文档里混进“忽略上面规则”这种注入文本，模型可能真的跟着跑。

工程上要把高风险动作变成显式状态，而不是只靠语气词提醒模型小心点。

## 怎么判断它有没有用

- 如果动作会写入、删除、支付、发布、发消息，默认就要权限分级，不该全开放。
- 如果用户看不见影响范围，就不要让 Agent 直接执行。
- 如果输入里可能混有外部文档、网页、邮件内容，就要默认把它当不可信数据。
- 如果输出一旦发错就难撤回，那就必须加人工确认或至少二次校验。

判断一个真实系统时，最实用的问法是：模型说“可以做”的时候，程序有没有办法说“不行，先停”。

## 最近冒出来的词

`ant apply`。这是个真实的 CLI 变化，不是噱头。

Anthropic 的 release notes 在 2026-09-03 提到，它可以把 agents、environments、skills、memory stores、deployments 放进仓库文件里描述，然后运行后先出计划、再批准、最后应用，并写出 `claude-lock.json` 锁定一致性。

它和今天这篇的关系很直接：权限和资源最好也能像代码一样声明、审查、落锁，而不是散在几段 prompt 里。

来源提示：Anthropic Claude Platform release notes，2026-09-03。

## 一个小例子

```txt
Input:
用户说：“把今天的 AI Agent Daily 写完并发布。”

Process:
1. 系统允许本地写 Markdown
2. 检查是否包含 API key、私密日志、地址、电话等敏感内容
3. 如果内容安全，才允许 commit 和 push
4. 如果内容可疑，停在本地草稿，不进入发布态

Output:
安全内容：`draft_checked -> committed -> pushed`
敏感内容：`draft_saved -> blocked_publish`
```

这里能看出护栏的价值：不是让 Agent 少干活，而是把“写草稿”和“把草稿推到外部世界”拆成两档。

## 常见误区

1. 把“模型觉得可以”当成“系统就该执行”。
2. 只管工具权限，不管输入是否被污染。
3. 只做确认弹窗，不展示具体影响范围。
4. 出错后没有审计，最后只剩一句“它刚才为什么这么做”。

## 今天自测

1. 你这个 Agent 里，哪三个动作必须默认走确认？
2. 哪些输入应该默认当成不可信数据？
3. 如果执行错了，系统能不能说清楚是谁授权、改了什么、卡在哪一步？

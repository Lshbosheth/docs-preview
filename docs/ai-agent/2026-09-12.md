# Agent 的成本与延迟：先算一轮运行要付出什么

## 今天先记住

Agent 的成本和延迟不是最后再优化的数字，而是每次模型调用、工具等待、上下文大小和重试共同产生的运行约束。先把一轮运行拆开，才能决定该缩短上下文、并行工具，还是直接限制 Agent 的步数。

## 它在大地图里的位置

::: tip 今日坐标
**评估、可观测性与可靠性 → ▶ 成本与延迟**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

成本与延迟横跨这条闭环：上下文越长，模型调用可能越贵；工具越多，等待越久；评估发现失败后再重试，又会把前面的开销叠加。它不是一个独立零件，而是判断整条 Agent 链路能不能上线的尺子。

## 它到底是什么

可以把一次运行的总开销粗略拆成：

```txt
总延迟 = 模型排队与生成时间 + 工具耗时 + 串行等待 + 重试耗时
总成本 = 输入 Token 成本 + 输出 Token 成本 + 工具 / 存储 / 网络成本
```

真正有用的不是只记一个总数，而是给每个 `run_id` 记录：模型名、输入输出 Token、每一步开始和结束时间、工具名、重试次数、最终状态。这样才知道慢在模型，还是慢在某个外部 API。

## 为什么 Agent 里会用到它

普通问答通常只有一次模型请求；Agent 可能先规划，再调用三个工具，再根据结果补一次请求。假设一次模型请求 1 秒、一个工具 2 秒：四步串行就是约 7 秒，两个互不依赖的工具并行后可能降到约 5 秒；但若失败重试一次，延迟和 Token 又会继续增加。

所以成本与延迟会反过来影响决策：低风险、实时任务适合限制步数和上下文；复杂但不着急的任务可以接受更多工具调用；有依赖关系的工具不能为了“并行”硬拆，否则会拿旧输入执行错误动作。

## 怎么判断它有没有用

- 用户在等待，或任务有明确 SLA（服务级目标）时，必须按步骤记录 p50 / p95 延迟，而不是只看平均值。
- 每次运行都可能多轮调用模型时，给 `max_steps`、Token 预算和总耗时预算；任何一个超限都要进入可解释的失败状态。
- 两个工具互不依赖且都是只读时，可以并行；一个工具输出是另一个输入时，保持串行。
- 若成本上升却说不清是上下文变长、重试变多还是模型变贵，说明观测字段还不够支撑优化。

## 一个小例子

```txt
Input:
用户说：“检查文档是否合规，合规就提交并推送。”

Process:
1. 模型读取任务与规则：0.8 秒，输入 3k Token
2. 文件检查与敏感信息扫描互不依赖，并行执行：各 1.2 秒
3. 检查通过后才调用 git commit / push：2 秒
4. 系统设置 max_steps=6、总耗时预算=10 秒，并记录每一步 trace

Output:
扫描发现敏感信息 -> blocked，不调用提交工具，节省后续副作用与成本
扫描通过但 push 超时 -> publish_pending，保留提交状态，等待可恢复重试
```

这里的优化不是笼统地“让系统更快”，而是用状态和依赖关系做决定：只读检查可以并行，高风险发布必须等硬断言通过后再执行。

## 常见误区

1. 只看平均延迟，掩盖少数请求卡在超时或重试。
2. 为省 Token 盲目截断上下文，导致模型丢掉权限、日期或任务状态。
3. 把所有工具都并行调用，忽略前后依赖和可能产生的副作用。
4. 只统计模型费用，不统计失败重试、外部 API、队列和存储成本。

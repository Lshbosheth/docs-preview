# 轨迹评估：Agent 好不好，为什么不能只看最终答案？

## 今天先记住

评估 Agent 时，最终答案只是最后一层证据。真正要看的，是它有没有把目标理解对、工具选对、状态改对、错误处理对。否则一次“答对”可能只是碰巧，下一次换个输入就会把系统带偏。

## 它在大地图里的位置

::: tip 今日坐标
**评估 / 修正 → 轨迹评估**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

前两篇讲可观测性和失败恢复：先把运行过程看清，再让系统能从断点继续。今天往后走一步：有了 trace 之后，怎么判断这条运行轨迹本身是不是合格。

## 它到底是什么

轨迹评估（trajectory evaluation）就是评估一次 Agent run 的中间过程，而不是只给最终输出打分。

普通问答可以问“答案对不对”。Agent 任务还要问：它有没有读到正确上下文？有没有调用必要工具？工具参数有没有传错？工具失败后有没有停住或重试？最终结论有没有引用实际观察结果？

所以一条评估样本最好不只包含 `input` 和 `expected_output`，还要包含关键过程约束，比如“必须先读取上一课”“不得修改无关文件”“push 失败时不能重新生成全文”。

## 为什么 Agent 里会用到它

Agent 的风险常常藏在中间步骤。比如最终回复写着“已发布”，但实际 trace 显示 `git push` 超时；或者它答对了概念，却用错了工具、重复写了文件、泄露了不该进日志的正文。

这类问题靠人工读最后一句话很难发现。轨迹评估把“结果好看”拆成可检查的状态转移：输入是什么、走了哪些节点、每一步证据是什么、最后输出是否被这些证据支撑。

## 怎么判断它有没有用

- 如果任务会调用工具、写文件、发请求或改变外部状态，就不要只评估最终文本。
- 如果你关心“有没有按流程做”，样本里就要写过程约束，而不是只写理想答案。
- 如果一次失败无法判断是计划错、工具错、权限错还是恢复错，说明评估粒度太粗。
- 如果轨迹评估只能靠人肉看日志，至少先把关键状态、工具名、参数摘要和错误类型结构化。

判断真实系统时，可以拿一条成功 run 反问：如果把工具结果换成错误码，它会继续硬答吗？如果跳过某个必要步骤，评估能抓出来吗？如果最终文本正确但中间重复执行副作用，系统会判失败吗？

## 一个小例子

```txt
Input:
用户说：“生成并发布 2026-08-21 的 AI Agent Daily。”

Process:
评估规则：
1. 必须读取框架和上一课。
2. 文件只能写入 docs/ai-agent/2026-08-21.md。
3. 不能运行 docs:build。
4. commit message 必须包含 2026-08-21。
5. push 失败时状态应变为 publish_pending，而不是重新写正文。

Output:
如果 trace 显示：
read_framework -> read_previous -> write_markdown -> git_commit -> git_push
且文件路径、日期、提交信息都匹配，评估通过。
如果最终回复说 DONE，但 trace 没有 git_push，评估失败。
```

这个例子里，评估目标不是“文章看起来像文章”，而是“整条发布链路有没有按约束完成”。

## 常见误区

1. 只用人工看最终答案。它能抓文风问题，抓不到重复副作用和错误断点。
2. 把评估写成宽泛口号，比如“内容质量高”。更有用的是“是否读取指定文件、是否只提交目标文件、是否在失败时保留断点”。
3. 用单个黄金答案评估 Agent。Agent 的正确性常常是状态机正确，不是句子一字不差。
4. 忽略失败样本。没有超时、拒权、工具空返回这类样本，恢复逻辑基本没被测过。

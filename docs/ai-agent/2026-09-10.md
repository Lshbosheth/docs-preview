# 离线评测集：Agent 怎么把偶然成功变成可比较的证据

## 今天先记住

离线评测集不是“准备几道题让模型考试”，而是把真实任务、完成条件和失败边界固定下来，让 Agent 每次改动后都能回答：到底变好了，还是只是刚好答对了一次？

## 它在大地图里的位置

::: tip 今日坐标
**评估、可观测性与可靠性 → ▶ 离线评测集**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

它位于运行闭环之外的“反复回放”位置：线上 trace 告诉你刚才发生了什么，离线评测集则让你在改提示词、换模型或改工具后，重新跑同一批任务，比较系统是否真的变了。

## 它到底是什么

一条合格的评测样本至少包含四件事：输入任务、允许使用的环境、成功断言、可接受的失败边界。不要只保存“标准答案”，因为 Agent 可能通过不同工具路径完成同一目标。

例如，“发布一篇指定日期的文档”可以拆成：

- 输入：主题要求和日期。
- 环境：只能写入目标目录，可调用文件检查和 Git。
- 成功断言：文件路径、frontmatter 日期、H1 标题、提交文件集合都正确。
- 失败边界：检测到敏感信息时必须阻止发布，而不是继续 push。

这样评估的对象就从“这句话像不像好答案”，变成“目标状态是否达到，过程有没有越权，成本是否超预算”。

## 为什么 Agent 里会用到它

Agent 有随机性，工具还有外部状态；一次成功不能证明下一次也会成功。评测集把变化隔离出来：如果只换模型，任务和工具不变；如果只改工具 schema，其他条件不变。

实践中可以分三层：

1. **结果层**：文件、数据库或消息是否到达目标状态。
2. **轨迹层**：是否选对工具、参数是否合规、有没有重复动作或无效循环。
3. **约束层**：步数、延迟、Token、权限和人工审批是否在边界内。

结果层适合程序断言；轨迹层适合规则检查和人工抽样；开放式表达才考虑 LLM-as-a-Judge。别让一个“总体 8.5 分”掩盖了“重复发了两次消息”这种硬失败。

## 怎么判断它有没有用

- 任务能写出明确完成条件时，优先做离线样本；不能定义完成条件的开放式任务，只能把它当辅助证据。
- 每次改动都会影响工具选择、状态转移或权限时，必须回放旧样本，防止修一个问题又退回另一个问题。
- 样本应来自真实失败、边界输入和高频任务，而不是只挑最容易成功的演示题。
- 评测结果要能定位到断言或步骤；如果只能说“这版平均更好”，还不够支持工程决策。

## 最近冒出来的词

**Trajectory evaluation（轨迹评估）**最近在 Agent 平台文档里被单独拿出来讲：它评估的是一串工具调用和状态变化，而不只是最终回复。它不是新的 Agent 类型，而是把“怎么做到的”纳入验收。对今天的离线评测集来说，最实用的启发是：样本里要保存可比较的 trace。来源提示：Google Cloud Gemini Enterprise Agent Platform 文档，页面检索于 2026-09-10。

## 一个小例子

```txt
Input:
“生成今天的 AI Agent 课程并发布。”

Process:
1. Agent 生成 Markdown
2. 检查日期、标题、章节和敏感信息
3. 只暂存目标文件并提交
4. 回放评测集中的日期错误、重复文件、敏感内容样本

Output:
断言全通过 -> 允许 push
任一硬断言失败 -> publish_blocked，并指出失败步骤
```

同一批样本在改动前后各跑一次，比较的不只是通过率，还要看失败从哪一步开始、是否增加了工具调用和延迟。

## 常见误区

1. 只收集成功案例，导致评测集无法暴露边界。
2. 把最终文本当唯一答案，忽略工具副作用。
3. 样本、模型、工具版本一起变化，最后无法解释分数变化。
4. 用 LLM 评分替代文件、数据库和 API 的直接断言。

## 今天自测

1. 你的一个 Agent 任务，最少能写出哪三个成功断言？
2. 哪类失败必须检查轨迹，而不是只看最终回答？
3. 如果通过率没变，但重复动作减少了，这算不算改进？你会怎么记录？

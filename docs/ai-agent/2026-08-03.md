# 停止条件与预算：Agent 怎么知道该收手？

## 今天先记住

Agent 不是一直跑到“看起来像完成了”才停。一个能上线的 Agent，必须提前定义停止条件和预算：做到什么状态算完成，遇到什么风险必须停，最多能花多少轮、多少时间、多少工具调用。

## 它在大地图里的位置

::: tip 今日坐标
**评估 / 修正 → 停止条件与预算**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

前面讲产品边界，是从“系统能不能做”划责任线。今天往运行时再缩一圈：当 Agent 已经开始执行，它怎么判断继续、重试、改计划，还是收手。

停止条件放在评估 / 修正这一层，但会影响整条链路。目标不清会让它停不下来；工具结果不稳定会让它反复重试；没有预算会让一次小任务变成无限循环。

## 它到底是什么

停止条件是一组可检查的结束规则。它不等于一句“完成后停止”，而是要能被程序判断。

常见规则有三类：成功停止、失败停止、预算停止。成功停止是输出已经满足验收标准；失败停止是继续做也不会变好，或碰到敏感、越权、缺少确认等状态；预算停止是轮数、时间、Token、费用、工具调用次数到达上限。

预算不是只为了省钱。它更像运行时护栏：防止 Agent 在同一个错误观察上来回解释、反复搜索、重复提交，或者为了修一个小问题改动越来越大。

## 为什么 Agent 里会用到它

普通 Chatbot 通常一问一答，结束点天然明显。Agent 会行动，会观察结果，还会根据观察继续决策，所以它需要显式的“刹车”。

比如文档发布 Agent 写完 Markdown 后发现构建失败。它可以修一次 frontmatter，修两次链接；但如果第三次仍然失败，就应该停止并报告失败原因，而不是继续猜。这里的关键状态不是“更可靠”，而是从 `retrying_build_fix` 变成 `stopped_budget_exceeded`，后续不再执行 push。

## 怎么判断它有没有用

- 如果任务存在循环空间，比如搜索、修错、部署、测试、重新生成，就必须有停止条件。
- 如果一次失败后继续执行可能扩大影响，比如反复发消息、重复下单、重复提交，预算必须比模型自由发挥优先级更高。
- 如果结果可以被验收，就把验收写成可检查项：文件存在、日期一致、测试通过、没有敏感词、状态为 `reviewed`。
- 如果只能靠“模型觉得差不多”，这个停止条件还不够工程化，至少要补一条人工确认或最大步数。

## 最近冒出来的词

`MCP Tasks extension` 可以顺手记一下。MCP 2026-07-28 规范把长时间运行的任务移出核心协议，放进官方 Tasks 扩展，用任务句柄和轮询来表达“还没结束”的工作。

它不是新的 Agent 思想，更像协议层给停止、继续、补输入和查询状态留出的接口。和今天的主题对应：长任务不能只靠连接还开着来表示“正在做”，而应该有明确的任务状态、句柄和结束条件。

## 一个小例子

```txt
Input:
用户说：“生成 2026-08-03 的 AI Agent Daily 并发布。”

Process:
1. 生成 Markdown，检查 title、date、H1、文件名和 URL slug。
2. 扫描是否包含敏感信息。
3. 如果检查失败，最多修正 2 次。
4. 如果仍失败，停止发布；如果通过，commit 并 push。

Output:
成功：draft -> validated -> published。
失败：draft -> validation_failed -> stopped_after_2_fixes。
```

这个例子能拿来判断真实系统：停止条件不是“Agent 不要乱来”的愿望，而是运行状态的一部分。你看日志时应该能回答：它为什么继续、为什么停、停在第几步、有没有执行后续高风险动作。

## 常见误区

1. 只设置最大轮数，不设置成功标准。这样 Agent 会停，但不一定是完成。
2. 把重试当成万能修复。相同输入、相同工具、相同错误，重复三次通常只是在烧预算。
3. 预算只看 Token，不看外部副作用。一次工具调用可能比一万 Token 更危险。
4. 停止后不保存状态。没有 `stopped_reason`，后续人工接手只能重新猜发生了什么。

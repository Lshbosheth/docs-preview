# 评估、可观测性与可靠性：Agent 出错后怎么把现场抓住？

## 今天先记住

Agent 真正难的不是“会不会答”，而是每次跑完以后，你能不能说清楚它做了什么、为什么这么做、哪一步开始偏了。

## 它在大地图里的位置

::: tip 今日坐标
**横跨整条链路 → 评估、可观测性与可靠性**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

前几天讲的恢复、幂等、权限，都是“别把系统做坏”。今天讲的是另一半：如果它还是出错了，怎么把错误变成能复盘的证据，而不是一段含糊的“失败了我再试试”。

这层横跨整条链路，因为它不只看最后答案，还看输入、模型选择、工具参数、返回结果、重试次数、耗时和副作用。

## 它到底是什么

可观测性（observability）不是加日志这么简单，而是让一次 Agent 运行能被还原。

至少要留下三类东西：输入是什么，系统中间做了什么，外部世界最后变成什么状态。

评估（evaluation）是在这堆记录上问一句：这次做得对不对，和上次比是变好了还是变差了。

可靠性（reliability）则是把这些观察结果反过来变成约束，比如超时后怎么退、重复消息怎么去重、坏输出怎么拦住。

## 为什么 Agent 里会用到它

Agent 不像普通接口调用，失败不只是一条报错。

它可能先选错工具，再拿错参数，最后还把一半成功的结果当成完整成功。

如果没有 trace，你只能看到“最后没对”；
如果没有指标，你不知道是模型变差了、工具变慢了，还是某个分支最近总误路由；
如果没有评估集，你就只能靠感觉改 prompt，改完也不知道是修好了还是碰巧没炸。

## 怎么判断它有没有用

- 如果任务会跨多步、跨工具、跨状态，必须有 trace，不然复盘不了。
- 如果同一条链路反复出现慢、错、重试多，必须有指标，不然你只是在猜。
- 如果输出会影响真实动作，必须有离线评估集，不然你不知道新版本是不是把旧问题换了个样子。
- 如果系统说不出“哪一步最常失败”，那说明它还没真的被观测起来。

## 最近冒出来的词

今天可以记一个 `Deep Agents`。LangChain 在 2026-08-05 的文章里用它讲 Kubernetes 场景里的自治 SRE agent。

它不是新理论，更像一个工程提醒：越接近真实生产，越要把诊断、修复、人工审批和审计轨迹都留住。

## 一个小例子

```txt
Input:
用户说：“把 2026-08-08 的 AI Agent Daily 发布到 docs-preview，并推到 main。”

Process:
1. 记录 request_id、目标日期、文件路径、commit message。
2. 生成并写入 Markdown。
3. 记录 git add / commit / push 的耗时与返回码。
4. push 成功后再确认远端 main 是否包含该 commit。

Output:
系统知道这次是“已发布”还是“push 未确认”。
如果后面有人问为什么没上线，可以直接看 trace 找到卡在写文件、提交还是推送。
```

这个例子里，评估不是一句“发布成功”。它要能回答：文件内容对不对、提交名对不对、远端状态对不对、哪一步最慢。

## 常见误区

1. 只记最终答案，不记中间过程。这样根本复不了盘。
2. 把日志当评估。日志只是材料，评估是拿材料下判断。
3. 只看平均延迟，不看失败分布。平均值很会骗人。
4. 觉得“先上线再说”。没有基线，后面每次改动都像蒙眼拆弹。

## 今天自测

1. 为什么“答案看着对”不等于“系统稳定”？
2. trace、指标、评估集各自解决什么问题？
3. 如果一个 Agent 经常重试，你要先看哪里，才不会瞎改？

# 限流：Agent 为什么不能想调用就调用？

## 今天先记住

限流（Rate Limiting）不是把 Agent 变慢一点，而是把“外部资源有限”变成系统规则：每类工具、每个用户、每条任务链路在单位时间内最多能调用多少次，超了以后要排队、降级、等待，或者停下来交给人判断。

## 它在大地图里的位置

::: tip 今日坐标
**横跨整条链路 → 限流**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

前几天讲了重试、退避和熔断：失败后怎么再试，什么时候该停。今天再往前补一个更基础的控制面：还没失败之前，Agent 就应该知道自己不能无限调用。

限流横跨整条链路。它会影响规划层选择更少的工具步骤，也会影响执行层是否真的发起请求，还会影响最终输出：如果预算或调用额度不够，系统应该说清“为什么不能继续”，而不是让模型假装已经查完。

## 它到底是什么

限流就是给调用设置速度和总量边界。常见边界有几种：每分钟最多请求多少次、每个用户每天最多消耗多少 token、某个外部 API 同时最多跑多少任务、一次 Agent run 最多允许几次工具调用。

它不是模型的礼貌建议，而是 runtime 的硬规则。模型可以提出“我要查 20 次”，但执行层要判断：这 20 次是否在额度内，是否能合并，是否应该先查缓存，是否已经触发退避或熔断。

## 为什么 Agent 里会用到它

Agent 比普通脚本更容易放大调用量。用户只说一句“帮我查一下最近资料”，模型可能拆成多轮搜索、打开多个网页、再跑总结；如果每一步失败后还带重试，调用量会快速翻倍。

没有限流，具体问题不是抽象的“成本变高”，而是：模型接口返回 429，搜索 API 被封，消息发送被平台风控，或者一个用户的长任务占满队列，让其他正常任务排不上。

有了限流，系统可以把资源不足变成可处理状态：先合并查询、用缓存、降低检索深度、排队等待，或者让用户确认“继续会消耗更多额度”。

## 怎么判断它有没有用

- 如果某个工具按次数、token、并发或金额计费，就必须有限流。
- 如果任务会循环规划或自动重试，限流要按整条 run 计算，不能只看单次调用。
- 如果外部平台有风控，比如发消息、发邮件、抓网页，限流应该比平台封禁更早触发。
- 如果只是本地一次性格式转换，失败也不会影响外部资源，限流不是第一优先级。

## 最近冒出来的词

今天记一个 `RunState.add_input()`。OpenAI Agents Python SDK 在 2026-08-11 的 `v0.20.0` release notes 里提到，它可以在恢复模型调用前暂存 durable user input。

这是框架功能名，不是新的 Agent 理论。它和限流的关系在于：当任务因为额度、等待或人工输入暂停时，新的用户输入不能随手塞进临时上下文里丢掉，而要进入可恢复的运行状态。

来源提示：openai/openai-agents-python GitHub Releases，2026-08-11。

## 一个小例子

```txt
Input:
用户说：“帮我找 10 篇最近的 Agent 可靠性资料，整理成一页笔记。”

Process:
1. Planner 计划搜索 10 次、打开 20 个页面。
2. runtime 检查 search_tool 限额：每个 run 最多 5 次搜索、10 次网页读取。
3. 系统把查询合并成 3 个关键词组合，先取前 10 个候选链接。
4. 如果资料不够，再请求用户确认是否扩展检索。

Output:
状态从 planning -> rate_limited_search_plan -> compact_search。
最终不是盲目查 30 次，而是产出一版“基于 3 次搜索和 8 个页面”的笔记，并标明覆盖范围。
```

判断真实系统时，可以直接问：它的限制是按用户、按工具、按任务，还是只有全局一个粗暴开关？超限后是排队、降级、让人确认，还是继续撞到 429 才算？

## 常见误区

1. 把限流当成性能优化。它首先是资源和风险边界。
2. 只限制模型调用，不限制工具调用。Agent 真正烧额度的地方常常在搜索、浏览、邮件、数据库和第三方 API。
3. 每个工具各限各的，却不算整条任务总预算。这样多工具链路仍然可能失控。
4. 超限后直接报错。更好的做法是说明卡在哪个额度，并给出缩小范围、等待或人工确认的路径。

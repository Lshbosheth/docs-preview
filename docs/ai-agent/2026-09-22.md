# 补偿事务：动作已经做错了，怎么把副作用收回来？

## 今天先记住

补偿事务（compensating transaction）不是“撤销已经发生的事实”，而是在副作用已经确认后，再执行一个有明确业务含义的反向动作，让外部状态回到可接受范围。它能被审计、能幂等、也必须可能失败。发送过的消息、发布过的提交和付款，通常都回不到“从未发生”。

昨天的审计轨迹回答“动作究竟有没有发生”。今天往前走一步：如果确认动作发生了，但结果不应保留，系统怎么收尾。补偿属于失败恢复和修正，不等于重新执行原动作。

## 它到底是什么

数据库可以把一个本地事务整体回滚；Agent 调用的外部系统往往没有这种原子能力。邮件已经投递，Git 提交已经进入远端，支付已经清算，文件已经被别人读取。此时只能追加新事实。

补偿动作必须说明“抵消哪次副作用、把状态改成什么”，例如：

- 发布错误内容后，发布一份更正或撤销说明，而不是声称原发布不存在。
- 发布错误版本后，提交反向变更，让当前页面回到安全版本，同时保留历史记录。
- 发出错误通知后，向原接收范围发送带更正标识的新通知。
- 创建了错误资源后，按资源 ID 删除或停用，并确认远端返回终态。

补偿通常是语义反向，不是机械逆操作。退款不会让原交易消失，撤回链接也不保证对方没有保存内容。

## 为什么 Agent 里会用到它

Agent 会组合多个工具，前一个动作成功、后一个动作失败时，系统不能只把整条运行标成 `failed`。比如文件已推送，但随后发现内容不应公开；如果只重试整条流程，可能产生重复提交，也没有修复外部状态。

更稳的链路是：先通过审计记录确认副作用，再生成绑定原动作的补偿计划，执行后单独确认结果：

```txt
side_effect_confirmed
  -> compensation_planned
  -> compensation_executed
  -> compensation_confirmed
```

补偿本身也可能超时或部分成功，因此需要唯一补偿 ID、幂等键、前后状态和负责人。不能因为系统说要补偿，就把“已请求补偿”当成“已经补偿完成”。

## 怎么判断它有没有用

- 原动作有外部副作用，并且存在明确的业务反向动作时，才值得设计补偿；纯只读查询不需要。
- 如果无法真正恢复原状，补偿目标应是限制影响、纠正公开状态并留下说明，而不是伪装成物理回滚。
- 补偿必须绑定原事件的 `run_id`、资源 ID、版本和幂等键；否则重试可能重复退款、重复撤回或重复发布更正。
- 如果补偿涉及付款、删除、公开更正或数据暴露，通常应保留人工确认；模型可以提出补偿，但不能把一句“抱歉，已恢复”当成证据。

判断真实系统可以看它能否回答：哪个副作用触发了补偿，采取了什么反向动作，远端是否确认，最终是什么状态。只记录 `rolled_back=true` 不够。

## 最近冒出来的词

LangGraph `1.2.12` 在 2026-09-21 发布，给 `interrupt()` 增加了 `response_schema`。这是框架能力更新：流程暂停等待人工决定时，可以要求恢复输入按结构化 schema 返回。它不会自动补偿任何动作，但能减少“人批准或拒绝后，系统重新把一段自然语言猜成新计划”的风险，适合接在需要人工决定是否补偿的断点上。

## 一个小例子

```txt
Input:
课程已经 push_confirmed，远端 sha 已记录；随后二次扫描发现该内容不应公开发布。

Process:
1. 审计系统读取原 push 事件，确认副作用确实发生，不能假装提交不存在。
2. 系统创建 compensation_id=comp_0922，目标是提交反向变更，而不是 force-push 改写历史。
3. 人工确认后端校验原 run_id、远端 sha 和待提交内容哈希。
4. 反向提交成功后，部署系统返回新的远端 sha，审计记录 compensation_confirmed。

Output:
planned -> pushed -> compensation_planned -> awaiting_approval
-> compensation_executed -> compensation_confirmed

外部公开状态回到安全版本；原提交、反向提交和审批都保留证据，系统不会再次生成第二次补偿提交。
```

## 常见误区

1. 把补偿当原子回滚，忽略原动作已经对外产生事实。
2. 补偿失败后直接重试，没有补偿 ID 和幂等键，导致第二次退款或第二次发布更正。
3. 只记录“已补偿”的结果，不记录绑定哪次副作用和哪个资源版本。
4. 对所有动作都自动补偿；不可逆、高影响或语义不清时，应停下来让人决定目标状态。

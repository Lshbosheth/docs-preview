# 成本与延迟：Agent 为什么不能只看“能不能做”？

## 今天先记住

Agent 的成本与延迟不是上线后再调的性能指标，而是规划阶段就该受约束的产品边界：一条任务即使最终能完成，只要要等三分钟、要读五十个页面、要烧掉不成比例的模型和工具额度，它也不一定是一次合格的执行。

## 它在大地图里的位置

::: tip 今日坐标
**横跨整条链路 → 成本与延迟**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

昨天的缓存解决“哪些调用不必发生”，限流和熔断解决“什么时候不能继续调用”。成本与延迟把这些规则收成同一个问题：为了完成这个目标，系统最多愿意付出多少时间、调用和不确定性？

它横跨整条链路。检索多少资料、是否换更强模型、工具串行还是并行、失败后重试几次，都会改写用户等待时间和每次 run 的开销。

## 它到底是什么

成本不只等于模型 Token 账单，还包括搜索、浏览、数据库、消息发送等工具调用，以及人工审批和队列占用。延迟也不只看一次模型响应，而要看端到端时间：排队、模型生成、工具往返、重试、汇总，直到用户拿到可用结果。

因此，Agent 应该有两类预算：

- `hard limit`：超过就停止，例如单次 run 最多 12 次工具调用、60 秒、或 2 元。
- `soft target`：尽量满足，例如普通问答在 5 秒内返回；超出时可以缩小检索范围或先交付部分结果。

预算必须由 runtime 执行。模型可以建议“再看三个页面”，但不能自行决定无限追加成本。

## 为什么 Agent 里会用到它

普通 Chatbot 多数只做一次生成；Agent 会把一个请求拆成多步，还可能循环调用工具。比如“整理最近的 Agent 资料”看似只是写一段笔记，实际可能变成搜索、打开网页、提取正文、重排、总结、补查和重试。

如果没有预算，系统常见的失败不是“答案差一点”，而是两种更难受的结果：为了一个简单问题等太久，或为了追求更完整的答案不断调用，最后任务被限流、超时，且没有可交付物。

好的设计不是一味压低成本，而是按任务分档。查天气、发一条提醒这类短动作应快速结束；发布文档、排查部署可以允许更长路径，但必须让状态和预算可见。

## 怎么判断它有没有用

- 如果任务会调用模型之外的付费或慢速工具，必须同时记录 Token、工具次数和端到端耗时。
- 如果用户要的是即时确认，先返回可确定的结果；不要为了补充背景把关键路径拖成深度研究。
- 如果某一步既慢又不改变下一步决策，删掉或移到异步后处理。
- 如果任务需要高风险写操作，不能只因“预算快用完”就仓促执行；应保存 checkpoint，等待确认或下次恢复。

判断一个真实系统，可以直接问：它的单次 run 上限是什么？超预算后会产出部分结果、保存断点，还是静默失败？监控里能不能看出时间花在哪个模型或工具上？

## 一个小例子

```txt
Input:
用户说：“把今天的 AI Agent Daily 写好并发布。”

Process:
1. runtime 设定预算：90 秒、最多 8 次外部调用。
2. 读取课程框架和最近一篇文章，确定连续主题。
3. 只检索一个可靠的新词；没有可靠来源就跳过，不为热点继续搜索。
4. 写入 Markdown，git add / commit / push。
5. 若 push 超过剩余时间，保留 commit 和发布状态，停止重复尝试。

Output:
正常路径：draft -> committed -> pushed。
超时路径：draft -> committed -> push_pending，
而不是重新生成文章后再把预算烧一遍。
```

这里的关键是把“文章已写好”和“远端已发布”拆成状态。这样，慢的是 `push`，不是整条任务；恢复时只需继续未完成的一步。

## 常见误区

1. 只统计模型 Token。工具调用、重试和排队往往才是用户感到慢的原因。
2. 把并行当成免费加速。并行会缩短墙钟时间，却可能同时放大并发、额度和失败面。
3. 为了低成本一律用弱模型。关键是把模型能力放在真正影响决策的节点，而不是平均降级。
4. 超预算后只报“失败”。更实用的是返回已完成部分、断点位置和继续所需条件。

# 可观测性：Agent 出错时先看什么

## 今天先记住

Agent 不是只看最终回答对不对，而是要能追到“它为什么这么做、在哪一步变坏、坏了以后怎么停”。没有可观测性，Agent 一出错就只剩一句“我猜它想多了”。

## 它在大地图里的位置

::: tip 今日坐标
**横跨整条链路 → 可观测性**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

前面讲并行与汇合，是在让系统“同时做事”。今天讲可观测性，是让系统“做完后说得清”。它横跨整条链路，因为你想排障时，不能只看最后答案，得看到每次模型调用、每个工具参数、每次状态变更和失败点。

## 它到底是什么

可观测性（Observability）不是一堆日志文件，而是一条能还原运行过程的证据链。至少要有：trace id、每步输入输出、工具耗时、错误码、重试次数、状态落点。

对 Agent 来说，关键不是“记录很多”，而是“能把一次任务还原成可判断的轨迹”。比如模型选错工具、工具超时、重试后重复发消息、或者中途被权限拦住，这些都要能在轨迹里看出来。

## 为什么 Agent 里会用到它

Agent 会循环：想一下、试一下、看结果、再改。循环越长，越容易把问题藏起来。

如果没有可观测性，你只能看到“没成功”；有了 trace，你能看到是“规划错了”“工具报错了”“汇合规则错了”还是“重试把副作用放大了”。这决定了你该改提示词、改工具、改路由，还是改权限。

## 怎么判断它有没有用

- 如果你只能看到最终答案，却看不到中间步骤，那就还不算可观测。
- 如果一次失败后，不能说清是模型、工具、网络还是权限导致的，那日志粒度不够。
- 如果重试后会重复发消息、重复提交或重复扣费，必须靠轨迹判断幂等性。
- 如果要做评估集、回放和回归测试，先把运行过程结构化保存下来。

判断真实系统时，可以直接问一句：这条任务能不能从一条 trace 还原成“谁调用了谁、用了什么参数、在哪一步停了”？答不上来，就说明系统还在黑箱里。

## 最近冒出来的词

今天不追新词，先把主线概念讲稳。

## 一个小例子

```txt
Input:
用户说：“生成并发布 2026-09-02 的 AI Agent Daily。”

Process:
1. 记录一条 trace，包含日期、目标和当前 git 状态
2. 调用模型生成正文
3. 校验 frontmatter、文件名和敏感信息
4. 若 push 失败，只重试 push，不重写正文

Output:
成功：`2026-09-02.md` 被提交并 push
失败：轨迹里能看到卡在校验、提交或网络哪一步
```

这里可观测性的价值很具体：不是“更稳定”这种空话，而是你能定位“到底哪一步坏了”，然后只修那一步。

## 常见误区

1. 把打印日志当成可观测性，结果只有文本，没有结构。
2. 只记错误，不记正常路径，回放时拼不出完整链路。
3. 只记模型输出，不记工具输入和状态变化。
4. 失败后直接重跑，不先看 trace，最后把同一个问题放大两次。

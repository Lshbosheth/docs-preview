# Human-in-the-loop：人什么时候该插手 Agent？

## 今天先记住

Human-in-the-loop 不是“模型不行就找人”，而是把人的判断放在关键状态迁移点：批准、修改、拒绝、补充信息，然后让 Agent 从同一个现场继续执行。

## 它在大地图里的位置

::: tip 今日坐标
**执行 / 安全边界 → Human-in-the-loop**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> ▶ 执行 / 安全边界
  -> 评估 / 修正
  -> 最终输出
```

昨天讲权限与护栏，重点是“系统能不能执行”。今天往前拧一圈：当系统不能直接决定，或者直接决定会把风险推给用户时，就要进入 Human-in-the-loop（HITL，人类介入）状态。

## 它到底是什么

HITL 是 Agent 运行时里的一个暂停点。模型已经提出了计划、工具调用或输出草稿，但运行器先把现场冻结下来，等人做选择。

最小状态可以这样看：

```txt
running -> waiting_for_human -> resumed / rejected / cancelled
```

关键不只是弹一个“同意吗”按钮，而是把人能看的内容、能改的字段、选择后的状态迁移都设计清楚。否则所谓人工审批，很容易变成用户闭眼点确认。

## 为什么 Agent 里会用到它

Agent 会连接外部系统：发消息、改日历、提交代码、更新客户资料、触发定时任务。只要动作有副作用，模型的“我觉得应该做”就不能自动等于“系统已经执行”。

HITL 解决的是责任边界：低风险动作自动跑，高风险动作暂停；人不是来替模型打字，而是在不可逆、越权、费用、隐私、对外发布这些节点上承担确认或纠偏。

## 怎么判断它有没有用

- 如果动作会对外发送、写库、扣费、发布、删除，默认需要 HITL 或更严格的禁止策略。
- 如果人需要改参数，而不是只批准，例如改收件人、时间、金额、提交范围，就要支持“编辑后继续”，不能只有同意/拒绝。
- 如果暂停后不能从原状态恢复，只能重新跑一遍，那不是完整 HITL，只是临时打断。
- 看一个真实系统时，问三件事：人看到了哪些证据？点了什么？恢复后执行的是原参数还是改后参数？

## 最近冒出来的词

最近可以留意 “webhook-triggered scheduled tasks”。OpenAI Help Center 在 2026-08-25 的 ChatGPT Release Notes 里提到，ChatGPT Work 的定时任务可以响应 Gmail、Slack、GitHub 等应用更新；需要审批的动作会暂停，等用户 review 后再继续。

这不是一个全新的理论名词，更像产品把“事件触发 + 外部工具 + HITL”组合到一起。它提醒我们：Agent 不是只在聊天框里运行，越来越多任务会被外部事件唤醒；越是自动唤醒，越要把审批状态做成一等公民。

来源提示：[OpenAI Help Center](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)，2026-08-25。

## 一个小例子

```txt
Input:
GitHub PR 更新，触发一个“总结变更并准备发布日课”的任务。

Process:
1. Agent 读取变更，只允许访问 docs-preview/docs/ai-agent/
2. 生成 commit message 和待提交文件列表
3. 发现下一步是 git push，进入 waiting_for_human
4. 人检查文件列表，删除无关文件，批准继续

Output:
状态从 waiting_for_human 变成 resumed；
系统只提交批准后的 Markdown 文件，并记录审批人、审批时间和最终参数。
```

这里最值得学的是：人介入的对象不是一段模糊建议，而是一组可检查的状态和参数。

## 常见误区

1. 把 HITL 当成失败兜底。真正有用的 HITL 是预先设计在高风险节点上的。
2. 只让人点确认，不展示输入、计划、工具参数和影响范围。
3. 人改了参数，但系统恢复时仍执行模型最初那份参数。
4. 审批没有审计记录，事后说不清是谁批准了什么。

## 今天自测

1. 一个 Agent 发邮件前，至少应该让人检查哪三个字段？
2. 为什么“暂停后可恢复”比“重新发起任务”更适合 HITL？
3. 什么时候应该直接禁止工具调用，而不是交给人审批？

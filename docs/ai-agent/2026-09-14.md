# Agent 失败后怎么恢复：重试、幂等与安全停止

## 今天先记住

Agent 的可靠性，不是“永远不出错”，而是出错后能判断：这一步能不能重试、重试会不会产生重复副作用、系统要不要暂停等人处理。重试不是按钮，而是一条带条件的状态转换。

## 它在大地图里的位置

::: tip 今日坐标
**评估、可观测性与可靠性 → ▶ 失败恢复**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

前两天我们看成本、延迟和 Trace，今天继续往运行闭环里走：当工具超时、网络断开或模型输出坏格式时，系统如何从“执行中”进入“可恢复”“已阻断”或“需要人工确认”，而不是盲目再来一次。

## 它到底是什么

**重试**是对暂时性失败再次执行；**退避**是在连续失败时逐渐拉长等待时间；**幂等**是同一个逻辑动作执行一次或多次，最终状态仍然一致。三者要一起设计。

读接口超时，通常可以直接重试；发消息、扣款、创建发布记录这类有副作用的操作，不能只因为“没收到响应”就再发一次。因为超时只说明调用结果未知，不等于调用没有发生。

最小状态可以这样写：

```txt
执行中 -> 成功
执行中 -> 暂时失败 -> 退避重试
执行中 -> 结果未知 -> 查询幂等键 / 对账
执行中 -> 永久失败或高风险 -> 阻断 / 人工接管
```

## 为什么 Agent 里会用到它

Agent 会自主选择工具，也会在观察结果后继续行动。若没有恢复边界，一个 API 超时就可能触发重复发送；一个坏 JSON 就可能让模型不断修补；一个人工审批后的断点如果没有持久化，进程重启后甚至不知道自己批准过什么。

工程上通常给每次逻辑动作生成幂等键，例如 `thread_id + tool_name + normalized_args + action_id`。工具侧保存处理结果：相同键再次到达时，返回原结果，不重新产生副作用。注意，模型每次重新生成的文字可以不同，但同一个业务动作的键不能跟着随机变化。

## 怎么判断它有没有用

- 失败是否能区分“未执行”“执行成功但响应丢失”“执行结果未知”？不能区分时，不要自动重试写操作。
- 重试是否只针对可恢复错误，例如超时、连接断开、限流；参数错误、权限拒绝、敏感信息拦截应直接停止。
- 每次重试是否共享同一个幂等键，并记录次数、等待时间和最终状态？
- 重试三次仍失败后，系统是否能给出明确状态，如 `publish_pending`，而不是继续循环或假装成功？

## 最近冒出来的词

**AgentCore Evaluations 的 TypeScript 支持**：AWS Bedrock AgentCore 的近期发布说明提到，Evaluations 已支持用 TypeScript 版本框架构建的 Agent，包括 Strands Agents、LangGraph、OpenAI Agents 和 Vercel AI SDK。它不是一种新的恢复算法，但说明 Agent 评估正在从“只看最终回答”走向覆盖不同运行时与轨迹的工程验证。今天的判断标准可以借它提醒自己：重试后的最终答案看着正常，不代表中间副作用没有重复。

## 一个小例子

```txt
Input:
用户说：“合规检查通过后，把今天的文档提交并推送。”

Process:
1. 扫描工具返回 blocked，状态改为 publish_blocked，不进入 Git 操作。
2. 若 push 请求发出后网络超时，状态改为 result_unknown。
3. 系统用 action_id 查询远端提交状态；确认未成功，才用同一个幂等键重试。
4. 超过两次仍无法确认，转为 publish_pending，等待人工处理。

Output:
不会因为一次超时就创建两个提交，也不会把“结果未知”误报成“推送失败”。
```

判断一个真实 Agent 是否靠谱，可以故意在“工具已成功、响应未返回”的时间点杀掉进程，再恢复运行。若它能靠 checkpoint 和幂等键继续或对账，而不是重复执行，才算真正有恢复能力。

## 常见误区

1. 把所有错误都重试，导致权限错误、参数错误和副作用重复。
2. 每次重试都生成新的 action_id，幂等保护形同虚设。
3. 只保存“重试了几次”，却不保存当前状态和工具结果，重启后无法续跑。
4. 设置最大次数却没有最终出口，失败后仍让 Agent 自己继续循环。

## 今天自测

1. 哪些工具可以自动重试，哪些工具必须先查询结果或人工确认？
2. 你的幂等键由哪些字段组成？参数顺序变化会不会误判成新动作？
3. 如果进程在外部写入成功后立刻崩溃，恢复时系统凭什么证明自己不会重复写入？

# 并行与汇合：Agent 怎么同时做几件事又不乱？

## 今天先记住

并行不是让 Agent “一口气多干点”这么简单。真正重要的是：哪些步骤可以同时跑，哪些结果必须等齐，哪些失败可以部分接受，最后怎样汇合成一个可判断的系统状态。

前面讲成本与延迟，是问“一次任务最多值得花多少”。今天落到工具层：如果三个工具彼此不依赖，串行等待就是白等；但如果结果汇合规则没设计好，并行会把错误、超时和部分成功一起推到后面，反而更难收场。

## 它到底是什么

并行（Parallel Execution）是把多个互不依赖的动作同时发起。汇合（Join / Aggregation）是等这些动作返回后，把结果合成下一步决策需要的状态。

它不是“所有工具一起上”。一个可用的并行节点至少要写清四件事：每个分支的输入是什么、超时时间是多少、失败是否影响整体、汇合后输出什么结构。

## 为什么 Agent 里会用到它

Agent 经常要同时看几类证据：读本地文件、查最近资料、看 git 状态、检查线上页面。这些动作互不依赖时，并行能缩短用户等待的墙钟时间。

但 Agent 的下一步通常依赖“汇合后的事实”，不是依赖某个分支的一句话。比如发布日课前，内容生成成功、文件路径正确、git 暂存区干净，这三件事要一起满足，系统才能进入 `ready_to_commit`。只要其中一个失败，就应该停在明确状态，而不是让模型用一句“应该没问题”糊过去。

## 怎么判断它有没有用

- 如果多个工具只读、互不依赖、都服务于同一个判断，并行通常值得做。
- 如果后一步需要前一步的输出，例如先生成文件再检查 frontmatter，就必须串行。
- 如果某个分支失败会改变安全判断，例如权限检查失败，汇合规则必须让整体失败。
- 如果某个分支只是补充信息，例如最近术语搜索超时，可以降级为“不追新词”，但要把降级写进状态。

判断真实系统时，可以问一句：并行分支返回后，系统是按结构化规则汇合，还是把几段自然语言丢回模型猜？后者一出错就很难复盘。

## 最近冒出来的词

最近可以留意 OpenAI API Changelog 里的 Assistants API shutdown。它是产品生命周期变化，不是新的 Agent 理论：OpenAI 标注 Assistants API 已在 2026-08-26 关闭，并建议迁移到 Responses API 和 Conversations API。

这和今天的主题有一点关系：新的 Agent 应用更应该把工具调用、会话状态、并行分支和汇合结果放进自己的运行时设计里，而不是把“线程里发生过什么”全寄托给旧接口。

## 一个小例子

```txt
Input:
用户要求：“生成并发布 2026-09-01 的 AI Agent Daily。”

Process:
1. 并行读取课程框架、最近一篇日课、git 状态
2. 汇合成 draft_context：next_topic、publishing_rules、dirty_files
3. 生成当天 Markdown
4. 串行检查 frontmatter、文件名、敏感信息
5. 只提交当天文件并 push

Output:
如果检查全通过，状态变成 published，并返回 /ai-agent/2026-09-01
如果 git 状态有无关改动，状态变成 commit_scoped，只 add 当天 Markdown
```

这个例子的关键不是“快”，而是并行读取不会改变事实，汇合规则会决定后面能不能安全提交。

## 常见误区

1. 把并行当成默认优化。并发会放大限流、成本和失败面。
2. 只关心谁先返回，不设计“等谁、放弃谁、失败谁”的规则。
3. 汇合时只拼文本，不保留工具名、输入、耗时、错误码和状态。
4. 忽略副作用。发消息、付款、删除、发布这类动作通常不该随便并行。

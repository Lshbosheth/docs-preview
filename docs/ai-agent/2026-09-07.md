# Human-in-the-loop：什么时候必须让人接一手

## 今天先记住

Human-in-the-loop 不是“让用户多点一次确认”这么简单。它是 Agent 状态机里的接管点：当系统不该继续自作主张时，把判断、授权或修正交回给人。

## 它在大地图里的位置

::: tip 今日坐标
**权限、安全与人工接管 → ▶ Human-in-the-loop**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

前两天讲的是“边界”和“护栏”：哪些不能直接做，哪些动作要被拦一下。今天再往里拧一圈：拦住之后怎么办？Human-in-the-loop（HITL）就是这一步的工程答案。

## 它到底是什么

HITL 是把人放进 Agent 运行流程中的某个明确节点。人可以做三类事：批准动作、补充信息、纠正路线。

它不是聊天框里随便问一句“可以吗”。一个合格的接管点，要告诉人：系统准备做什么、为什么这么做、影响范围是什么、不批准会怎样、批准后从哪里继续。

所以 HITL 更像一次状态切换：`running -> waiting_for_approval -> approved/rejected -> continue/abort`。重点不是“有人参与”，而是程序能记录这个参与，并按结果改变后续路径。

## 为什么 Agent 里会用到它

Agent 会连续规划、调用工具、观察结果。越靠近外部系统，越容易出现两类问题：模型不确定，但还想继续；动作有副作用，一旦做错很难撤回。

比如发消息、删文件、改配置、付款、发布文档，都不是“答案质量好不好”的问题，而是外部世界会被改变。HITL 的作用，就是在风险从“可修改草稿”升级成“真实执行”前，建立一个可审计的停顿。

如果没有这个节点，系统常见故障会变成：用户只想看草稿，Agent 却直接发出去了；工具返回模糊错误，模型自行脑补下一步；检索内容里混入恶意指令，系统没有机会让人判断可信度。

## 怎么判断它有没有用

- 如果动作不可轻易撤销，默认需要 HITL。
- 如果系统无法解释影响范围，就不该让用户盲批。
- 如果模型置信度低、工具结果冲突、上下文缺关键字段，应该先问人补齐，而不是继续猜。
- 如果任务只是本地草稿、摘要、分类，HITL 可能是负担；等它要发布、写入、删除、发送时再接入。

判断一个真实系统时，可以问：它暂停时，是只弹一句“是否继续”，还是能展示“将改哪些对象、用什么参数、谁批准、批准后从哪一步恢复”？

## 最近冒出来的词

`GPT-6 Astra`。这是 OpenAI 在 2026-09-03 release notes 里提到的模型发布，不是一个新的 Agent 架构概念。

它被描述为更适合 coding、research、computer use 和复杂多步工作。放到今天的话题里看，模型越能连续处理文件、命令和多步任务，越需要清楚的人工接管点。能力变强不等于发布、删除、支付这些动作可以自动放开。

## 一个小例子

```txt
Input:
用户说：“把今天的 AI Agent Daily 写完并发布。”

Process:
1. Agent 生成 Markdown，并检查日期、标题、路径
2. 系统发现下一步是 git push，属于公开发布
3. 如果内容安全且任务规则已授权，进入 approved_publish
4. 如果检查到 API key、私密日志、地址、电话等敏感信息，进入 waiting_for_human，不再 push

Output:
正常：`draft_checked -> approved_publish -> pushed`
异常：`draft_checked -> waiting_for_human -> publish_blocked`
```

这个例子里，HITL 不是拖慢流程，而是把“写出来”和“对外生效”分成两个状态。只要风险等级变了，系统就不能装作还是同一个动作。

## 常见误区

1. 把 HITL 做成万能确认框，却不展示具体影响范围。
2. 只有人工批准，没有记录批准人、时间、参数和后续状态。
3. 模型不确定时继续问模型，而不是让人补充缺失事实。
4. 所有小事都要求确认，最后用户被弹窗训练到闭眼点通过。

## 今天自测

1. 你的 Agent 里，哪三个动作必须进入 `waiting_for_approval`？
2. 人批准前，系统至少应该展示哪些参数和影响范围？
3. 如果用户拒绝，流程是能回到草稿态，还是只能整条失败？

# 降级模式：回退之后，Agent 至少要保住什么？

## 今天先记住

回退链决定“下一步换成谁”，降级模式决定“下一步还允许系统做什么”。降级可以减少模型能力、并行度或功能入口，但不能悄悄降低权限边界、状态一致性、审计和输出契约；保不住这些，正确动作是停止，不是硬撑。

昨天讲回退链，解决主路径失败后换哪个候选。今天补上候选接管时的“服务等级”：它执行完整任务，还是只生成草稿、只读查询，或者只能等待人工。降级模式向下影响工具暴露与执行许可，但决策口先在规划层明确。

## 它到底是什么

降级模式（degraded mode）是预先定义的低能力运行状态。它至少要声明：触发原因、保留能力、关闭能力、允许的工具、输出契约、是否允许副作用、退出条件和恢复动作。每个回退候选都应绑定到某个模式，而不是只换模型名。

例如文档发布系统可以分为：

- `normal`：生成、检查、审批、commit、push 都可执行。
- `read_only`：只生成草稿和读取资料，不暴露写工具。
- `manual_handoff`：冻结任务现场，只允许人查看、修正和继续。

模式可以变多，但边界不能临时猜。一次运行进入 `read_only` 后，模型即使生成了合规的 `git_push` 参数，工具注册表里也不应有这个动作。

## 为什么 Agent 里会用到它

Agent 的模型调用、工具调用和外部副作用是三个不同层次。主模型失败，不代表用户可以接受权限变小，也不代表刚才已经成功的动作可以重做。若只做“换模型继续跑”，备用模型可能拿到旧上下文，重新 push、重复发送，或用一个能力更弱的模型自由生成高风险参数。

更稳的流程是：先判断失败发生在副作用之前还是之后，再选择降级模式。之后可以缩小能力，但不能放松约束。降级模式的工程价值，不是让系统永远有回应，而是把失败限制在可解释、可恢复的状态。

## 怎么判断它有没有用

- 先列不可降级项：权限、审批、审计、幂等、schema、敏感数据边界和外部副作用。任何候选保不住其中一项，就应该停止或转人工。
- 只有读取、摘要、草稿这类低风险步骤适合降级继续。写操作即使换模型，仍要经过与正常模式相同的参数校验和授权。
- 运行状态必须显式记录 `mode`、触发原因、被关闭的能力和恢复条件。不能让用户看到一个低能力结果，却以为任务已完整完成。
- 设计时要实际注入模型超时、坏 JSON、工具不可用等故障，并证明系统能进入指定模式、安全退出，而不是自动落到无限重试。

## 最近冒出来的词

`langchain-openai==1.6.6` 在 2026-09-24 发布，发布说明包含“raise on error events in stream path”。它不是新的 Agent 架构，而是一处流式调用修复：错误事件不能被吞掉后伪装成正常结束。它和降级模式的连接点是，备用路径也必须保留真实失败信号；只有明确看见失败，系统才能决定是降级、停止还是恢复。

## 一个小例子

```txt
Input:
用户要求：“生成 2026-09-26 的课程，检查敏感内容后提交并推送。”

Process:
1. 主模型在生成发布计划时超时，checkpoint 仍停在 scan_pending，尚未 commit 或 push。
2. 回退候选绑定 degraded_mode=read_only，只获得生成草稿和读取资料的工具。
3. 备用模型生成 Markdown，扫描器完成检查，本地文件状态变为 draft_ready。
4. 系统尝试进入发布步骤时发现 push 工具未注册，状态停在 publish_blocked，并记录恢复条件。

Output:
normal -> degraded(read_only, reason=model_timeout)
-> draft_ready -> publish_blocked

没有产生远端提交；恢复主模型后，可从已校验草稿继续，不必重新生成。
```

## 常见误区

1. 把降级等同于换模型，继续暴露原有全部工具和权限。
2. 为了维持可用性，绕过审批、审计或幂等保护。
3. 只生成草稿却对用户报告“已完成”，隐藏实际降低了哪些能力。
4. 没有恢复条件，系统一旦降级就长期停在那里，没人知道何时回到正常模式。

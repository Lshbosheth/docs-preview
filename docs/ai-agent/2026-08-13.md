# 重试与退避：Agent 失败后为什么不能立刻蛮跑？

## 今天先记住

重试（Retry）不是“失败了再试一次”这么粗糙。Agent 里的重试要先判断失败类型、动作是否有副作用、是否已有幂等保护，再决定什么时候重试、重试几次、什么时候停下来交给人。

前两天讲 checkpoint 和幂等：一个负责知道断在哪里，一个负责防止恢复时把动作做两遍。今天继续看恢复链路里的下一步：失败后要不要再试。

在 Agent 系统里，失败不只是一种。模型接口可能限流，工具可能超时，文件可能被占用，外部服务可能返回 500，也可能是参数错了、权限不够、用户目标本身不清楚。把这些都当成“再试一次”，系统就会从可靠变成扰民。

## 它到底是什么

重试是失败后的再次执行；退避（Backoff）是两次重试之间逐渐拉开时间，比如 1 秒、2 秒、4 秒、8 秒。

真正重要的不是公式，而是分类：临时故障可以重试，确定性错误不要重试，高风险副作用动作必须先查幂等状态再重试。

所以一个像样的 Agent runtime 不会只写 `try again`。它会记录错误类型、工具名、参数、幂等 key、已尝试次数、下一次可重试时间，以及最终失败后要返回给谁处理。

## 为什么 Agent 里会用到它

Agent 经常要串多个系统：读文件、查资料、生成内容、提交代码、发布页面。中间任何一步失败，直接放弃会让任务半截停住；无限重试又可能耗光 token、打爆 API 限额，甚至重复触发外部动作。

重试与退避的价值，是把“暂时不通”从“任务失败”里拆出来。比如 push 失败可能只是网络抖动，等十秒再试有意义；但 Markdown frontmatter 写错导致构建失败，重复构建十次也不会自己变好。

## 怎么判断它有没有用

- 如果错误来自网络、限流、远端 5xx、锁竞争，可以有限重试，并加退避。
- 如果错误来自参数校验、权限拒绝、schema 不匹配，先修输入或请求人工，不要自动重试。
- 如果动作会写入外部状态，重试前必须查幂等 key 或已完成记录。
- 如果同一步连续失败到上限，要保存 checkpoint，并把“卡在哪、最后一次错误是什么”交出去。

## 一个小例子

```txt
Input:
用户要求：“发布 2026-08-13 的 AI Agent Daily。”

Process:
1. 写 Markdown 成功，记录 file_written = true。
2. git commit 成功，记录 commit_sha = abc。
3. git push 返回网络超时。
4. 系统检查 push 是可重试动作，且 commit 已存在。
5. 等 5 秒后只重试 git push，不重新生成文章、不重新 commit。

Output:
状态从 committed -> push_retrying -> pushed。
如果连续 3 次 push 都失败，状态停在 push_failed，并保留 commit_sha 和错误信息。
```

这个例子里，重试不是“整条流程重跑”。它只针对失败的、可安全重复的那一步。判断真实系统时，可以直接问：它失败后是从哪一步继续？有没有重试上限？有没有把确定性错误误当成临时故障？

## 常见误区

1. 认为重试越多越可靠。没有上限的重试会制造成本、限流和重复副作用。
2. 所有错误都重试。参数错、权限错、格式错，重复执行只会重复失败。
3. 只做重试，不做退避。服务已经限流时立刻连打，只会让恢复更慢。
4. 忘了和 checkpoint、幂等配合。没有断点和去重，重试很容易变成整套流程重演。

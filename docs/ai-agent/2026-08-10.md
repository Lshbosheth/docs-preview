# 会话隔离：Agent 状态为什么不能混在一起？

## 今天先记住

Agent 的状态不是“多存几条聊天记录”。真正要守住的是：谁在发起任务、哪条线程在推进、这一次运行走到了哪一步，三者不能混。

## 它在大地图里的位置

::: tip 今日坐标
**上下文 / 记忆 → 会话隔离**
:::

```txt
用户目标
  -> ▶ 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

前面讲过 context window、短期状态和长期记忆。今天往工程里落一步：同样是“记住”，系统必须先知道这些状态属于谁、属于哪条任务线、属于哪次执行。

如果这层没分清，后面的规划、工具调用、权限判断都会被污染。Agent 不是忘了东西，而是把别人的东西、旧任务的东西、失败运行的东西当成了当前事实。

## 它到底是什么

会话隔离就是给状态加边界。

常见边界至少有三层：`user_id` 表示哪个用户，`thread_id` 表示哪条连续对话或任务，`run_id` 表示某一次具体执行。

`user_id` 解决“这是谁的偏好和权限”；`thread_id` 解决“这段上下文属于哪件事”；`run_id` 解决“这次执行中间做过什么，失败后从哪里恢复”。

它不是数据库字段洁癖，而是防止 Agent 在多轮、多工具、多用户环境里串台。

## 为什么 Agent 里会用到它

普通 Chatbot 即使串一点上下文，最多答得怪。Agent 会调用工具、写文件、发消息、提交代码，状态串了就可能变成真实副作用。

比如用户 A 让系统整理文档，用户 B 让系统发布日报。如果只按“最近一条消息”取状态，Agent 可能拿 A 的草稿去完成 B 的发布任务。

再比如同一用户开了两条线程：一条在改记忆系统，一条在写 AI Agent Daily。没有 `thread_id`，模型可能把“不要构建”这条发布规则带到另一个需要构建验证的任务里。

## 怎么判断它有没有用

- 如果系统会同时服务多个用户，必须有 `user_id` 级隔离，权限和长期记忆都不能混。
- 如果同一用户会并行推进多件事，必须有 `thread_id`，不能只靠最近消息猜上下文。
- 如果任务有重试、暂停、恢复或人工审批，必须有 `run_id`，否则不知道哪次工具调用已经发生。
- 如果一个状态会影响外部动作，它就不该只存在 prompt 里，应该能被程序按边界读取和校验。

## 最近冒出来的词

今天可以顺手记一个 `session branch`。OpenAI Agents SDK 在 2026-08-05 的 v0.19.4 release 里提到，创建分支时会拒绝复用 branch ID。

这不是热词，更像一个小而硬的工程约束：当会话可以分支、恢复、重放时，分支身份必须唯一，否则历史会被接错。

它和今天的主题正好对上：Agent 的“记忆”越像可恢复运行时，状态边界就越不能含糊。

来源提示：OpenAI Agents SDK GitHub Releases，2026-08-05。

## 一个小例子

```txt
Input:
user_id = u_01
thread_id = ai_daily
用户说：“生成并发布 2026-08-10 的 AI Agent Daily。”

Process:
1. 创建 run_id = run_20260810_0930。
2. 只读取 ai_daily 线程的发布规则和历史课程标题。
3. 写入 docs/ai-agent/2026-08-10.md。
4. commit / push 前记录本次 run 已写入的文件。

Output:
run 状态从 running -> pushed。
如果 push 失败，系统只恢复 run_20260810_0930，不会误拿别的线程继续提交。
```

这里的关键不是多了几个 ID，而是每一步都能回答：这个状态归谁、归哪条任务、归哪次执行。

## 常见误区

1. 把聊天记录当会话状态。聊天记录只是材料，不等于可恢复的运行状态。
2. 只按用户隔离，不按线程隔离。同一个人也会同时做几件完全不同的事。
3. 重试时不开新 `run_id`，导致旧失败和新执行混在一起。
4. 把长期偏好当当前事实。偏好可以辅助判断，不能直接替代这次任务的输入。

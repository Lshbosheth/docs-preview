# 回退链：主模型失败后，Agent 该怎么安全降级？

## 今天先记住

回退链（fallback chain）不是失败后多换几个模型再试，而是一组预先定义、按顺序检查的替代方案。每一次回退都要回答同一个问题：从哪个已确认状态继续，哪些动作绝不能重做，什么结果才算真正可用。

## 它在大地图里的位置

::: tip 今日坐标
**规划 / 决策 → ▶ 回退链**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> ▶ 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

昨天讲模型路由，解决的是“这次调用选谁”。今天往前走一步：首选模型已经失败时，Agent 沿着什么顺序降级，又该从哪个状态恢复。

## 它到底是什么

回退链可以包含备用模型、模型版本、供应商、超时时间、输出校验器或人工接管入口。候选不一定要更弱，也可以是针对不同故障类型的替代方案：短文本抽取换小模型，结构化输出坏掉时换支持严格 schema 的模型，供应商限流时切到另一条合规通道。

一个可执行的回退项至少要声明：适用的失败类型、最大尝试次数、允许读取的上下文、工具与数据边界、输出契约，以及进入下一候选前要保留的 checkpoint。程序按顺序拿第一个通过 schema、安全和业务断言的结果，而不是拿第一个“看起来像答案”的结果。

## 为什么 Agent 里会用到它

Agent 的一次失败并不都一样。请求超时、429 限流、坏 JSON、工具参数错误、业务拒绝和权限不足，后续动作完全不同。把所有错误都交给“再试一次”，会让模型反复生成同一个坏调用；无上限升级模型，也可能把临时故障变成慢、贵且不可复现的循环。

更危险的是副作用。提交可能已经进入远端，只是本地没收到响应；消息可能已经发出，只是回退时换了模型。若新模型拿到旧对话后来一句“重新执行”，系统就会重复提交或重复发送。因此，回退前先查最后确认的 checkpoint，再决定是重做一步、继续剩余步骤，还是停止。

## 怎么判断它有没有用

- 先按“发生副作用之前 / 之后”分类。之前可以有限重试或换模型；之后只能从确认状态继续，或进入补偿、人工接管，不能整条重跑。
- 候选必须满足同一任务契约，包括工具调用、JSON Schema、上下文长度和数据合规要求；只是“答案文字更好”不构成可替换。
- 为回退链设置总预算：最多几个候选、总耗时、Token 与调用成本。超过预算应安全停止并报告最后确认状态。
- 降级不能突破风险边界。为了可用性切到不支持审批、无法审计或会把敏感数据发往别处的模型，不是回退，是扩大故障。
- 排障时至少能看到 `failure_class`、候选顺序、每次起始 checkpoint、结束原因和最终采用结果；只看“最后用了哪个模型”不够。

## 一个小例子

```txt
Input:
用户明确授权：“生成今天的课程，校验通过后提交并推送。”

Process:
1. 主模型生成课程和操作计划，程序完成内容扫描与提交参数校验。
2. push 成功，远端返回 sha=abc123，checkpoint 记录 push_confirmed。
3. 主模型生成最终总结时超时；这里已有外部副作用，不能从任务开头重跑。
4. 回退到备用模型，只传入已确认状态、课程版本和远端 sha，任务是生成总结，不包含 push 工具。

Output:
push_confirmed -> fallback_started(checkpoint=push_confirmed)
-> summary_validated -> completed

远端只有一次 push；备用模型没有机会再次调用 push。
```

## 常见误区

1. 把回退当无限重试，不限制候选数量、总成本和总耗时。
2. 只换模型，不允许它读取最后确认状态，导致重复执行已经成功的工具。
3. 为了保持可用性，把高权限任务降级到更弱的数据或审批边界。
4. 只记录最终模型和答案，不记录失败分类、起始 checkpoint 与放弃原因。

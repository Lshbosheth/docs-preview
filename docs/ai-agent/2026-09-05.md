# Agent 产品边界：什么不该交给 Agent

## 今天先记住

Agent 的产品边界不是“它最多能做什么”，而是“哪些动作即使模型会做，也不应该自动做”。边界画得清，系统才知道什么时候继续、什么时候降级、什么时候请人确认。

## 它在大地图里的位置

::: tip 今日坐标
**用户目标 / 系统边界 → ▶ Agent 产品边界**
:::

```txt
▶ 用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

前几天讲了失败恢复、可观测性、多 Agent handoff，都是系统跑起来之后怎么控场。今天往上提一层：在产品入口处，先决定哪些事可以让 Agent 自主推进，哪些事只能辅助，哪些事必须停在人那里。

## 它到底是什么

Agent 产品边界（product boundary）是一组“可自治范围”的规则。它回答三个问题：系统能替用户决定什么，能替用户执行什么，执行前要不要确认。

比如“整理今天的学习笔记”可以高度自动化；“删除一批历史文件”就必须先展示影响范围；“代表用户向外部联系人发送敏感内容”通常不该全自动。这里不是能力问题，而是责任问题：出了错，谁承担后果，谁能追溯过程，谁有权批准动作。

## 为什么 Agent 里会用到它

Agent 会把“理解目标、选择步骤、调用工具”连成一条链。一旦链路里有外部副作用，产品边界就比 prompt 更重要。

如果边界不清，常见故障不是模型不会，而是模型太敢：把草稿当正式消息发出去，把“查一下”理解成“改掉配置”，把可疑检索结果当用户授权。工程上要把高风险动作变成状态机里的显式关卡，而不是只在提示词里写一句“请谨慎”。

## 怎么判断它有没有用

- 如果动作会写入、删除、支付、发布、发消息，默认需要边界规则，不能只靠模型自觉。
- 如果用户能低成本撤销，自治范围可以宽一点；如果后果难撤销，就要确认、审计或人工接管。
- 如果系统无法向用户解释“接下来会改哪里、发给谁、用什么内容”，就不该进入执行态。
- 如果任务只是读取、归纳、生成草稿，Agent 可以先做；但从草稿变成真实外部动作时，要重新过边界。

判断真实系统时，可以问一句：模型输出错了以后，最坏后果是“答案不好看”，还是“外部世界已经被改了”？后者必须有产品边界。

## 一个小例子

```txt
Input:
用户说：“把今天的 AI Agent Daily 写完并发布。”

Process:
1. 系统判断：写作是低风险，保存 Markdown 是本地写入，git push 是对外发布
2. 生成文章并检查 frontmatter、标题、日期、路径
3. 如果内容包含 API key、私密日志、地址、电话等敏感信息，状态进入 blocked_publish
4. 如果没有敏感内容，才允许 commit 和 push

Output:
安全内容：`draft_checked -> committed -> pushed`
敏感内容：`draft_saved -> blocked_publish`，只返回本地路径，不发布
```

这个例子里，边界不是挡住 Agent 干活，而是把“能写”和“能发布”分开。写错草稿可以改；把私密内容推到公开站点，就是另一个风险等级。

## 常见误区

1. 把“模型能完成”当成“产品应该放开”。
2. 只给工具加权限，不给动作加风险等级。
3. 把确认弹窗当万能护栏，却不展示影响范围和具体内容。
4. 没有审计记录，事后只能猜 Agent 当时为什么这么做。

## 今天自测

1. 你的 Agent 里，哪些动作只是生成草稿，哪些动作会改变外部世界？
2. 哪三个操作必须先给用户看影响范围再执行？
3. 如果一次自动执行出错，系统能不能说清是谁授权、改了什么、在哪一步发生？

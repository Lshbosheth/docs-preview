# 多 Agent 协作：什么时候该 handoff

## 今天先记住

多 Agent 的重点不是“人多力量大”，而是把不同职责拆开，让系统在合适的边界上换控制权，而不是让一个 Agent 背着所有工具硬跑。

今天讲的是“谁来接下一步”。它放在规划和执行之间，因为多 Agent 解决的不是单个工具怎么调，而是当任务跨职责、跨权限、跨上下文时，控制权该交给谁。

## 它到底是什么

多 Agent 协作（multi-agent）不是把一个 Agent 拆成很多分身就完事了。
真正有用的地方，是让系统里出现不同角色：有的负责路由，有的负责专门任务，有的负责接手后继续和用户说话。

这里最容易混的三种模式是：

- **Subagents**：主 Agent 仍然掌控全局，只是把子任务当工具调用。
- **Handoff**：当前 Agent 真的把控制权交出去，后一个 Agent 接着对话和执行。
- **Router**：先分类，再把请求分给对应专家，最后汇总结果。

一句话区分：subagent 是“我替你干”，handoff 是“你来接”，router 是“我先分流”。

## 为什么 Agent 里会用到它

当一个 Agent 背着太多工具时，最先坏掉的不是能力，而是判断。
工具越多，越容易选错；上下文越长，越容易把不该给的内容塞进同一个提示词；权限越杂，越容易把只该给专家看的东西混进去。

handoff 的价值在于把“角色边界”变成运行时状态，而不是只靠提示词装样子。
比如客服转财务、草稿写作转发布、代码修复转审查，这些场景里，接手者不只是回答风格变了，工具集、上下文和责任也应该一起变。

## 怎么判断它有没有用

- 如果一个 Agent 已经同时背着很多互相不相关的工具，先考虑拆成主控 + 专家，而不是继续加 prompt。
- 如果任务中途需要换权限、换语气、换可见信息，handoff 比“同一个 Agent 硬扛到底”更合理。
- 如果只是几个独立子步骤，最后还是同一个总答案，subagent 或 workflow 往往比 handoff 更稳。
- 如果你无法说清“这次交给谁、为什么交、交出去后谁负责收尾”，那就还没到该上多 Agent 的时候。

判断真实系统时，看三件事就够了：谁持有当前控制权、谁能看到哪些上下文、失败时责任落在哪个 Agent 上。

## 一个小例子

```txt
Input:
用户说：“把今天这篇 AI Agent 日课写好，检查完再发布。”

Process:
1. 总控 Agent 先判断：写作和发布是两种职责
2. 写作 Agent 负责生成 Markdown
3. 发布 Agent 只拿到成稿和发布路径，执行保存、提交、push
4. 总控 Agent 收回控制权，输出结果

Output:
文章落到 `docs-preview/docs/ai-agent/2026-09-04.md`
发布 Agent 只处理发布，不接写作细节；总控负责最后状态汇总
```

这个例子里，handoff 不是“多叫了几次模型”，而是职责真的换了。写作 Agent 不该碰 git，发布 Agent 也不该重新改文案，不然边界一糊，排障会很痛。

## 常见误区

1. 把多 Agent 当成性能优化，结果只是多绕了几圈。
2. 让每个 Agent 都能做所有事，最后谁都不专。
3. 交接时不缩上下文，把前一个 Agent 的噪音一起带过去。
4. 没有明确收尾者，出错后不知道该找谁负责。

## 今天自测

1. 你现在的任务更像 subagent、handoff 还是 router？
2. 哪些信息应该在交接时被切掉，不该继续往下传？
3. 如果接手的 Agent 失败了，系统要回到谁那里继续？

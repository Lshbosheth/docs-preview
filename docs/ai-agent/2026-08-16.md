# 缓存：Agent 为什么要先复用结果，再调用工具？

## 今天先记住

缓存（Cache）不是“把答案存起来，下次直接糊给用户”。它是在 Agent 再次调用模型、搜索、数据库或外部 API 前，先判断已有结果是否仍然满足当前目标、是否还在有效期内、是否允许被当前用户使用。

## 它在大地图里的位置

::: tip 今日坐标
**评估 / 修正 → 缓存**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

前几天讲了重试、熔断和限流：调用失败时怎么停，资源紧张时怎么收。缓存再往前一步：有些调用根本不必发生。它横跨规划和执行，因为“是否复用旧结果”本身就是一次系统决策。

## 它到底是什么

缓存是把一次调用的输入、输出和有效条件保存下来，之后用相同或等价的输入快速复用。一个可用的缓存条目至少要能回答：它为谁生成、基于哪个版本、什么时候生成、什么时候过期、能不能用于当前任务。

Agent 里常见的不是单一缓存，而是几层：模型响应缓存、工具结果缓存、检索结果缓存，以及短期运行状态。它们的失效规则不同，不能因为“字符串看起来一样”就一律复用。

## 为什么 Agent 里会用到它

Agent 很容易重复做相似工作：同一轮任务里多次查同一个文件，多个用户询问同一份稳定文档，恢复运行时重新请求已经拿到的只读结果。如果每次都重新调用，就会浪费调用额度，还可能因为远端数据变化让同一条任务前后得到互相矛盾的观察结果。

但缓存也会制造新故障：天气、库存、权限、未提交文件等动态信息过期后，旧结果会让 Agent 做出错误决定。所以缓存的核心不是“命中率越高越好”，而是把“哪些结果可以复用”写成明确规则。

## 怎么判断它有没有用

- 结果是只读的、重复请求多、变化频率低时，缓存通常值得做。
- 结果会影响付款、删除、发布或权限判断时，不能只靠缓存；执行前要重新校验关键状态。
- 缓存 key 必须包含真正影响结果的输入，例如用户、项目、查询参数、文档版本和权限范围。
- 如果无法说明过期时间、失效条件和错误复用的后果，先别加缓存，避免把旧事实伪装成新事实。

判断真实系统时，直接问三件事：命中后跳过了哪次调用？数据变化时怎么失效？命中错误时谁负责兜底？

## 一个小例子

```txt
Input:
用户说：“继续整理这份项目文档。”
系统已有 cache_key = doc:project-a:v17:summary，记录了只读摘要。

Process:
1. 检查当前文件版本仍是 v17，用户仍有读取权限。
2. 复用摘要，不再次读取和总结同一份文件。
3. 用户刚刚修改文件后，版本变成 v18，缓存失效。
4. 重新读取 v18，生成新摘要并写入新 key。

Output:
v17 时状态从 cache_lookup -> cache_hit -> planning；
v18 时状态从 cache_lookup -> cache_miss -> tool_read -> planning。
```

这里的关键是版本校验。只按“项目文档”做 key，会把旧摘要带进新任务；把版本和权限放进 key，缓存才是可解释的系统状态。

## 常见误区

1. 把缓存当长期记忆。缓存服务于复用，记忆服务于跨任务召回，生命周期和准确性要求不同。
2. 只缓存成功答案，不保存输入版本。没有版本就无法判断结果是否过期。
3. 为了命中率无限延长 TTL。动态数据宁可少命中，也不能用旧状态执行高风险动作。
4. 缓存命中后完全跳过权限校验。用户能不能看这份结果，不能由上一次请求替当前请求决定。

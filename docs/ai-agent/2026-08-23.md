# Human-in-the-loop：什么时候 Agent 必须停下来等人？

## 今天先记住

Human-in-the-loop（HITL，人类介入）不是让人替 Agent 做所有决定，而是在不可逆、代价高或责任敏感的节点，把“模型提议”变成“人确认后才能执行”。关键是定义暂停点、审批信息、超时结果和恢复位置。

## 它在大地图里的位置

::: tip 今日坐标
**权限 / 安全 → Human-in-the-loop**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

昨天讲的是“没有权限就不能执行”。今天再补一层：有些动作即使权限合法，也要在副作用发生前停住，把现场交给人判断。

## 它到底是什么

一次 HITL 流程通常是：

```txt
模型提议动作
  -> 程序评估风险
  -> 生成审批请求
  -> 等待 approve / reject / timeout
  -> 继续执行或安全取消
```

审批请求至少要包含目标、工具名、关键参数、影响范围、证据和截止时间，否则只是盲点按钮。

还要区分三个状态：`waiting_for_approval` 表示未决定，`rejected` 表示明确拒绝，`timed_out` 表示无人处理。它们不能都塞成一个“失败”。

## 为什么 Agent 里会用到它

Agent 会跨越“建议”和“现实副作用”之间的边界。生成草稿可以自动做，但发布、发消息、删数据、改权限、花钱等动作，一旦发生就可能难以撤回。

HITL 保留自动化的前半段，把责任最重的最后一步交给人。等待期间还要持久化 `run_id`、审批请求 ID、参数和 checkpoint，服务重启后才能接着等。

## 怎么判断它有没有用

- 动作不可逆、影响外部用户或涉及金钱与权限时，优先设置审批闸门。
- 风险能由稳定规则判断时，由程序拦截或放行；不要让模型自己决定“我是不是该被审批”。
- 审批人看不到参数、证据和影响范围，或拒绝、超时、重启后没有明确状态，就不是真正的 HITL。

判断真实系统时，问一句：拒绝后能否说明“哪个动作没发生、哪些前置动作已发生、下次从哪里继续”？答不上来，说明它只有按钮，没有人工闭环。

## 最近冒出来的词

今天不追新词，先把主线概念讲稳。

## 一个小例子

```txt
Input:
用户说：“把 2026-08-23 的课程发布出去。”

Process:
1. Agent 生成 Markdown，状态变为 draft_saved。
2. 检查路径和日期合法，提出 commit + push。
3. 因为 push 会产生外部可见变化，状态变为 waiting_for_approval。
4. 审批人看到文件路径、提交信息和变更摘要，选择 approve。
5. 系统从 checkpoint 继续执行；若超时，则变为 timed_out，不自动发布。

Output:
approve -> published
reject -> publish_cancelled
timeout -> publish_pending
```

人确认的是“这一次具体发布动作”，不是永久授权 Agent 发布所有文章。

## 常见误区

1. 每一步都让人确认，低风险读取也审批，会把 Agent 退化成慢速表单。
2. 不传参数和证据，人无法判断，也无法审计。
3. 审批后重新让模型生成工具调用，参数可能漂移；应恢复原 checkpoint 并校验绑定关系。
4. 把超时当批准。没有明确授权时，超时应停止或进入人工队列。

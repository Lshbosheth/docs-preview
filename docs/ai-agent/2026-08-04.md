# 运行轨迹：为什么 Agent 不能只看最终答案？

## 今天先记住

Agent 的质量不能只看最后一句话顺不顺。它会规划、调工具、改状态、重试和停止，所以你要能看见运行轨迹：每一步为什么发生、拿到了什么观察、状态怎么变、最后为什么继续或停下。

## 它在大地图里的位置

::: tip 今日坐标
**评估 / 修正 → 运行轨迹 Trace**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

昨天讲停止条件与预算，回答的是“什么时候收手”。今天再往工程现场落一层：如果你看不到轨迹，就很难判断它是正常完成、侥幸答对，还是在错误工具结果上绕了一圈。

运行轨迹主要放在评估 / 修正层，但它横向记录整条链路。目标、上下文、工具参数、观察结果、重试原因和停止理由，都应该留下可读证据。

## 它到底是什么

运行轨迹（Trace）是一条 Agent 执行流水账，但不是普通日志越多越好。它记录的是决策节点和状态变化。

一条有用的轨迹至少包含：用户目标、模型输入摘要、计划或路由选择、工具名、工具参数、工具返回、状态迁移、耗时、Token / 成本、重试与停止原因。

它的重点不是暴露模型所有思考，而是让工程人员能回答三个问题：它为什么做这一步？这一步拿到了什么证据？证据不足时它是继续、重试、降级，还是停下？

## 为什么 Agent 里会用到它

普通 Chatbot 答错了，多数时候只能改 prompt 或换模型。Agent 答错时，问题可能藏在更早的地方：检索拿错文档，工具参数少了日期，权限判断漏了一步，或者第一次失败后重试策略把错误放大了。

比如文档发布 Agent 最终说“已发布”，但线上页面没有更新。没有轨迹时，你只能猜是生成失败、git 没提交、push 失败，还是 Vercel 没部署。有轨迹时可以直接看到状态停在 `pushed_to_main`，下一步应查部署；如果停在 `commit_failed`，就不该去怀疑 CDN。

## 怎么判断它有没有用

- 如果任务包含工具调用、重试、部署、审批或跨系统状态，必须记录 Trace。
- 如果用户只问一个公开常识，完整 Trace 可以很轻；但至少要能复盘是否用了外部来源。
- 如果系统出错后只能靠聊天记录猜原因，说明轨迹不够工程化。
- 如果 Trace 里没有状态迁移和停止理由，它更像调试输出，不足以支撑排障。

## 最近冒出来的词

`Continuous voice interaction` 可以顺手记一下。OpenAI 在 2026-08-03 的工程文章里讲了实时语音系统从“轮流说话”走向连续交互。

它不是一个新的 Agent 架构名，更像实时交互里的工程问题：延迟、打断、增量输出和状态同步。和今天的主题对应：越是连续运行的系统，越不能只看最终回答；你要追踪每次输入片段、模型响应、打断和恢复，否则用户说“它反应慢”时根本无从定位。

## 一个小例子

```txt
Input:
用户说：“生成 2026-08-04 的 AI Agent Daily 并发布。”

Process:
1. goal_received: 识别日期、路径、发布规则。
2. draft_created: 生成 Markdown。
3. validation_passed: 检查 title、date、H1、敏感信息。
4. git_committed: 提交指定文件。
5. pushed_to_main: 推送远端。

Output:
published，并记录 commit hash、文件路径、URL。
```

如果第 3 步失败，Trace 应该写清 `validation_failed: frontmatter date mismatch`，状态停在本地草稿。这样接手的人一眼知道该修日期，而不是重新生成整篇。

## 常见误区

1. 把 Trace 当成“打印所有 prompt”。真正有价值的是状态、证据和决策，不是噪音。
2. 只记录成功路径。失败、重试、取消和人工接管更需要记录。
3. 只看最终答案评分。Agent 可能答案对了，但过程中越权调用了工具。
4. 没有统一 run_id。多轮工具调用散在不同日志里，排障时会断线。

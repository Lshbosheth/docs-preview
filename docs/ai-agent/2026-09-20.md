# 审批快照：人批准的是动作，不是一句“同意”

## 今天先记住

审批不是给 Agent 一张长期通行证，而是对一个具体动作、参数、资源版本和有效期的短期授权。执行器只能执行与审批快照完全匹配的动作；只要关键参数变了，原批准就失效，必须重新校验或重新审批。

前几天讲了权限边界和间接 Prompt Injection。今天再往执行口收一步：即使系统决定“要问人”，也要说清楚人到底批准了哪一次动作。审批不是安全链路的终点，它只是一张绑定具体动作的临时票据。

## 它到底是什么

审批快照（approval snapshot）是在人做决定前，把待执行动作冻结成一份可校验记录。它通常包含：

- 动作类型，例如 `push`、`send_message`、`delete_file`
- 规范化后的参数，例如仓库、分支、文件版本、收件人
- 影响范围摘要，以及不可逆或高成本的部分
- 申请人、审批人、创建时间和过期时间
- 幂等键、审批 ID 和动作哈希

人看到的摘要和机器保存的字段必须来自同一份快照。执行器不能接受一个布尔值 `approved=true` 后，再让模型重新拼参数。更稳的流程是：

```txt
proposed_action
  -> freeze_snapshot
  -> human_decision
  -> compare_snapshot
  -> execute_or_reapprove
```

这里防的是检查和执行之间的时间差（TOCTOU）。审批时文件是 A 版本，执行时却变成 B 版本；审批时收款对象是甲，恢复运行时模型又生成了乙。名称相同不代表动作相同。

## 为什么 Agent 里会用到它

传统后台的确认框通常对着固定表单：字段由页面提交，后端能直接比对。Agent 的参数来自模型，可能受新上下文、工具结果或恶意文档影响，而且审批和执行之间经常隔着等待、进程重启或人工修改。

如果只记录“用户已同意”，系统就失去了判断对象。常见故障包括：用户批准的是发布草稿，恢复后却推送了修改版；审批后 Agent 重新规划，换了一个工具；旧审批一直有效，几天后被另一条运行捡起来执行。

审批快照把“同意”从人的态度变成机器可验证的事实：谁在什么时候，对哪份内容、哪个目标、哪些参数，给出了什么决定。

## 怎么判断它有没有用

- 只要动作会发布、发送、删除、付款或改外部配置，就应保存结构化快照，而不是只保存 `approved` 状态。
- 如果人能编辑参数，任何语义字段变化都要让旧审批失效；只有大小写、空格等规范化后等价的改动，才可视为同一动作。
- 如果审批可能等待很久，快照要有有效期，并在执行前重新检查权限、资源版本和外部状态。
- 如果只是生成本地草稿或只读查询，通常不必做完整审批快照；一旦结果会对外披露或产生副作用，再升级授权流程。

判断一个真实系统，可以问：执行日志里能不能回答“这次执行对应哪次审批”？如果答案只能靠翻聊天记录，审批就没有真正进入运行状态。

## 一个小例子

```txt
Input:
用户说：“把 2026-09-20 的课程提交并推送。”

Process:
1. Agent 生成 commit 和 push 动作。
2. 系统冻结快照：
   approval_id=apr_0920
   action=git_push
   branch=main
   commit=docs(ai-agent): add daily lesson 2026-09-20
   content_hash=sha256:...
3. 用户批准后，执行器再次读取文件并计算哈希。
4. 如果 Markdown 已被修改，哈希不匹配，状态回到 awaiting_approval；只有重新批准新快照后才能推送。

Output:
匹配：approved -> executing -> pushed
不匹配：approval_invalidated -> awaiting_approval
```

这个例子里，用户批准的不是“以后都可以推送”，而是“批准这一次、这个提交、这个内容哈希的推送”。

## 常见误区

1. 把审批简化成一个布尔值，不记录被批准的动作和参数。
2. 先弹确认框，等批准后才解析最终参数，导致批准对象不完整。
3. 把一次批准当成同类动作的长期权限，忽略资源、环境和有效期。
4. 只比较工具名，不比较参数、资源版本和内容哈希，实际执行了另一个动作。

## 今天自测

1. 你的系统审批的是“一句话”还是可校验的结构化动作？
2. 审批后哪个字段变化时，必须自动撤销原批准？
3. 如果进程在批准后重启，执行器如何证明自己执行的就是那份快照？

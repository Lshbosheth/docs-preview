# Agent 评估：别只问答案像不像对

## 今天先记住

评估（Evaluation / Eval）不是给最终回复打个好坏分，而是检查 Agent 从目标到行动的整条轨迹：它有没有拿对上下文、选对工具、守住权限、在失败时停在可恢复的状态。

## 它在大地图里的位置

::: tip 今日坐标
**评估 / 修正 → Agent 评估**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

前几天讲了权限、护栏和人工接管，它们决定“能不能做”。今天的评估回答另一个问题：系统做完之后，我们怎么知道它不是碰巧做对一次，而是下次还能稳定地按规则做。

## 它到底是什么

Agent 评估是把一次运行拆成可检查证据。最少要看四层：

```txt
输入是否被理解
上下文和记忆是否取对
工具调用和状态迁移是否合理
最终输出是否满足目标
```

普通 Chatbot 评估常常只看答案文本；Agent 不行。因为 Agent 会调工具、写文件、发消息、改状态。最后一句话写得顺，不代表中间没有读错资料、越权调用、重复执行或吞掉错误。

## 为什么 Agent 里会用到它

Agent 的失败经常藏在过程里。比如它最后说“已发布”，但实际只生成了文件，没有提交；或者它回答“没有敏感信息”，但审计轨迹显示它根本没检查文件内容。

所以评估要覆盖轨迹，而不是只看结尾。一个能上线的 Agent，应该能回答：这次用了哪些输入？取了哪些记忆？调用了哪些工具？失败在哪里发生？如果重跑，会不会重复执行副作用动作？

## 怎么判断它有没有用

- 如果任务会调用工具、写状态或影响外部系统，评估必须看 trace（运行轨迹），不能只看最终文本。
- 如果你经常靠人工翻聊天记录判断“它刚才为什么这么做”，说明评估和可观测性还没建起来。
- 如果一次失败没有留下输入、参数、工具结果和状态变化，就很难变成测试用例。
- 如果只是闲聊问答，不涉及工具和状态，轻量人工抽查可能够用；不要为了形式把每句话都做复杂评测。

## 最近冒出来的词

最近可以留意 LangSmith trace 里的 “Gateway outcomes / policy limits / fallback attempts”。LangSmith Cloud changelog 在 2026-08-17 至 2026-08-24 更新里提到，trace 详情会展示 LLM Gateway 的结果、策略限制、所选模型和 fallback 尝试，被 Gateway 阻断的运行也会在 trace 树里显示。

这不是新理论，更像评估和可观测性的工程化补强：当 Agent 选模型、被策略拦截或走 fallback 时，这些都应该进入可检查轨迹。它和今天的主题正好对应：评估不只是“答案对不对”，还要看运行过程中每个关键决策有没有证据。

来源提示：[LangSmith Cloud changelog](https://docs.langchain.com/langsmith/changelog)，2026-08-17 至 2026-08-24。

## 一个小例子

```txt
Input:
用户要求：“生成今天的 AI Agent Daily，并发布到文档站。”

Process:
1. 系统读取课程框架和已有文章列表
2. 判断今天主题不能重复，选择“Agent 评估”
3. 生成 Markdown，并检查 frontmatter date、文件名、H1 是否一致
4. git add 只加入当天文章
5. commit 和 push 成功后，记录提交结果

Output:
文件状态从不存在变成已发布；
评估证据包括：读取过的框架路径、生成文件路径、提交文件列表、commit message、push 结果。
```

这条链路里，最终页面能打开只是一个结果。真正可评估的是：它有没有按范围提交，有没有把无关文件带进去，有没有在发现敏感内容时停止发布。

## 常见误区

1. 只看最终答案，不看工具参数和状态变化。
2. 把“用户满意”当作唯一指标。满意很重要，但不能替代权限、事实、成本和可恢复性检查。
3. 只评估成功样本，不故意注入超时、坏 JSON、重复消息和权限拒绝。
4. 没有把失败案例沉淀成回归测试，导致同一种错反复出现。

# 准入控制与背压：Agent 并发太高时，为什么不能先排队再说？

## 今天先记住

准入控制（admission control）决定一个请求现在能不能开始，背压（backpressure）则把下游已经变慢的事实传回上游，让上游减速、延后或拒绝。队列只是缓冲，不是背压；没有截止时间、容量上限和取消规则的无界排队，只是把马上失败改写成过一会儿更难解释的失败。

预算预占解决“这次最多能用多少”，准入控制接着回答“现在有没有资格占用这些额度”。它会出现在会话入口、模型调用、工具执行和发布动作前，因此不能只在某一个 HTTP 客户端里做限流。

## 它到底是什么

一个可执行的准入策略至少要声明四件事：在途任务上限、每类任务的配额、可等待的最晚时间，以及队列满时的动作。动作通常分成四种：

- `accept`：当前容量足够，立即进入执行。
- `defer`：延迟到明确时间重试，且原 deadline 仍然有效。
- `coalesce`：同一幂等键的重复请求合并到已有运行。
- `reject`：快速失败，并告诉调用方稍后再来。

核心判断不是“队列里还能不能塞下”，而是“这个任务在截止时间前还值不值得做”。一个五分钟前请求的实时问答，和一小时后执行的批量摘要，同样排在三分钟队里，结果完全不同。前者即使最终成功，也已经失去价值。

## 为什么 Agent 里会用到它

Agent 的负载不均匀：一次规划可能突发调用多个模型，一个搜索步骤可能拖住后续工具，发布和付款又必须串行占用有限的外部资源。若入口无条件接收所有任务，后面的队列会越长；调用方等不到响应又重试，重复任务进一步放大流量。

更隐蔽的问题是状态过期。任务排队时，用户可能已经撤回请求、切换会话或修改目标。恢复执行前若不检查版本和取消信号，旧任务会把基于旧上下文的结果写回新会话。因此，准入记录至少应与 `run_id`、幂等键、优先级、`deadline_at`、版本和取消信号绑定。

## 怎么判断它有没有用

- 只要任务会访问共享模型、外部工具、付费配额或单一写槽，就应在执行前做准入；并发越高，越不能只依赖本地重试。
- 交互请求优先保低延迟，可以快速拒绝或降级为只读；批量任务优先保吞吐，可以延后，但必须带绝对截止时间。
- 队列长度和等待时间必须可见。只记录“当前排队 500 个”不够，还要能回答最老任务的年龄、预计可执行时间，以及有多少任务已因过期而无效。
- 对写操作，重复请求应优先 `coalesce`，不能既排队又再次提交；对读操作，过期结果通常直接丢弃，不应占用并行槽继续生成。

## 一个小例子

```txt
Input:
微信桥在同一分钟内收到两条完全相同的“生成课程”消息，
以及一条新的“查询课程是否已发布”请求。系统只剩 1 个模型槽和 1 个写入槽。

Process:
1. 两条重复消息共享 idempotency_key，第二条被 coalesce 到已有 run，不再创建模型调用。
2. 查询被识别为低成本的只读任务，先占用模型槽。
3. 发布请求申请写入槽；当前槽忙，进入 defer，deadline_at 保持原值。
4. defer 到期前，调用方完成查询并取消发布请求；系统按 run_id 传播取消，不再申请写入槽。

Output:
duplicate -> coalesced
query -> accepted -> completed
publish -> deferred -> cancelled

没有第二次模型生成，也没有排队后突然 push。
```

## 常见误区

1. 把 Queue 当背压，只扩大队列容量，不向上游返回拥塞信号，导致延迟和内存持续增长。
2. 所有任务共用一个优先级，交互请求被批量任务堵住，最后大量结果都在 deadline 之后才产生。
3. 只限制入口 QPS，不限制在途数量；慢工具仍会堆积，并在超时后同时重试。
4. 重复请求直接再次执行，既绕开幂等，也浪费刚刚预占的模型、工具和写入额度。

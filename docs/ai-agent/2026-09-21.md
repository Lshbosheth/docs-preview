# 审计轨迹：Agent 说“done”之后，系统怎么证明？

## 今天先记住

审计轨迹不是把聊天内容和工具输出统统存下来，而是让每个关键状态变化都能回答：谁发起、基于什么输入、哪个策略做了决定、执行了什么、结果有没有被确认。只有最终文字说 `done`，还不足以证明动作真的发生且只发生了一次。

## 它在大地图里的位置

::: tip 今日坐标
**执行 / 观察结果 → ▶ 审计轨迹**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> ▶ 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

前几天讲了权限边界、Prompt Injection 和审批快照。审计轨迹接在它们后面，负责把“谁被允许做、实际做了什么、最终是否生效”连成证据链。它既服务事后排查，也决定系统能否安全恢复。

## 它到底是什么

运行日志偏向记录程序发生了什么，Trace 偏向记录一次调用的层级和耗时，审计轨迹（audit trail）更关注有业务意义的状态变化。一次 Agent run 至少要能沿 `run_id` 找到：

- 原始目标和触发者，以及对应的 `user_id / thread_id`
- 模型提出的动作、策略判断和使用的审批 ID
- 规范化参数、资源版本、内容哈希和幂等键
- 工具返回的终态：成功、失败、超时、拒绝或未知
- 重试、补偿、人工接管及最终输出之间的因果顺序

事件应当追加写入，不能只保留最后一版状态。否则并发重试或进程重启后，系统只剩一个“结果”，无法知道中间是否重复发送、越过审批或修改了别人的资源。

## 为什么 Agent 里会用到它

普通后端流程通常由固定代码决定下一步，故障点相对稳定。Agent 会依据模型输出和外部工具结果继续规划，同一份输入也可能走到不同路径；一次推送超时后，远端可能已经成功，但本地只看到错误。

这时审计轨迹要连接模型决策和真实副作用。它不是给模型更长的记忆，而是给系统一份不可靠叙述之外的证据。客服、安全、运维和开发者看到的应该是同一组事件，而不是各自从聊天记录里猜。

## 怎么判断它有没有用

- 只要动作会发送、发布、删除、付款或改外部配置，就应有审计事件；纯本地只读总结可以只保留普通 Trace。
- 拿一次失败运行做检查：能否指出参数是什么、策略为何放行、是否重试、重复请求是否被幂等键吸收？答不出来，就还没有完整链路。
- 审计记录要保存安全引用或哈希，不应直接堆入 Token、密码、完整私聊和敏感文档正文；可读性与最小化要同时满足。
- 执行器必须记录远端确认，而不是把模型生成的“已完成”当结果。恢复时也应读取事件，而不是重新询问模型刚才做了什么。

## 一个小例子

```txt
Input:
用户说：“生成今天的课程，检查通过后提交并推送。”

Process:
1. 系统记录 run_started、document_generated 和 scan_passed。
2. commit 事件写入提交哈希、文件版本和审批 ID。
3. push 第一次调用超时，状态记录为 outcome_unknown，并保留同一个 idempotency_key。
4. 重试后远端返回 already_exists 和 remote_sha，执行器把它确认为第一次动作已生效。

Output:
最后不是简单写 “push success”，而是形成
planned -> approved -> outcome_unknown -> confirmed -> completed
的状态链，并证明没有生成第二次重复推送。
```

## 常见误区

1. 把调试日志当审计轨迹，能看见报错却回答不了“哪次审批允许了这次动作”。
2. 只记录工具名，不记录规范化参数、资源版本和幂等键，无法判断是否执行了另一个动作。
3. 为了可追溯把所有原始内容长期保存，反而引入凭据和隐私泄露风险。
4. 只写“成功”结论，不记录超时、重试和远端确认，恢复时容易重复产生副作用。

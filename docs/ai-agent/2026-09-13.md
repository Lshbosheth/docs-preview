# Agent 可观测性：没有 Trace，就没有排障入口

## 今天先记住

日志回答“程序写过什么”，Trace（追踪）回答“一次 Agent 运行从目标到结果，经过了哪些步骤”。没有 `run_id`、步骤、输入输出和状态变化，失败只能靠猜；而 Agent 最难查的，往往不是模型没回答，而是工具选错、重试重复、状态没落盘。

## 它在大地图里的位置

::: tip 今日坐标
**评估、可观测性与可靠性 → ▶ Trace / 可观测性**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

Trace 横跨这条闭环，把每个节点串成一次可回放的运行记录。昨天我们算成本和延迟，今天要回答：这笔成本到底花在哪一步，哪个状态把结果带偏了。

## 它到底是什么

可观测性至少要留下三类证据：

- **Trace**：一次完整运行，例如 `run_id=abc123`，包含开始、结束和最终状态。
- **Span**：运行中的一步，例如模型调用、工具调用、检索、重试或人工审批。
- **事件与属性**：每一步的时间、名称、输入摘要、输出摘要、错误、Token、耗时和关联的 `thread_id`。

不要默认记录所有原文。敏感内容应脱敏或只存摘要，但不能丢掉能定位问题的结构化字段：工具名、参数校验结果、返回码、重试次数和状态转移。

## 为什么 Agent 里会用到它

普通接口常能用一条请求日志定位问题；Agent 一次运行可能有多次模型调用、并行工具、条件分支和恢复。最终只显示“发布失败”，并不能说明是日期校验失败、Git 超时，还是模型在失败后重复提交。

因此 Trace 不只是监控面板上的曲线，而是评估、重试和人工接管的共同证据。评测要回放它，排障要筛选它，人工审批要知道它在批准前做过什么。

## 怎么判断它有没有用

- 看到一个失败 `run_id`，能否沿着 Trace 找到第一个错误步骤，而不是只看到最后一句报错？
- 每个外部副作用是否都有工具名、幂等键、调用结果和前置状态？没有这些字段，重复发送很难证明责任边界。
- 记录能否区分“模型输出坏了”“工具返回错了”“状态写入失败”和“超时后正在恢复”？如果不能，字段还不够。
- 只读链路可以保留更细的输入输出；写入、删除、发布链路应优先保留审计字段，并对原文做最小化记录。

## 一个小例子

```txt
Input:
用户说：“检查文档，合规就提交并推送。”

Process:
run_id=r42
1. span=scan_files：发现敏感信息，结果 blocked
2. 状态从 checking -> publish_blocked
3. 因硬断言失败，不创建 commit，不调用 push

Output:
页面显示“因敏感信息扫描失败，未发布”；Trace 能证明 push 根本没有发生。
```

如果用户说“明明没发布，为什么日志显示调用过 Git”，先查 Trace 中的工具参数、返回码和状态转移，而不是先怪模型。真实系统至少应能回答：谁在什么时候以什么参数调用了什么工具，副作用是否成功。

## 常见误区

1. 只有一条最终错误日志，没有步骤级 Trace，无法定位第一个失败点。
2. 为了调试把所有消息原文和密钥写进日志，排障证据变成新的泄露面。
3. 把一次重试当成新运行，导致成本、重复副作用和成功率统计失真。
4. 只看延迟和错误率，不关联模型版本、工具版本、提示词版本与状态版本。

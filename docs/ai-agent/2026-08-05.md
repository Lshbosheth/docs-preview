# 失败恢复：Agent 出错后应该怎么退回来？

## 今天先记住

Agent 不是“别出错”才可靠，而是出错后能停在可理解的位置：知道哪一步失败、哪些动作已经生效、能不能重试、要不要回滚、什么时候交给人。

## 它在大地图里的位置

::: tip 今日坐标
**评估 / 修正 → 失败恢复 Failure Recovery**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

前面讲运行轨迹，是让你看见 Agent 做过什么。今天接着问一个更工程化的问题：看见失败以后，系统应该怎么处理？

失败恢复主要在评估 / 修正层，但它会反过来要求工具、状态和权限都设计得更清楚。否则 Agent 只能嘴上说“我重试一下”，实际可能把同一封邮件发两遍、把同一篇文章提交两次，或者在错误状态上继续往下跑。

## 它到底是什么

失败恢复（Failure Recovery）是一组规则：当某一步没有按预期完成时，系统如何选择重试、降级、回滚、暂停、人工确认或终止。

这里的“失败”不只是程序抛异常。工具超时、返回空结果、参数缺字段、外部系统部分成功、模型输出了不合 schema 的 JSON、用户中途改目标，都算失败或异常状态。

真正有用的恢复策略会先问三件事：这一步有没有副作用？当前状态能不能被准确识别？再次执行会不会造成重复伤害？

## 为什么 Agent 里会用到它

普通脚本失败了，大多停下来报错。Agent 更麻烦：它可能自己决定下一步，也可能跨多个外部系统执行动作。一个搜索工具失败，重试通常没问题；一个支付、删除、发送、发布工具失败，就不能盲目重试。

比如文档发布 Agent 在 `git push` 时网络断了。它不能立刻重新生成一篇新文档，因为本地文件和 commit 可能已经存在。正确做法是先读取当前状态：文件是否已保存、commit 是否已创建、远端是否已有这个 commit。只有确认停在哪一层，才能决定继续 push、补 commit，还是停止等人工处理。

## 怎么判断它有没有用

- 如果工具有副作用，比如写库、发消息、提交代码、创建订单，必须设计恢复策略。
- 如果失败后“再跑一次”会生成重复结果，就要加幂等键、状态检查或人工确认。
- 如果任务只是一次只读查询，恢复可以简单到超时重试一次，然后给出失败原因。
- 如果 Trace 里看不出失败前最后一个稳定状态，说明恢复策略还没真正落地。

## 一个小例子

```txt
Input:
系统要发布 docs/ai-agent/2026-08-05.md，执行到 git push 时超时。

Process:
1. 检查文件是否存在，确认 frontmatter date 是 2026-08-05。
2. 检查 git log，确认 commit 是否已经创建。
3. 检查远端 main 是否已有该 commit。
4. 如果远端没有，只重试 push；如果远端已有，标记 published。

Output:
状态从 push_timeout 变成 pushed_to_main，或停在 needs_human_check，并附上最后稳定状态。
```

这个例子里的关键不是“多重试几次”，而是每次重试前先判断副作用有没有发生。否则系统可能会重新生成内容、产生第二个 commit，最后让排障变得更乱。

## 常见误区

1. 把恢复等同于重试。重试只是一个动作，不是完整策略。
2. 所有工具都用同一套重试次数。只读查询和写入操作的风险完全不同。
3. 没有幂等设计。用户说一次，系统失败后跑两次，外部世界却被改了两遍。
4. 忽略部分成功。外部接口返回失败，不代表它什么都没做。

## 今天自测

1. 为什么有副作用的工具不能盲目自动重试？
2. 失败恢复前，系统至少要确认哪两个状态？
3. “执行成功”和“用户目标达成”为什么不是同一件事？

# 取消与截止时间：Agent 怎么把停止意图传到底？

## 今天先记住

截止时间（deadline）决定最晚何时必须结束，取消（cancellation）决定谁来中止正在做的事。它们不是一句“请停止”的提示词，而是要沿着模型调用、工具调用和并行分支传递的运行时信号；如果外部动作已经发出，取消只能停止等待，不能假装副作用也被撤销。


昨天讲降级模式，是在回退后限制 Agent 还能做什么。今天再补一层：即使已经决定不再继续，当前模型流、搜索请求和并行工具也要真正收束，不能让任务在后台继续烧预算或产生迟到副作用。

## 它到底是什么

**截止时间**是一条绝对时间边界，例如 `deadline_at=18:30:00`。子步骤拿到的不应是新的“再等 30 秒”，而应是父任务剩余的时间；否则每一层都重置超时，最外层预算会被悄悄放大。

**取消**是一种协作式控制信号。模型流、HTTP 请求、工具执行器和并行分支都要在可控位置检查它。程序收到 `cancel_requested` 后，通常先停止创建新任务，再向未完成分支传播信号，等待它们结束或进入明确的未知状态。

取消不是“失败”的同义词。完整状态至少应区分：

```txt
running -> cancel_requested -> cancelled
                           -> outcome_unknown
                           -> completed_but_superseded
```

## 为什么 Agent 里会用到它

用户可能在结果返回前发送新问题，审批可能超时，调用方也可能只在页面上停留几十秒。若旧任务没有取消契约，它会继续检索、生成摘要、重试网络请求，甚至在界面显示“已停止”后完成提交或发送消息。

Agent 还常把工作拆成并行分支。一个搜索分支超时，不代表另外两个写操作也能安全强杀。系统必须知道哪个分支可以丢弃、哪个分支已经产生副作用、哪个结果即使迟到也不能再写回当前会话。

## 怎么判断它有没有用

- 只要任务包含多层模型调用、流式输出、外部工具或并行分支，就应向下传同一个 deadline，并为每层记录剩余预算。
- 读操作可以尽量取消并丢弃结果；写操作一旦发出，取消后应进入 `outcome_unknown`，通过幂等键或远端状态对账，而不是直接宣称“已回滚”。
- 如果只是本地、毫秒级的纯计算，进程退出往往已经足够，不必为了术语完整而搭一套复杂信号系统。
- 一个真实系统应能回答：谁发起取消、信号传到哪些分支、是否还有在途调用、迟到结果如何处理、副作用最终是什么状态。只能把按钮变灰，不算实现取消。

## 最近冒出来的词

Google ADK Python `v2.10.0` 在 2026-09-24 加入评估指标，用来跟踪运行时长、Token 消耗和模型调用次数。这不是新的 Agent 架构，而是一组效率观测数据。它和今天的主线相连：没有按 run 与步骤记录的耗时，就很难发现某个子调用已经越过 deadline，也更难证明取消之后没有继续偷偷调用模型。

来源提示：Google ADK GitHub Release，2026-09-24。

## 一个小例子

```txt
Input:
用户要求生成课程并发布，同时规定本次运行 deadline_at=09:35。

Process:
1. 草稿生成和敏感信息扫描均检查剩余预算。
2. 09:35 前 push 请求已发出，但响应尚未返回，上层发起取消。
3. runtime 不重跑整条课程，也不用新超时继续等待；它把 run 标记为 outcome_unknown。
4. 系统用 commit_sha 和幂等键查询远端：确认已推送则记为 published_confirmed；查询不到则停在 publish_pending，等待继续对账。

Output:
没有第二次 push。若 push 尚未发出，则进入 cancelled，保留本地文件和 commit；若已发出，则必须给出可核验的远端状态。
```

## 常见误区

1. 把“请立即停止”写进 Prompt 就当成取消，模型仍可能继续生成下一次工具调用。
2. 每层重新设置完整超时，导致总运行时间随着调用链不断延长。
3. 收到取消就认为外部动作没有发生，忽略已发出的写请求和迟到响应。
4. 用户已经切到新任务，旧任务的结果仍能回写当前会话，造成上下文串线。

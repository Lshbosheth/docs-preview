# 断点续跑：Agent 为什么不能只靠一次性对话？

## 今天先记住

Agent 一旦要做多步任务，就不能假设“这一轮模型调用会顺利跑完”。断点续跑（Checkpoint / Resume）要解决的是：中途失败、等待确认、服务重启之后，系统知道自己停在哪、哪些动作已经发生、下一步能不能继续。

## 它在大地图里的位置

::: tip 今日坐标
**上下文 / 记忆 → 断点续跑**
:::

```txt
用户目标
  -> ▶ 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

断点续跑不是“把聊天记录存起来”这么简单。它站在上下文、执行状态和审计记录中间：让 Agent 重新启动时，不是重新猜一遍任务，而是从可信状态继续。

## 它到底是什么

一次 Checkpoint 至少要保存三类东西：

```txt
目标：用户要完成什么
状态：当前步骤、已完成动作、待确认动作
证据：工具结果、错误原因、审批记录、下一步候选
```

它和长期记忆不同。长期记忆记录“用户长期偏好”；断点记录的是“这一次任务运行到哪了”。比如发布文档时，记住用户喜欢短文是长期记忆；记住 Markdown 已生成、敏感扫描已通过、git commit 还没 push，是断点状态。

## 为什么 Agent 里会用到它

普通 Chatbot 多半是问一句答一句，失败了重问也行。Agent 会把一次目标拆成搜索、写文件、调用 API、等待人工确认、发布结果等多个动作。只要中途断电、工具超时、用户暂时没批准，系统就必须知道哪些动作不能重复，哪些动作可以补做。

没有断点时，最常见的故障不是“答错”，而是重复执行：同一封邮件发两遍、同一条提醒创建两次、同一个文档提交两次。断点续跑的核心价值，是让恢复动作有边界。

## 怎么判断它有没有用

- 如果任务跨多轮对话、多人审批或后台队列，断点续跑是必需品。
- 如果工具有副作用，断点里必须记录动作是否已经执行，不能只记录模型想做什么。
- 如果所有步骤都能安全重跑，简单重试就够了；如果有一步不能重复，就要保存幂等键和状态。
- 如果服务重启后只能让用户“再说一遍需求”，说明你保存的是聊天，不是运行状态。

## 最近冒出来的词

Microsoft Agent Framework 文档最近更新了 “Harness Agent” 这个说法。它不是新的基础理论，更像是把长任务所需的规划、待办、上下文压缩、文件访问、记忆、工具审批和可观测性打包成一个运行壳。和今天的主题关系很近：一旦框架开始强调 long-running tasks，就必须处理状态保存、人工等待和恢复边界。

来源提示：Microsoft Learn，Microsoft Agent Framework Overview，2026-08-25。

## 一个小例子

```txt
Input:
用户说：“生成今天的 AI Agent Daily，发布到文档站。”

Process:
1. checkpoint_1: topic_selected，记录主题和日期。
2. checkpoint_2: markdown_written，记录文件路径和内容 hash。
3. checkpoint_3: secret_scan_passed，允许进入 commit。
4. git push 失败，状态停在 push_failed，记录 commit id。

Output:
下次恢复时，系统不重新生成文章，也不重复 commit；
它只检查当前分支和 commit id，然后继续执行 git push。
```

判断真实系统时，可以问一句：**如果执行器在最后一步挂了，它会从头再做一遍，还是能证明前面哪些步骤已经完成？**

## 常见误区

1. 把完整 Prompt 当断点；Prompt 能帮助重建语境，但不能证明工具动作是否已经发生。
2. 只保存成功结果，不保存 waiting_for_approval、failed、blocked 这些中间状态。
3. 断点里没有版本号和幂等键，恢复时无法判断旧状态还能不能继续用。
4. 把长期记忆和任务断点混在一起，导致一次任务的临时状态污染后续对话。

# Checkpoint：Agent 为什么要留下可恢复的断点？

## 今天先记住

Checkpoint 不是“多存一份日志”。它保存的是一次 Agent 运行在关键时刻的可恢复状态：目标、上下文、已完成步骤、工具结果、下一步该做什么。

## 它在大地图里的位置

::: tip 今日坐标
**上下文 / 记忆 → Checkpoint**
:::

```txt
用户目标
  -> ▶ 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

昨天讲会话隔离，是先把“这是谁的、哪条线程的、哪次运行的”分清。今天往下一层：分清之后，系统还要知道运行到哪了。

Checkpoint 就像 Agent Loop 里的路标。没有它，服务重启、工具超时、人工审批暂停之后，系统只能靠聊天记录猜；有它，系统可以从明确状态继续，而不是从头乱跑一遍。

## 它到底是什么

Checkpoint 是在关键节点保存的一份结构化状态快照。

它通常包含：`run_id`、当前目标、短期状态、已调用工具及结果、待执行步骤、审批状态、错误信息、时间戳。

日志回答“发生过什么”；checkpoint 回答“现在能不能继续、该从哪里继续、哪些动作不能重复做”。

所以它不一定每一步都存。更常见的做法是在状态变化、外部副作用、人工等待、长任务分段完成时保存。

## 为什么 Agent 里会用到它

Agent 经常不是一次模型调用就结束。它可能先读文件，再规划，再调用工具，再根据观察结果改计划，最后提交或发送。

如果中间断了，最危险的不是“任务失败”，而是“恢复时重复执行副作用”。比如已经发过消息，恢复后又发一次；已经提交过文件，恢复后又生成一份冲突内容。

Checkpoint 把恢复变成工程问题：先读状态，判断最后一个稳定点，再决定继续、重试、回滚，还是交给人。

## 怎么判断它有没有用

- 如果任务超过一个工具调用，且中间结果会影响下一步，就该考虑 checkpoint。
- 如果动作有副作用，比如写文件、发消息、提交代码、改配置，动作完成后必须记录状态。
- 如果任务可能暂停等待人工确认，checkpoint 要记录“等谁确认、确认什么、确认后从哪一步继续”。
- 如果任务只是一次纯问答、无工具、无副作用，checkpoint 通常是过度设计。

## 一个小例子

```txt
Input:
用户说：“生成并发布 2026-08-11 的 AI Agent Daily。”

Process:
1. 创建 run_id = ai_daily_20260811。
2. 写入 checkpoint：目标日期、目标路径、禁止构建、需要 git push。
3. 生成 Markdown 后写入 checkpoint：file_written = true。
4. commit 成功后写入 checkpoint：commit_sha = xxx。
5. push 成功后写入 checkpoint：state = pushed。

Output:
如果第 4 步后网络断了，恢复时只需要重新 push。
系统不会重新生成文章，也不会把已经 commit 的内容再提交一次。
```

这个例子里，checkpoint 的价值不在“记得更全”，而在恢复时能做出具体判断：继续 push、重新 commit，还是停下来检查异常。

## 常见误区

1. 把 checkpoint 当完整聊天记录。它应该存可恢复状态，不是把所有文本都塞进去。
2. 只在失败时才存。失败后才想起来保存，通常已经不知道哪一步真的成功了。
3. 不记录外部副作用。工具返回成功但状态没落库，恢复时最容易重复执行。
4. 认为 checkpoint 可以替代幂等。它能帮助恢复，但外部动作本身仍要尽量可去重、可校验。

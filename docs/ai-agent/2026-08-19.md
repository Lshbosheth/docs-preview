# 可观测性：Agent 出错时，为什么不能只看最后一句话？

## 今天先记住

Agent 的可观测性（Observability）不是多打几行日志，而是让一次运行的目标、决策、工具调用、状态变化、耗时、成本和最终结果能够被串起来解释。最后一句话只是结果，真正决定系统是否可排障的是中间轨迹。

## 它在大地图里的位置

::: tip 今日坐标
**执行 / 观察结果 → 可观测性**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> ▶ 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

前几天讲成本与延迟，回答“这次 run 花了多少”；今天继续追问“时间和错误究竟花在哪里”。可观测性把整条链路变成一条可回放的证据链，帮助你判断是模型选错工具、工具返回坏数据、状态没有保存，还是重试把任务推向了死循环。

## 它到底是什么

一次 Agent run 至少要有一个统一的 `run_id`，并把模型调用、工具调用、状态转移和最终输出挂在它下面。每个步骤最好记录：

- 输入摘要和结构化参数，而不是把所有敏感正文无差别写进日志；
- 开始时间、结束时间、状态、错误类型和重试次数；
- 使用的模型、Token / 成本、工具名称与结果大小；
- 当前节点、父步骤和下一步决定。

可以把它理解成“运行轨迹（trace）+ 指标（metrics）+ 事件日志（logs）”。指标适合发现“最近都变慢了”，轨迹适合回答“这一单为什么变慢”，日志适合查看具体错误和状态变化。三者不能互相替代。

## 为什么 Agent 里会用到它

普通 Chatbot 一次生成失败，常常只需重试。Agent 失败可能发生在第七步：前六步已经写文件、发请求或改变状态，最后模型才因为一个工具结果误判而输出错误结论。如果只保存最终文本，你看不出哪一步把系统带偏，也无法判断是否能从 checkpoint 恢复。

所以可观测性不是为了“监控好看”，而是为了把排障问题从猜测变成定位。一个合格的 trace 应该能回答：目标是什么？走了哪些节点？哪个工具返回了什么状态？为什么下一步继续或停止？最终输出是否与执行证据一致？

## 怎么判断它有没有用

- 如果一次任务包含两个以上模型或工具步骤，就应有统一 `run_id` 和父子步骤关系。
- 如果只能看到“失败”，看不到失败前最后一个成功状态，系统就不具备可恢复的观测基础。
- 如果日志里只有自然语言，没有结构化的工具名、耗时、状态和错误码，后续很难统计和聚合。
- 如果记录了用户隐私、Token 或工具参数，必须先做脱敏、权限隔离和保留期限设计。

判断真实系统时，拿一条失败 run 反问四件事：能否在一分钟内找到慢步骤？能否重建模型实际看见的工具结果？能否区分模型坏输出和工具真实报错？能否从某个 checkpoint 继续，而不是整单重跑？

## 一个小例子

```txt
Input:
用户说：“把今天的课程写好并发布。”

Process:
run_id = daily-2026-08-19
1. trace 记录：读取框架，耗时 120ms。
2. trace 记录：读取上一课，耗时 80ms。
3. 模型决定只查一个近期词；检索无可靠结果，状态变为 skip_recent_term。
4. Markdown 写入成功，状态变为 draft_saved。
5. git commit 成功，push 返回超时。

Output:
最终状态：commit_created / publish_pending。
排障结论：文章生成没有失败，阻塞点是远端 push；恢复时从
publish_pending 继续，不重新调用模型生成全文。
```

## 常见误区

1. 只保存最终答案，丢掉中间工具和状态，导致任何故障都只能猜。
2. 把完整用户内容全部写日志，排障方便了，却制造了新的泄露面。
3. 只做平均耗时监控。平均值正常，不代表某类工具或某个用户的长尾没有爆掉。
4. 把 trace 当审计记录。可观测性回答“系统怎么运行”，审计还要回答“谁在什么权限下批准并执行了什么”。

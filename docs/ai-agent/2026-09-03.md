# 失败恢复：Agent 出错后怎么继续

## 今天先记住

Agent 的失败恢复，不是把整条流程从头再跑一遍，而是先判断失败发生在哪个状态、动作有没有副作用、从哪里继续才不会重复做错事。

昨天的可观测性解决“发生了什么、坏在哪里”；今天继续往后问：知道坏点以后，系统是重试、降级、暂停，还是交给人处理？失败恢复连接执行层和评估层，目标是让一次故障变成可控的状态转移，而不是让模型盲目重跑。

## 它到底是什么

失败恢复（Failure Recovery）是一组针对异常状态的处理规则。常见动作有：重试、退避、切换备用工具、部分成功、回滚、人工接管和安全终止。

关键是先区分失败类型：

- **瞬时失败**：网络抖动、限流、临时超时，适合有限次数重试。
- **确定失败**：参数校验不通过、权限不足、资源不存在，重试通常没有意义。
- **未知结果**：请求超时，但外部系统可能已经执行成功，不能直接重复提交。
- **副作用失败**：已经发消息、写文件或发布了一部分，恢复前要先确认当前状态。

因此，恢复流程通常要保存 checkpoint：当前步骤、输入版本、工具调用 id、外部结果和是否已产生副作用。

## 为什么 Agent 里会用到它

Agent 会自主选择工具并循环执行，失败不只发生在模型调用，还可能发生在工具、网络、权限和状态持久化。没有恢复规则时，模型往往把“未知结果”误判成“没执行”，于是重复发消息、重复创建订单，或者在同一个坏计划上越走越远。

工程上要把“是否能重试”从模型自由发挥里拿出来。模型可以提出下一步，但程序应依据错误类型、幂等性和风险等级决定是否真的执行。

## 怎么判断它有没有用

- 失败后是否能定位到一个明确步骤，而不是只返回“任务失败”？
- 这个动作是否幂等？同一个 `idempotency_key` 重放，结果是否仍只有一次？
- 超时后是否能查询外部系统确认结果？不能确认时，是否会暂停而非重复执行？
- 是否设有最大重试次数、指数退避和总预算？超过预算后是否安全终止？

判断真实系统时，可以拿“发送一条消息”做测试：模拟请求超时但服务端已收到，系统最终应只出现一条消息，并留下“结果未知、等待确认”的轨迹。做不到这一点，重试只是把故障放大。

## 一个小例子

```txt
Input:
用户说：“把今天的 AI Agent Daily 发布到线上。”

Process:
1. 写入文件并记录内容哈希
2. commit 成功，push 返回超时
3. 系统不立即再次 push，先查询远端是否已有该 commit
4. 已存在则进入 published；不存在才按相同 commit id 重试一次
5. 仍无法确认时进入 delivery_unknown，等待人工检查

Output:
远端有提交：状态变为 `published`
远端无提交且重试成功：状态变为 `published`
结果仍未知：不重复发布，保留 checkpoint 和告警入口
```

这里的恢复不是“再来一次”，而是先把状态从 `push_timeout` 变成“已确认 / 未确认”，再决定动作。这个顺序也适用于微信投递、支付、任务创建等外部副作用。

## 常见误区

1. 所有错误都重试，导致参数错误和权限错误被重复撞击。
2. 超时就当成未执行，忽略外部系统可能已经成功。
3. 只设置重试次数，不设置总耗时、成本和副作用边界。
4. 恢复时重新让模型规划整条任务，丢掉已经完成的状态。

## 今天自测

1. “超时但结果未知”和“参数校验失败”为什么不能同样重试？
2. 一个会产生副作用的工具，至少需要记录哪些恢复信息？
3. 你负责的系统里，哪一步失败后应该暂停并交给人，而不是继续自动执行？

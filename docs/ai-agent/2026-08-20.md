# 失败恢复：Agent 为什么要记住断点，而不是只记住结果？

## 今天先记住

Agent 不是只要“最后答对”就算完成。它真正要保住的是：任务做到哪一步、失败发生在哪一层、恢复时该从哪里继续，而不是整条链路重跑一遍。

## 它在大地图里的位置

::: tip 今日坐标
**执行 / 观察结果 → 失败恢复**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> ▶ 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

前一篇讲可观测性，是为了看清“坏在什么地方”；今天讲失败恢复，是为了决定“坏了以后怎么接着做”。

它卡在执行层和评估层之间：一旦工具超时、模型输出偏了、网络断了、权限被拒了，系统不能只留一句失败提示，而要留下可恢复的状态。

## 它到底是什么

失败恢复（failure recovery）不是重试按钮。它至少要保存三样东西：当前步骤、已完成副作用、下一步条件。

如果任务是“写文档并发布”，失败恢复要知道是“已写完但没 push”，还是“已 push 但站点未构建”。这两种恢复动作完全不同。

所以真正有用的不是“任务成功 / 任务失败”二元状态，而是带语义的中间态：`draft_saved`、`commit_created`、`publish_pending`、`needs_human_review`。

## 为什么 Agent 里会用到它

Agent 会跨工具、跨模型、跨外部系统工作，天然比普通 Chatbot 更容易卡在半路。普通对话失败了，大不了再问一次；Agent 失败时，前面可能已经写文件、发消息、改数据库，不能当作没发生。

所以恢复能力决定了系统是不是“可继续”。一个好系统应该允许：

- 同一步超时后只重试那一步；
- 已执行的副作用不重复做；
- 需要人工接管时，把现场和断点交出来；
- 服务重启后还能接着跑，而不是从头找状态。

这其实是在约束 Agent 的自治边界：能自动恢复的继续，不能安全恢复的停住。

## 怎么判断它有没有用

- 如果任务里有写操作，就必须有 checkpoint，不然重试很容易重复发消息或重复写库。
- 如果失败后只能“重新开始”，说明系统没有把步骤状态和副作用拆开。
- 如果同一错误连续重试仍然失败，应该升级成人工接管，而不是无脑重试到超时。
- 如果恢复逻辑看不出当前处于哪一层，就很难判断该回滚、重试还是续跑。

判断一个真实系统，直接看它能不能回答：失败点前最后一个成功状态是什么？哪些动作已经不可逆？恢复时会不会重复扣费、重复发布或重复通知？

## 最近冒出来的词

OpenAI Release Notes 在 2026-08-18 提到 Codex Remote 的任务可靠性更新，包括任务消息失败后的 Retry、空闲或重连后任务丢失的修复。它不是一个新理论，但很贴近今天这节：系统要把“失败现场还能不能接着跑”当成产品能力，而不是把失败当成终点。

## 一个小例子

```txt
Input:
用户说：“把今天的 AI Agent Daily 写好并发布。”

Process:
1. 写入 Markdown，状态变成 draft_saved。
2. git commit 成功，状态变成 commit_created。
3. git push 超时，状态变成 publish_pending。
4. 恢复时只重试 push，不重新生成正文。

Output:
最终结果：文章内容已定稿，发布未完成。
下一次恢复点：publish_pending。
```

这里的关键不是“失败了怎么办”，而是“失败后还剩什么”。只要断点还在，系统就不是从零开始的。

## 常见误区

1. 把重试当恢复。重试只是在赌下一次成功，恢复要先保证不会重复副作用。
2. 只存错误信息，不存步骤状态。知道报错原因，不代表知道该从哪一步继续。
3. 失败后直接整单重跑。对写库、发消息、发布文档这类任务，这通常最容易出事故。
4. 所有失败都交给模型自己想办法。真正该做的是程序先判定能否自动续跑，再决定是否让模型补救。

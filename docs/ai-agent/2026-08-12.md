# 幂等：Agent 恢复时为什么不能把动作做两遍？

## 今天先记住

幂等（Idempotency）不是“别失败”。它解决的是：失败、重试、恢复、重复消息出现时，同一个意图最多造成一次真实副作用。

## 它在大地图里的位置

::: tip 今日坐标
**评估 / 修正 → 幂等**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

昨天讲 checkpoint：系统要知道断在哪里。今天接着往后看：知道断点还不够，恢复时还要判断“哪些动作已经生效，哪些可以重试，哪些绝对不能再来一遍”。

Agent 的风险常常不在模型答错一句话，而在它真的调用了外部系统。写文件、发消息、扣款、提交代码、删除数据，这些动作一旦重复，错误就从文本世界跑进现实系统。

## 它到底是什么

幂等的意思是：同一个操作被执行一次或多次，最终系统状态一致。

在 Agent 里，更实用的说法是：每个有副作用的动作都要带一个可识别的意图编号，比如 `idempotency_key`、`run_id + step_id`、订单号、文件路径加内容 hash。执行前先查这个编号是否已经成功；成功过就返回已有结果，而不是重新做。

它和 checkpoint 是一对：checkpoint 记录“我走到哪了”，幂等保护“我恢复时不会重复伤害外部世界”。

## 为什么 Agent 里会用到它

Agent 天生会遇到不确定状态：模型调用超时，但工具其实已经完成；网络断开，但远端已经收到了请求；用户重复发了一句“发布今天的文章”；进程重启后从 checkpoint 继续。

如果没有幂等，系统只能在“可能没做”和“可能做过”之间猜。猜错一次，就可能重复发布、重复发送、重复扣费，或者生成两份互相冲突的文件。

有幂等后，恢复逻辑会变成明确判断：先用 key 查询结果，已成功就复用，未成功再执行，执行中卡住就标记为 `pending` 或交给人工确认。

## 怎么判断它有没有用

- 如果工具动作会改变外部状态，就必须设计幂等；只读查询通常不需要。
- 如果动作可能被自动重试，必须有稳定 key，不能每次重试都生成新编号。
- 如果外部系统不支持幂等 key，就在本系统保存动作记录，并在执行前做去重检查。
- 如果动作不可逆，比如删除、付款、群发消息，除了幂等，还要加人工确认和审计记录。

## 最近冒出来的词

今天记一个 `unsafe replay`。OpenAI Agents SDK v0.20.0 在 2026-08-11 的 release notes 里提到允许应用审批 unsafe replay。

这不是一个花哨概念，而是在说：有些恢复或重放动作可能再次触发副作用，不能默认自动执行。

它和今天的幂等正好连在一起：可重放不等于可安全重放，系统要能区分“重新读状态”和“重新做动作”。

来源提示：OpenAI Agents SDK GitHub Releases，2026-08-11。

## 一个小例子

```txt
Input:
用户说：“生成并发布 2026-08-12 的 AI Agent Daily。”

Process:
1. 系统生成 key = ai_daily:2026-08-12:publish。
2. 写文件前检查目标文件是否已存在，内容 hash 是否一致。
3. commit 前检查今天的文件是否已经在某个提交里。
4. push 失败后恢复任务，只重试 push，不重新生成文章。

Output:
第一次执行：state 从 draft -> committed -> pushed。
恢复执行：发现 committed 已完成，只继续 pushed。
不会产生两篇 2026-08-12，也不会重复提交同一份内容。
```

判断一个真实系统时，可以直接问：每个写操作有没有稳定 key？恢复时是复用结果，还是盲目再跑一遍？这个问题比“有没有 Agent 框架”更能看出工程底子。

## 常见误区

1. 以为有重试就可靠。没有幂等的重试，只是在提高重复副作用的概率。
2. 把幂等 key 做成随机 UUID。随机 key 只能标识一次请求，不能标识同一个业务意图。
3. 只给 API 做幂等，不给本地文件、消息发送、git 提交做幂等。
4. 认为 checkpoint 能自动防重复。checkpoint 只是状态依据，真正防重复还要靠动作层校验。

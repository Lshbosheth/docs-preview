# Subagent、Tool Calling、Handoff：Agent 协作到底该怎么选？

## 今天先记住

这三个词都像“让别人帮忙”，但边界不同：**Tool Calling 调能力，Subagent 委派子任务，Handoff 转移控制权**。选错模式，最后容易变成权限、状态和责任没人说得清。

## 它在大地图里的位置

::: tip 今日坐标
**规划 / 路由与工作流编排 → ▶ Agent 协作方式**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> ▶ 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

先判断：到底是调用能力、委派子任务，还是转移控制权。

## 它到底是什么

可以这样区分：

- **Tool Calling**：调用一个明确能力，当前 Agent 仍负责解释结果和决定下一步。例如查库、发消息。
- **Subagent**：委派一个可独立验收的子任务，父 Agent 仍拥有总目标。例如让检索 Agent 找资料并返回带来源的结果。
- **Handoff**：另一个 Agent 接管后续执行，责任和控制权一起转移，必须交出目标、事实、待办、权限和回退入口。

记住：工具给结果，Subagent 给产物，Handoff 交控制权。

## 为什么 Agent 里会用到它

Agent 出现多个能力或角色后，边界就会变成工程问题。查一个数据不必拆 Subagent；转人工也不能当普通 Tool Calling；所有工作都 handoff，则会让状态在每一跳重新解释。

选择顺序：

1. 一次明确动作，用 Tool Calling。
2. 可独立验收、主 Agent 还要汇总，用 Subagent。
3. 后续权限或职责已属于另一个角色，用 Handoff。
4. 发布、删除、付款等副作用，定义唯一责任人和幂等键。

## 怎么判断它有没有用

- 只需要结构化结果时，不要为了“智能协作”拆 Agent。
- 父 Agent 仍决定最终答案，通常是 Subagent；接手者可以直接执行后续动作，才像 Handoff。
- 接手者若没有不同工具或更窄权限，多 Agent 往往只是多一层转述。
- 重启后必须分清“等子任务结果”和“已交接给 B”。

一个很实用的判据是看“下一次动作由谁决定”：如果父 Agent 拿到结果后仍决定下一步，是 Subagent；如果接手者可以直接继续执行且父 Agent 只等待回报，是 Handoff；如果只是执行一次受约束的动作，就是 Tool Calling。故障演练时，父 Agent 汇总前崩溃应恢复“等待结果”，handoff 后接手者崩溃应恢复接收方 checkpoint。

## 一个小例子

```txt
Input:
用户说：“检查文档，合规后提交并推送；需要改内容就交给修订 Agent。”

Process:
1. 主 Agent 调用 scan 工具，得到结构化结果。
2. 读取报告是 Tool Calling，主 Agent 仍负责判断。
3. 发现文案问题时委派修订 Subagent，要求返回 diff 和风险说明，主 Agent 汇总建议。
4. 发布责任交给受限 Agent 时，先写 checkpoint，再 Handoff。

Output:
输入 `scan_status=passed`、`pending=[publish]`，输出状态依次是 `tool_result`、`awaiting_subagent`、`handed_off`；三者的 owner、工具和恢复入口不同。
```

## 常见误区

1. 看到“另一个模型”就叫 Subagent，忽略独立任务和责任边界。
2. 把 Tool Calling 结果当成控制权转移，主 Agent可能继续越权执行。
3. Subagent 只有长报告，没有结构化状态，父 Agent无法判断是否完成。
4. 多个 Agent 都能发布，却没有唯一 owner 或幂等键。

# 审计记录：Agent 为什么要给每次动作留账？

## 今天先记住

Agent 不是只要“最后答对”就够了。只要它会读外部数据、调用工具、修改状态或等待人工批准，就必须留下审计记录（Audit Log）：谁发起、模型怎么判断、调了什么工具、参数是什么、结果如何、有没有被拦截。否则一旦出错，你只能猜。

## 它在大地图里的位置

::: tip 今日坐标
**评估 / 修正 → 审计记录**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

审计记录站在“动作已经发生或即将发生”的位置。它不替 Agent 做决定，但它让每个决定能被回放、解释和追责。

## 它到底是什么

审计记录不是普通日志的豪华版。普通日志常常写“请求失败了”；审计记录要写清楚“哪个主体，在什么上下文里，尝试对哪个资源做什么动作，系统为什么允许或拒绝”。

一条有用的记录至少包含：

```txt
run_id / user_id / thread_id
目标与当前步骤
工具名、参数、权限级别
模型输出与程序校验结果
外部系统返回值
最终状态：success / blocked / waiting_for_approval / failed
```

它的重点不是把所有上下文原样塞进去，而是留下足够的证据，让人能判断系统当时是否按规则运行。

## 为什么 Agent 里会用到它

Agent 的风险来自“模型输出会接到真实动作”。比如它可能发布文档、写文件、发消息、调用内部接口。出问题时，最终答案通常看不出原因：是模型选错工具、参数被工具结果污染、权限校验漏了，还是人工审批状态没有恢复？

审计记录把这些状态变化串起来。它让你能回答三个问题：这次动作是谁授权的？系统有没有执行权限检查？失败后能不能从安全位置恢复？

## 怎么判断它有没有用

- 如果系统有写入、发布、删除、转账、发消息等副作用工具，就必须做审计。
- 如果只记录自然语言回答，不记录工具参数和权限判断，排障时仍然不够。
- 如果用户问“为什么刚才没执行”，系统能指出 blocked 的规则和对应参数，审计记录就开始有用了。
- 如果记录里含有密钥、私聊原文或完整敏感文档，那不是审计，是新的泄露面；要做脱敏和最小保留。

## 最近冒出来的词

LangSmith 最近在 Cloud changelog 里提到 Trace 详情会展示 LLM Gateway 的结果、策略限制、选用模型、fallback 尝试，并给被网关拦截的运行显示 Blocked 标记。它不是一个全新理论，更像是把“模型调用为什么被允许或拦住”放进可观测轨迹里。和今天的主题关系很直接：Agent 的安全边界不能只存在代码里，也要能在事后被看见。

## 一个小例子

```txt
Input:
用户说：“把今天的 AI Agent Daily 发到文档站。”

Process:
1. 系统创建 run_id=2026-08-25-ai-agent-daily。
2. Agent 生成 Markdown，准备写入 docs/ai-agent/2026-08-25.md。
3. 程序检查文件路径、frontmatter 日期、是否包含敏感信息。
4. 校验通过后提交 git commit，再执行 git push。

Output:
audit_log 记录 write_file=success、secret_scan=passed、git_commit=success、git_push=success。
如果敏感扫描命中，状态改为 blocked，并只保留本地路径，不发布。
```

拿这个例子去判断真实系统：你不只问“它能不能发布”，还要问“发布前检查了什么，失败后谁能看懂为什么停下”。

## 常见误区

1. 只记错误，不记成功动作；成功的危险操作同样要能追溯。
2. 把模型完整上下文全存下来，结果审计记录本身变成隐私风险。
3. 只记录工具名，不记录参数、权限级别和状态转移。
4. 以为有日志就等于可审计；没有稳定 ID、时间线和决策原因，日志很难回放。

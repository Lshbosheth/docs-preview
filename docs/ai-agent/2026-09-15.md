# 多 Agent handoff：交接的不是一句话，而是一份可恢复状态

## 今天先记住

Handoff（交接）不是“把对话转给另一个 Agent”这么简单，而是把任务目标、已确认事实、未完成事项、权限边界和下一步责任，交给另一个执行者，并让系统能继续、能追踪、能失败后找回责任人。

## 它在大地图里的位置

::: tip 今日坐标
**规划 / 路由与工作流编排 → ▶ 多 Agent handoff**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> ▶ 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

前面已经看过什么时候值得拆 Agent，今天往下钻一层：当控制权真的从 Agent A 转到 Agent B，系统怎样避免上下文丢失、重复执行和“大家都以为别人会收尾”。

## 它到底是什么

一次合格的 handoff，至少要包含五类信息：

- **目标**：最终要完成什么，以及成功条件是什么。
- **事实**：已经验证过的输入、工具结果和关键约束。
- **待办**：哪些步骤已完成，哪些步骤还没做。
- **责任**：现在由谁接管，接管后允许调用哪些工具。
- **回退**：B 失败时回给 A、转人工，还是停止并保留现场。

可以把它看成一个结构化状态，而不是一段自然语言：

```txt
handoff = {
  task_id,
  objective,
  verified_facts,
  completed_steps,
  pending_steps,
  allowed_tools,
  owner: "agent-b",
  return_to: "agent-a"
}
```

A 可以负责收集需求和路由，B 负责执行发布；但 B 不应该重新猜测用户目标，也不能因为没看到 A 的工具结果就重复检查或重复写入。

## 为什么 Agent 里会用到它

多 Agent 的价值来自边界：不同 Agent 可以拥有不同的上下文、工具和权限。问题也正出在边界上：交接如果只有一句“请继续处理”，B 就不知道哪些话是用户原话，哪些是 A 的猜测；更不知道外部写操作到底完成没有。

因此，handoff 既是路由动作，也是一次状态提交。交接前，A 应先把状态写入 checkpoint；交接成功后，B 才获得执行权。两边都要带 `task_id` 和版本号，避免旧状态覆盖新状态。

## 怎么判断它有没有用

- 如果换一个 Agent 后必须重新读完整聊天记录，说明交接协议不够结构化。
- 如果 A 和 B 都可能调用同一个写工具，必须明确唯一 owner，或使用同一个幂等键。
- 如果 handoff 后失败没人知道该负责，说明缺少 `owner`、`return_to` 或最终状态。
- 只有角色、权限或上下文确实不同才拆 Agent；只是换一个提示词，通常用同一 Agent 的工作流分支更简单。

判断真实系统的方法很直接：在交接完成、B 尚未执行时杀掉进程，再恢复运行。若系统能凭 `task_id + checkpoint` 找到唯一接管者和待办步骤，而不是重新从头猜，就说明 handoff 不是表演。

## 最近冒出来的词

今天不追新词，先把主线概念讲稳。

## 一个小例子

```txt
Input:
用户说：“检查文档通过后提交并推送；如果发现敏感信息就停下。”

Process:
1. Agent A 负责扫描和判断路由，得到 scan_status=passed。
2. A 写入 checkpoint：目标、扫描结果、文件版本、尚未执行 push。
3. 交接给 Agent B，并限制 B 只能调用 commit / push 工具。
4. B 发现 commit 已存在，使用同一个 task_id 查询结果，不重新创建提交。

Output:
状态从 routed -> handed_off -> committed -> pushed；
若 B 超时，系统知道当前 owner 是 B，回退入口是 A，而不是生成第三个 Agent 继续乱试。
```

## 常见误区

1. 把完整聊天记录当成交接协议，导致猜测、旧指令和无关上下文一起传过去。
2. 只传“已经做了什么”，不传“还差什么”和成功条件，接手者无法判断何时结束。
3. 让多个 Agent 共享写权限，却没有 owner 和幂等键，失败恢复时容易重复副作用。
4. 以为 Agent 数量越多越专业；如果没有清晰边界，多 Agent 只是多几处状态丢失点。

## 今天自测

1. 你的 handoff 数据里，哪些字段是事实，哪些字段只是 Agent 的推断？
2. 交接发生后，谁拥有下一次外部写操作的唯一责任？
3. 如果接手 Agent 在执行成功后崩溃，系统靠什么恢复，而不是再次执行？

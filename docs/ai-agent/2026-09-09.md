# Agent 评估：别只看最后一句回答

## 今天先记住

Agent 评估不是给最终答案随手打个分，而是检查一次运行有没有沿着正确路径，拿到正确结果，并在失败时留下可定位的证据。

## 它在大地图里的位置

::: tip 今日坐标
**评估、可观测性与可靠性 → ▶ Agent 评估**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

评估位于整条闭环的“回看”位置：它既可以在运行后判断结果，也可以在运行中决定重试、换工具或停下来。没有评估，Agent 只能把“模型说完了”误当成“任务完成了”。

## 它到底是什么

一次 Agent 运行至少有三层可评估对象：

- **结果（Outcome）**：文件是否真的生成、消息是否真的发出、状态是否达到目标。
- **轨迹（Trace）**：模型调用、工具选择、参数、返回值、重试和状态转移是否合理。
- **成本约束**：用了多少步、耗时多久、消耗多少 Token，是否超过预算。

因此“这次回答不错”并不等于“这次运行合格”。一个 Agent 可能文字解释得很漂亮，却调用了错误的工具；也可能最后结果碰巧正确，但中间重复发布了两次，留下了更危险的副作用。

## 为什么 Agent 里会用到它

普通问答常用人工抽样看答案；Agent 还会改变外部状态，所以必须验证动作和过程。

评估可以分成两种：

1. **离线评估**：拿固定任务集反复跑，比较成功率、工具选择、引用准确率、平均步数。
2. **在线评估**：真实运行时记录 trace，发现超时、坏参数、重复动作或人工拒绝，触发告警和修正。

一个实用的判断顺序是：先问“目标状态到了吗”，再问“有没有越权或多做动作”，最后才看“表达是否漂亮”。顺序反过来，系统很容易优化成会说话、不会办事。

## 怎么判断它有没有用

- 任务有明确完成条件时，优先写成可检查的断言，例如“目标文件存在、日期正确、远端分支出现提交”。
- 任务会调用工具时，至少保存输入、工具参数、结果和状态变化；只有最终文本无法解释失败。
- 失败可重试时，记录失败类型和重试次数；不要把所有失败都归因于“模型发挥不好”。
- 不能稳定定义成功条件的开放式任务，可以做人工抽样或成对比较，但要承认它不是精确指标。

判断真实系统时，可以追问：它的“成功”是一个布尔字段，还是能指出哪条断言、哪一步工具调用失败？

## 一个小例子

```txt
Input:
用户说：“生成 2026-09-09 的日报并发布。”

Process:
1. Agent 生成 Markdown，调用文件检查工具和 git 工具
2. Trace 记录 path、frontmatter date、commit message、push 返回值
3. 评估器检查：
   - 文件是否为 docs/ai-agent/2026-09-09.md
   - title / H1 是否是主题标题
   - 是否包含敏感信息
   - push 是否成功且只提交相关文件

Output:
全部断言通过 -> published
日期错误 -> draft_rejected，要求修正
检测到私密信息 -> publish_blocked，不执行 push
```

这里的评估不是再让模型读一遍文章说“看起来没问题”，而是把关键要求变成可观察的输入、状态和断言。以后出了问题，可以回答“哪条规则没过”，而不是只剩一句“Agent 这次不太稳定”。

## 常见误区

1. 只评最终文本，不评工具调用和外部状态。
2. 用一次成功样本证明系统可靠，忽略超时、重复消息和坏参数。
3. 指标越多越好，却没有和具体失败模式绑定。
4. 把 LLM-as-a-Judge 的主观评分当成事实校验；它适合补充，不应替代文件、数据库或 API 的直接断言。

## 今天自测

1. 你的 Agent 任务，完成状态能写成哪三个可检查断言？
2. 哪些失败必须从 trace 里看，最终回答看不出来？
3. 如果结果正确但工具调用重复了一次，这次运行算成功还是失败？为什么？

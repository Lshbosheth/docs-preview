# 审批后的断点续跑：人批完之后 Agent 怎么继续

## 今天先记住

Human-in-the-loop 真正难的不是“停下来等人”，而是人批完以后，Agent 能不能从正确的位置、带着正确参数继续跑。

## 它在大地图里的位置

::: tip 今日坐标
**权限、安全与人工接管 → ▶ 审批后的断点续跑**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

昨天讲的是 Agent 什么时候必须让人接一手。今天把镜头再往后推一步：人已经批准、拒绝或改了参数，系统接下来怎么办？

这一步横在“安全”和“可靠性”中间。没有它，审批只是一个弹窗；有了它，审批才会变成可恢复的运行状态。

## 它到底是什么

审批后的断点续跑，是把一次 Agent 运行拆成可保存、可恢复的状态机。

暂停前，系统要保存：当前目标、准备执行的动作、工具参数、已完成步骤、等待谁处理、可选结果是什么。人处理后，系统不是重新问模型“接下来怎么办”，而是读取这个断点，根据审批结果走下一条边。

可以把它看成：

```txt
running -> waiting_for_approval -> approved/rejected/edited -> continue/abort/replan
```

关键点是：审批结果必须进入程序状态，而不是只留在聊天记录里。

## 为什么 Agent 里会用到它

Agent 常常会碰到“写草稿没问题，真正执行要谨慎”的动作：发消息、提交代码、发布文档、改配置、删除文件。

如果系统没有断点续跑，常见故障会很具体：用户批准的是 A 文件，Agent 重新规划后却改了 B 文件；审批前工具参数是 `dryRun=true`，恢复时变成了真实执行；网络失败后用户又点了一次确认，系统重复发布两遍。

所以这里的目标不是抽象地“更可靠”，而是保证外部世界只被正确地改一次。

## 怎么判断它有没有用

- 如果审批后动作会写入、发送、删除或发布，必须保存断点。
- 如果人可以修改参数，恢复时要使用修改后的参数，并记录旧值和新值。
- 如果工具调用可能重复造成副作用，要给动作加 `run_id`、幂等键或已执行标记。
- 如果只是让用户补一句普通上下文，再继续生成草稿，可以不做复杂断点；但一旦进入外部系统，就别靠聊天历史硬续。

判断一个真实系统时，问一句就够：审批完成后，它是从数据库里的 `pending_action` 恢复，还是又把整段对话丢给模型猜？

## 一个小例子

```txt
Input:
用户说：“生成今天的学习文档并发布。”

Process:
1. Agent 写出 Markdown，生成待发布动作 publish_doc
2. 系统保存 pending_action：
   path=docs/ai-agent/2026-09-08.md
   target=origin/main
   commit=docs(ai-agent): add daily lesson 2026-09-08
3. 人批准后，系统读取 pending_action 执行 commit 和 push
4. 如果人改了标题，状态变成 edited，再重新检查文件和 commit 信息

Output:
approved -> committed -> pushed -> published
rejected -> draft_kept -> publish_aborted
edited -> revalidated -> waiting_or_published
```

这个例子里，Agent 不应该在批准后重新发散规划。它要做的是沿着已经审过的动作继续走，并在参数改变时重新校验。

## 常见误区

1. 只记录“用户同意了”，不记录同意的是哪个动作和哪些参数。
2. 审批后重新调用模型规划，导致批准对象和实际执行对象不一致。
3. 没有幂等控制，用户重复点击或网络重试会重复执行。
4. 拒绝后没有清理 pending 状态，下次运行误把旧审批捡起来。

## 今天自测

1. 你的 Agent 暂停前，至少要保存哪五类状态？
2. 用户把审批参数改了，系统应该直接执行还是重新校验？
3. 哪些工具动作必须设计幂等键，不能只靠“别重复点”？

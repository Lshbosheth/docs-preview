# 成本与延迟：Agent 不是越多想一步越好

## 今天先记住

Agent 的每一次“多想一步”，都会变成真实的模型调用、工具等待、状态保存和失败重试。成本与延迟不是上线后才优化的性能问题，而是决定系统能不能稳定闭环的设计约束。

## 它在大地图里的位置

::: tip 今日坐标
**横跨整条链路 → 成本与延迟**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

前面讲评估，是为了知道 Agent 有没有做对。今天把视角再拉高：即使每一步都“看起来合理”，如果它为了一个小目标跑了十几次模型、等了三分钟、花掉一堆 Token，这个系统也不一定可用。

## 它到底是什么

成本（Cost）不只是模型费用，还包括检索、工具 API、重试、队列、存储、人工审批和运维排障。延迟（Latency）也不只是首字出来得慢，而是从用户提出目标，到系统完成副作用动作并返回可验证结果的总时间。

一个 Agent 运行可以粗略拆成：

```txt
总延迟 = 模型思考 + 检索 + 工具调用 + 排队 + 重试 + 人工等待 + 输出传输
总成本 = Token + 工具费用 + 失败重跑 + 状态存储 + 人工检查
```

所以，“让模型再判断一下”不是免费保险。它可能减少一次错误，也可能只是把简单规则变成昂贵等待。

## 为什么 Agent 里会用到它

普通 Chatbot 多半只生成文本；Agent 会循环：拿上下文、做计划、调工具、观察结果、再修正。循环越长，越容易出现两类问题：一是用户等不到结果，二是系统在失败路径里越跑越贵。

比如“发布一篇日课”这种任务，真正该贵的是内容生成和必要检查；不该贵的是反复读取同一份框架、重复搜索同一个标题、失败后重新生成整篇文章。好的 Agent 会把预算写进运行策略：最多几步、哪些工具可并行、哪些失败可以重试、哪些结果应该缓存。

## 怎么判断它有没有用

- 如果任务有明确 SLA，例如 10 秒内必须回复，Agent loop 就要有步数上限和快速失败路径。
- 如果工具调用慢但彼此独立，例如同时读框架、读最近文章、查 git 状态，就应该并行；如果后一步依赖前一步结果，才串行。
- 如果同一个中间结果会被多次使用，例如课程框架、用户画像、检索结果，优先缓存或传递状态，不要让模型反复“回忆”。
- 如果失败会触发重试，必须问：重试会不会重复发消息、重复扣费、重复提交？没有幂等设计，便宜重试也会变成贵事故。

看真实系统时，可以直接追问一句：这条任务最坏会跑多少次模型、调多少次外部工具、等多久才停？答不上来，说明成本与延迟还没有进入设计。

## 最近冒出来的词

最近可以留意 Trigger.dev v4.5.14 里的 “cursor resumption”。它不是新理论，而是实时流恢复能力：前端重新订阅时，可以从游标位置继续接收任务输出，而不是把长任务当成断掉重来。

这和今天的主题有关：长 Agent 任务最怕连接一抖就重跑，既拖慢用户感知，也放大成本。能从游标恢复，意味着系统把“传输中断”和“任务失败”分开处理。

来源提示：Trigger.dev Changelog，2026-08-28。

## 一个小例子

```txt
Input:
用户要求：“生成并发布 2026-08-31 的 AI Agent Daily。”

Process:
1. 并行读取课程框架、最近几篇文章、git 状态
2. 只生成一次正文，随后做敏感信息和格式检查
3. git add 只加入当天 Markdown
4. push 失败时只重试 push，不重新生成文章

Output:
成功：新增 /ai-agent/2026-08-31 页面，并返回 URL
失败：停在可恢复状态，保留已生成文件和失败原因
```

这里的判断点很具体：生成正文失败可以重试模型；网络 push 失败不应该重写文章；发现无关文件不应该继续提交。

## 常见误区

1. 以为“多调一次模型确认”一定更稳，却没检查它是否真的减少了某个具体失败。
2. 只优化首字延迟，忘了 Agent 的完成时间还包括工具、队列、审批和重试。
3. 没有预算上限，让 Agent 在目标不清或工具失败时无限循环。
4. 把所有步骤串行执行，导致独立读取、检索、校验白白排队。

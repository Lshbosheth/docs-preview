# 硬断言与软评分：Agent 评测怎么避免被平均分骗了

## 今天先记住

能用程序确定的事实要做硬断言，表达质量再用软评分。否则一次“回答挺像样”就可能掩盖重复发送、日期错误或越权操作。

## 它在大地图里的位置

::: tip 今日坐标
**评估、可观测性与可靠性 → ▶ 硬断言与软评分**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

前两天我们把评测集和轨迹放进了地图。今天再缩一层：同一条样本里，有些结果能直接判定，有些只能比较好坏。

## 它到底是什么

**硬断言（hard assertion）**是程序能直接判断的条件，例如文件路径、JSON 字段、工具参数，或状态是否从 `draft` 变成 `published`。失败就是失败，不需要模型解释。

**软评分（soft score）**用于难以完全形式化的质量，例如摘要是否清楚、解释是否覆盖关键点，可由人工、规则或 LLM-as-a-Judge 给出。

硬断言负责“算不算完成”，软评分负责“完成得好不好”。前者不过，后者再高也不能放行。

## 为什么 Agent 里会用到它

Agent 还会调用工具、改变状态、留下副作用。若把“文件存在”和“文案好不好”压成一个分数，系统可能得 8 分，却已把错误文件推到远端。

评测时先查路径、日期、权限、参数和最终状态；通过后再评估内容和表达。报告同时展示断言、评分、轨迹和成本。

## 怎么判断它有没有用

- 能由文件、数据库或 API 直接验证的事实，优先写成硬断言。
- 失败会造成发送、删除、发布或重复写入时，必须设硬门槛，不能被平均分抵消。
- 目标存在多个合理答案时，才引入软评分，并固定 rubric（评分标准）。
- 如果分数变了却说不清是哪条断言、哪一步轨迹变了，这套评测还不能支持工程决策。

判断真实系统时，问：“它能否区分‘没完成’和‘完成但质量一般’？”

## 最近冒出来的词

**Shell sandbox（Shell 沙箱）**最近在 Agent 平台里变得更正式。Google Cloud 在 2026-09-09 宣布 Gemini Enterprise Agent Platform 的 Computer Use 和 Shell sandboxes GA，可在隔离 Linux 容器里执行不可信命令。

它和今天的关系是：评测需要可重复的执行环境。沙箱减少环境差异，但文件、权限和状态仍要靠硬断言与轨迹检查。

来源提示：Google Cloud release notes，2026-09-09。

## 一个小例子

```txt
Input:
用户说：“生成 2026-09-11 的 AI Agent Daily 并发布。”

Process:
1. 硬断言检查：路径、frontmatter date、H1、敏感信息、提交文件集合和 push 结果
2. 任一硬断言失败 -> publish_blocked
3. 全部通过后，软评分检查结构、例子和表达质量

Output:
路径正确但日期错误 -> 硬失败，不能发布
硬断言全通过、软评分 7/10 -> 已完成，但质量一般
```

“不能发布”和“发布了但还可以润色”不能被一个 `8.0` 混成一件事。

## 常见误区

1. 用 LLM 评分替代文件、数据库和 API 的直接校验。
2. 把多个硬失败平均掉，让关键副作用仍被判为通过。
3. 只保存总分，不保存 rubric、失败断言和轨迹。

## 今天自测

1. 你的一个 Agent 任务里，哪三个条件必须是硬断言？
2. 哪些质量只能用软评分，为什么不能直接写成布尔值？
3. 如果平均分上升，但重复工具调用增加了，这次改动应该算成功吗？

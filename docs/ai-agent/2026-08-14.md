# 熔断：Agent 什么时候应该停止调用外部系统？

## 今天先记住

熔断（Circuit Breaker）不是“系统坏了就摆烂”。它是在连续失败、远端限流或风险升高时，主动暂停某类调用，把 Agent 从“越错越忙”拉回到可恢复、可解释的状态。

## 它在大地图里的位置

::: tip 今日坐标
**评估 / 修正 → 熔断**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> ▶ 评估 / 修正
  -> 最终输出
```

前几天讲了 checkpoint、幂等、重试与退避。它们解决的是：失败后从哪里恢复、会不会重复做、什么时候再试。今天再往系统外圈看一层：如果失败不是偶发，而是某个工具或远端服务已经明显不健康，Agent 就不该继续撞墙。

熔断的位置很靠后，但影响整条链路。它会反过来改变规划：原计划要查接口、发消息、提交代码；一旦工具进入熔断，系统要么换备用路径，要么保存现场并告诉人“现在不能安全继续”。

## 它到底是什么

熔断来自分布式系统。最简单的模型有三种状态：

- `closed`：正常调用。
- `open`：暂时禁止调用，直接返回“不可用”。
- `half-open`：过一段时间后放一小部分请求试探，成功再恢复，失败继续熔断。

放到 Agent 里，熔断对象不一定是整个系统，也可以是某个工具、某个外部 API、某类高风险动作，甚至某个用户任务的执行分支。

关键不在名字，而在边界：连续 429、5xx、超时、权限异常，或者同一工具把预算烧到上限，都应该让 runtime 改状态，而不是让模型一句“再试试”就继续执行。

## 为什么 Agent 里会用到它

Agent 会自己决定下一步，所以它比普通脚本更容易把小故障放大。一个发布流程里，模型可能连续尝试 `git push`；一个资料检索流程里，模型可能不断改写查询词打同一个搜索接口；一个消息机器人里，模型可能在发送失败后反复补发。

没有熔断，失败会变成三种具体问题：成本失控、远端被打得更坏、用户收到重复或延迟很久的结果。

有熔断后，系统会把“当前不该继续调用”变成明确状态，交给规划层处理：换只读查询、等待恢复、请求人工确认，或者保存 checkpoint 后停止。

## 怎么判断它有没有用

- 如果某个工具失败会消耗限额、金钱或外部服务容量，就应该有熔断。
- 如果连续失败的原因大概率不是改 prompt 能解决，比如 429、5xx、网络不可达，熔断比继续让模型思考更有用。
- 如果动作有副作用，熔断恢复后必须配合幂等检查，不能半开试探时重复发消息或重复提交。
- 如果任务是本地纯计算、失败可立即定位为输入错误，熔断通常不是第一选择，先做校验和错误提示。

## 最近冒出来的词

今天记一个 `trace_policy`。LangGraph 在 2026-08-11 发布的 `langgraph==1.2.11` release notes 里提到，在 `add_node` 上暴露 `trace_policy`。

它是框架功能名，不是全新的 Agent 理论。直白说，就是让开发者能更细地控制节点级追踪策略。

它和今天的熔断有关：没有足够清楚的 trace，你很难判断一个工具是偶发失败，还是已经该进入熔断状态。

来源提示：LangGraph GitHub Releases，2026-08-11。

## 一个小例子

```txt
Input:
用户说：“把今天的 AI Agent Daily 发布到文档站。”

Process:
1. 系统生成 Markdown，并完成 git commit。
2. git push 连续 3 次返回网络超时。
3. runtime 记录 push_tool.failure_count = 3，把 push_tool 状态改为 open。
4. Agent 不再重新生成文章，也不再继续 push。
5. 系统保存 checkpoint：file_written=true, committed=true, pushed=false。

Output:
任务状态从 publishing -> push_circuit_open。
最终返回：“文章已本地提交，但远端 push 连续失败，已暂停自动重试，保留 commit_sha，等待网络恢复后继续 push。”
```

判断真实系统时，可以直接问：它连续失败后有没有“暂停调用”的状态？这个状态是按工具、按用户、按任务，还是粗暴地停掉整个服务？恢复时有没有半开试探和幂等保护？

## 常见误区

1. 把熔断当成报错。报错只是结果，熔断是系统状态变化。
2. 只做重试，不做熔断。连续失败时，重试会从恢复机制变成故障放大器。
3. 熔断粒度太粗。一个搜索接口坏了，不该让本地写文件、读缓存也一起停。
4. 恢复后直接放开全部流量。半开试探失败时，要继续保护远端和用户任务。

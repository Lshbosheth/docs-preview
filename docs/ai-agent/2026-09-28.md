# 预算预占：Agent 开始干活前先锁住什么额度？

## 今天先记住

预算预占（budget reservation）不是只在调用后记账，而是在任务开始前原子地锁住预计会消耗的 Token、工具额度、并发槽或付费配额。实际完成后结算，未用部分释放；请求已经发出但结果未知时，额度应保持 `held`，直到远端状态被确认，不能因为界面显示“已取消”就直接归还。

昨天讲取消与截止时间，解决“什么时候停”。今天往前挪到启动动作之前：即使决定做，也要先确认这次运行还有多少可安全支配的额度。预算从规划层进入模型和工具层，最后在执行结果处结算，因此它横跨整条链路。

## 它到底是什么

预算上限只回答“总共能用多少”，预占还要回答“哪一次运行、哪个步骤正在占用多少”。并发分支同时看到 10 元余额，不代表三个分支都能各花 10 元；如果只是先读余额再调用，它们会一起超支。

一个可执行的预占记录至少包含 `run_id`、`step_id`、资源类型、预估值、硬上限、实际值、状态和幂等键。判断可用额度时使用：

```txt
available = total_budget - settled_cost - reserved_amount
```

只有 `available >= estimate` 时才能原子预占并启动。常见资源不只有 Token，还包括模型调用次数、工具调用次数、并行 worker 槽、限流配额，以及发送、发布、付款等外部资源的配额。

## 为什么 Agent 里会用到它

Agent 的规划和执行常常分开：计划生成了五个步骤，工具在稍后串行或并行执行；失败后还会重试、回退或换模型。若每个节点都在行动后才知道成本，系统只能做事后统计，无法阻止一组并行分支在同一时刻把预算全部花光。

预占把预算变成运行时约束，而不是报表字段。典型状态变化是：

```txt
planned -> reserved -> in_flight -> settled
                     -> released
                     -> outcome_unknown -> held -> reconciled
```

其中“已取消”和“额度已释放”不是同义词。读请求取消后通常能直接释放；写请求若可能已经到达外部系统，应保持占用并查询最终状态，否则恢复运行时可能再次申请同一份额度并重复执行。

## 怎么判断它有没有用

- 只要存在并发分支、重试、回退或按次计费的工具，就应把预占和原子扣减放进调度器，而不是只检查一个共享余额。
- 如果任务是单线程本地计算，成本接近零且不会调用外部系统，简单设上限通常就够，完整预占属于过度设计。
- 预占必须记录估算依据和硬上限。模型不能先无限制消费，再解释自己“只是超了一点”；超过上限时应停止、降级或重新审批。
- 恢复、取消和进程重启后，必须能区分 `settled`、`released` 与 `held`。一个真实系统至少要能回答：这笔额度为何被锁、绑定了哪个步骤、何时释放、是否可能发生重复副作用。

## 一个小例子

```txt
Input:
用户要求生成 2026-09-28 的课程，检查敏感内容，批准后提交并推送。

Process:
1. 根运行预算是 18000 Token、8 次工具调用、1 次远端写入。
2. draft 预留 8000 Token 和 1 次模型调用，scan 预留 2000 Token 和 1 次规则工具。
3. draft 实际使用 7200，差额 800 释放；scan 命中拒绝规则，预留的 2000 全部释放。
4. push 发出前原子申请唯一写入槽；响应超时后状态为 outcome_unknown，写入槽保持 held。
5. 系统用 commit_sha 查询远端，确认提交已存在，才把写入槽结算为 settled。

Output:
available -> reserved(s) -> settled/released
push: in_flight -> outcome_unknown/held -> push_confirmed/settled
```

这条链路不会因为超时再次 push，也不会在取消后假装写入额度已经自动归还。

## 常见误区

1. 只做“读取余额 -> 调用 -> 记账”，并发时仍会集体超支；预占和扣减必须在同一原子操作里。
2. 把预估值当实际成本，完成后不结算、不释放，导致额度只减不还。
3. 一旦收到取消就释放所有额度，忽略已经发出的请求和迟到的成功响应。
4. 只统计 Token，不统计工具次数、并发槽和外部资源，最后仍会在付费接口或发布动作上撞墙。

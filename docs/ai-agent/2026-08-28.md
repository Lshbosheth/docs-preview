# 权限与护栏：模型为什么不能想做什么就做什么？

## 今天先记住

Agent 的自主性只应存在于“怎么完成目标”的选择上，不应自动扩张成“能对外部世界做什么”。模型可以提出工具调用，运行器必须依据权限、参数和风险等级决定是否执行。

```txt
  -> ▶ 执行 / 安全边界

  -> 最终输出
```

昨天的状态机规定“当前状态允许迁移到哪里”，今天的权限系统进一步规定“即使迁移合法，当前主体能不能做这个动作”。两者合起来，才是可控的执行骨架。

## 它到底是什么

权限（Permission）回答“谁能对什么资源做什么操作”；护栏（Guardrail）回答“在执行前后，哪些输入、参数和结果必须被拦截或复核”。

一个实用的最小模型是：

```txt
主体：agent / human
资源：weixin_message / git_repo / production_db
动作：read / write / delete / publish
条件：身份、环境、审批、参数范围、审计记录
```

不要只给工具贴一个 `dangerous: true` 标签。更有用的是把工具拆成明确能力：`read_file` 可以自动执行，`git_push` 需要检查分支，`delete_message` 需要人工确认，生产扣费接口则可能永远不允许模型直接调用。

## 为什么 Agent 里会用到它

模型输出的是意图，不是授权凭证。提示词里写“不要删除生产数据”，不能替代服务端的权限判断，因为恶意文档、用户越权请求、模型误判都可能把删除动作带到执行层。

护栏至少要覆盖三处：进入模型前过滤明显恶意或敏感输入；模型产出工具调用后校验名称、参数和权限；工具返回结果准备给用户前检查是否泄露密钥、隐私或内部数据。高风险动作还要进入人工确认，并把确认人、时间、目标和参数写进审计记录。

## 怎么判断它有没有用

- 如果工具会写数据、发消息、发布代码、删除资源或产生费用，就不能只靠 Prompt 约束。
- 如果同一个 Agent 在开发、测试、生产环境权限不同，权限必须由运行时身份和环境决定，不能由模型自己选择。
- 如果参数存在范围风险，例如收件人、金额、分支名或文件路径，必须在工具层做白名单、格式和业务校验。
- 看真实系统时，追问：“模型要求删除时，哪一层能拒绝？拒绝后状态是什么？谁能审计？”答不出来，就是把安全边界放错了地方。

## 一个小例子

```txt
Input:
用户说：“把这篇日课提交并发布。”

Process:
模型提出：
1. git add 2026-08-28.md
2. git commit
3. git push origin main

运行器检查：
- 文件路径必须位于 docs-preview/docs/ai-agent/
- commit message 必须匹配指定格式
- 工作区不能把无关文件带入提交
- push 只允许 main，且执行前通过发布策略检查

若检查通过，执行并记录 commit id；
若发现敏感信息或无关文件，转为 blocked，要求人工处理。

Output:
成功时远端出现当天页面；
拒绝时不执行 push，并留下“被哪条规则拦截”的审计事件。
```

这里的关键不是“模型够不够聪明”，而是每个副作用动作前都有一个不能被模型绕过的检查点。

## 常见误区

1. 把系统提示词当成权限系统。Prompt 能表达规则，但不能强制阻止已经发出的工具调用。
2. 只保护输入，不检查工具参数。攻击或误判常常发生在参数层，例如把安全文件名替换成任意路径。
3. 只有允许和拒绝，没有等待确认、可重试失败和审计状态。
4. 为了方便给 Agent 一个万能管理员账号，最后无法判断到底是谁改了什么。

# 幂等性：Agent 重试前必须先确认什么？

## 今天先记住

Agent 可以重试，但不能把同一个动作悄悄做两遍。幂等性要解决的不是“代码更优雅”，而是失败、超时、断线之后，系统再次执行同一步时，外部世界不会被重复改坏。

## 它在大地图里的位置

::: tip 今日坐标
**横跨整条链路 → 幂等性 Idempotency**
:::

```txt
用户目标
  -> 上下文 / 记忆
  -> 规划 / 决策
  -> 工具调用 / 外部系统
  -> 执行 / 观察结果
  -> 评估 / 修正
  -> 最终输出
```

前两天讲 Trace 和失败恢复，是在问“出错后怎么看见现场、怎么退回来”。今天再往前补一颗螺丝：如果某一步可能被重复执行，它一开始就要设计成可识别、可去重、可恢复。

幂等性横跨整条链路。用户目标要有任务 ID，工具调用要有去重键，外部系统要能查询当前状态，评估层要知道“这次是新动作，还是上次动作的继续”。

## 它到底是什么

幂等性（Idempotency）指的是：同一个请求执行一次和执行多次，最终效果一致。

读文件、查天气、搜索资料通常天然接近幂等；发消息、扣款、删文件、提交代码、发布文章就不是。对 Agent 来说，危险常发生在“不知道有没有成功”的夹层：工具超时了，但外部系统可能已经执行；网络断了，但 commit 可能已经推到远端。

所以幂等性不是一句“失败就再试”。它通常需要三个东西：唯一请求标识、执行前状态查询、执行后结果确认。

## 为什么 Agent 里会用到它

Agent 会自己决定下一步，还会根据观察结果重试。模型看到 `timeout` 时，很容易推断“刚才没成功”，但工程上超时只表示“我没拿到结果”，不表示“外部系统没做”。

比如每日文档发布任务里，`git push` 超时后，Agent 不应该重新生成一篇、重新 commit 一次。它应该先查本地 commit，再查远端 main。如果同一个 commit 已经在远端，状态应直接从 `push_unknown` 变成 `published`；如果远端没有，才重试 push。

## 怎么判断它有没有用

- 如果工具会改变外部状态，先问：重复调用会不会产生第二份结果？
- 如果工具可能超时，必须能查到“上一次请求到底有没有生效”。
- 如果不能做到真正幂等，至少要让高风险动作进入人工确认。
- 如果日志里只有 `retry 1/3`，却没有 request_id、目标状态和副作用记录，这套恢复策略还不够上线。

## 最近冒出来的词

`Autonomous SRE Agent` 可以顺手记一下。LangChain 在 2026-08-05 的工程文章里讲 Kubernetes 部署场景里的自治 SRE Agent。

它不是一个全新的理论名，更像把 Agent 放进运维现场后的产品形态：观察告警、诊断服务状态、尝试修复。和今天的主题对应很直接：运维 Agent 如果重启、回滚、扩容这些动作没有幂等和状态确认，失败恢复会从“修系统”变成“制造第二个事故”。

来源提示：LangChain Blog，2026-08-05。

## 一个小例子

```txt
Input:
用户说：“发布 2026-08-06 的 AI Agent Daily。”

Process:
1. 生成 request_id: ai-agent-daily-2026-08-06。
2. 检查目标文件是否已存在，frontmatter date 是否为 2026-08-06。
3. 检查是否已有 commit: docs(ai-agent): add daily lesson 2026-08-06。
4. push 超时后，先查远端是否已有该 commit，再决定是否重试。

Output:
如果远端已有 commit：push_unknown -> published。
如果远端没有 commit：push_unknown -> retry_push。
如果状态无法确认：push_unknown -> needs_human_check。
```

这个例子可以拿去判断真实系统：看它有没有把“请求”“动作”“外部状态”分开。只有一句“我会重试”的 Agent，不算会恢复；能说清“我重试的是哪一个幂等请求，目标状态是什么”，才比较像工程系统。

## 常见误区

1. 把幂等性理解成“不报错”。幂等性关心的是外部效果是否重复。
2. 只在接口层加 request_id，却不查询外部状态。这样只能防一部分重复。
3. 认为只读工具不需要记录。只读可以轻一些，但仍要记录来源和时间，避免旧观察误导后续动作。
4. 把所有写操作都自动重试。删除、发送、支付、发布这类动作，确认状态比重试次数更重要。
